## Gaps

### F-3 · gap · (advisor) a reply with no structured result has no rejection line, and `schema` rejections have no count or "readable" rule
- **Section:** Tech stack and repo layout; Task contract › Plan checks
- **Evidence:** line 70 "An envelope that parses but whose structured result is missing or fails Pydantic validation is a rejected reply." Line 483 "`schema` | Pydantic rejects the reply | the `task_id` when it can be read, otherwise `reply`". Line 495: a rejected reply has "`error` set to its rejection lines, as `rule  subject  message`". Line 493 gives the count for every rule but `schema`. A missing result is not rejected by Pydantic, so it has no rule, subject or message, yet lines 495 and 693 need a line for it. Two readers also differ on a `task_id` that is a string but fails the pattern (`auth-1`): subject `auth-1` or `reply`.
- **Proposed fix:** "A reply whose structured result is missing is one `schema` rejection with subject `reply`. There is one `schema` rejection per Pydantic error; its subject is the `task_id` of the task the error lies in when that is a string, otherwise `reply`."

## Wording

### F-1 · wording · when `plan` writes its warning
- **Section:** CLI commands › Output; Task contract › Planning
- **Evidence:** line 694 "`plan` refuses with one line on standard error and exits 1. The refusals, checked in this order: `no approved spec version`; `policy is invalid; run openfactory validate`; `plan_NN is already approved; use replan`; `git ls-files failed: <error>`; `planner call failed: <error>`." and line 695 "When the spec files differ from the latest approved version, or cannot be loaded, `plan` writes the warning `spec files differ from approved sv_NN` to standard error and carries on". It is not said whether the warning is written before the refusals are checked.
  - Reading A: the warning is written whenever the files differ and an approved version exists, also on a refused `plan`.
  - Reading B: only when `plan` goes on to call the planner.
- **Proposed fix:** "The warning is written after the first three refusals have been checked and before `git ls-files` runs, so a `plan` refused by one of them writes no warning."

### F-4 · wording · (advisor) "cached input tokens" can mean two things
- **Section:** Metrics
- **Evidence:** line 651 "`tokens_in` includes cached input tokens." A runtime can report input tokens read from the cache and input tokens written to it separately.
  - Reading A: only cache reads are added.
  - Reading B: both are added.
- **Proposed fix:** "`tokens_in` is every input token the runtime reports: uncached, written to the cache and read from it." Or leave the sentence and pin it in the adapter task's captured fixture, said explicitly.

### F-5 · wording · (advisor) the new nullable fields contradict an unchanged Metrics sentence
- **Section:** Metrics; Domain model and storage › Event payloads
- **Evidence:** line 651 "Every LLM call and agent run records tokens in, tokens out, cost in USD, and wall-clock latency, so each task and each plan has a known price" against lines 389-391 "`tokens_in: <int> | null  # null when the runtime reported none`" (the same for `tokens_out` and `cost_usd`) and line 70 (a failed process is still recorded).
- **Proposed fix:** "…records wall-clock latency, and tokens in, tokens out and cost in USD when the runtime reports them".

### F-6 · wording · (advisor) `runtime` is not said to be closed or plain
- **Section:** Domain model and storage › Event payloads
- **Evidence:** line 382 "`runtime: "claude-code"`"; line 398 lists "the closed sets a stored payload holds" and does not name `runtime`. One reader types it `Literal["claude-code"]`, which makes the list in line 398 incomplete; another types it `str`.
- **Proposed fix:** "`runtime` is a plain string; Phase 1 writes `claude-code`."

### F-7 · wording · (advisor) `<error>` has no source
- **Section:** CLI commands › Output
- **Evidence:** line 694 "`git ls-files failed: <error>`; `planner call failed: <error>`. `<error>` is a single line."; line 70 "`error` set". Nothing ties the two together or says how a multi-line failure text becomes one line, so a test can assert the prefix only.
- **Proposed fix:** "`<error>` is the first line of the failure's text; for a planner call that text is `AgentRunFinished.error`." It could equally be a decision row in the command task.

### F-9 · wording · (advisor) the widen-only rule is a statement no test can check
- **Section:** Domain model and storage › Event payloads
- **Evidence:** line 398 "may be widened but never renamed or narrowed, so every stored event still validates". It is a rule for future changes, kept by review.
- **Proposed fix:** no change. The rule also stands in the ADR-007 amendment. A fixture of one stored event per closed value would make it testable, and can wait for the M2 payload task.

## Advisor

### Q1: Is F-1 real (the proposal does not say whether a refused `plan` also writes the "spec files differ" warning), and is the proposed sentence the right fix?
- Proposed: add "The warning is written after the first three refusals have been checked and before `git ls-files` runs, so a `plan` refused by one of them writes no warning."
- Challenge: The ambiguity is real. Line 694 orders the refusals, and line 695 says only that `plan` "writes the warning ... and carries on". The fix assumes Reading B is wanted; no document settles it (the SC-30 row says only that "Output" defines the warning). One thing the finding does not cite: line 470 reads "It fails if there is none, and warns if the files on disk differ from it. It fails if an approved plan exists", which puts the warning before the approved-plan refusal and so nudges a reader towards Reading A. The fix sentence is explicit enough to override that, but line 470 is the stronger evidence. The fix also settles the order of the two standard-error lines when `git ls-files` or the planner call fails (warning first).
- Strongest alternative: Reading A, warn as soon as an approved version is known, before the policy and approved-plan checks. It tells the user more on a refusal, but a refused `plan` then loads and hashes the spec files for nothing.
- Conflicts: none.
- Recommendation: the proposed sentence — one fixed point, and a refused `plan` does no spec loading (priority 6).
- Class: wording is right.
- Verdict: AGREE

### Q2: Is F-2 real (the proposal rests on ADR-012, still proposed, and on two drafted amendments, and `check_spec.py` cannot see it), and is "no proposal change; accept them before applying" right?
- Proposed: no change to the proposal; the human accepts ADR-012 and the ADR-005 and ADR-007 amendments before running `./scripts/apply_spec.sh 1.10`.
- Challenge: Real, and the evidence checks out. Read as binding today, two accepted ADRs disagree with the proposal:
  - ADR-007, Decision: "A payload does not reuse a closed domain type where that type may change" against line 398 (closed sets held, widened only) and line 367 (`tasks: [ TaskContract ]`).
  - ADR-011, Decision: "Git operations stay behind the `GitProvider` port, which arrives in M3" against line 402 ("The list of tracked files comes from `GitProvider`, whose first adapter is `git_cli`").
  - The ADR-005 amendment is a clarification, not a conflict: ADR-005 is silent on a failed process.
  - `check_spec.py` does pass: the proposal's only ADR ids are in code blocks or backticks.
  The fix is right but leaves four things unsaid:
  - `apply_spec.sh` step c only warns about `Status: proposed` and then asks y/n. It does not block, and it cannot see an amendment inside an accepted ADR, so the order rests on the human alone.
  - The evidence list is short by two: ADR-001 ("gives the latest approved version, the current draft and the next spec version id") and ADR-006's port list are also extended by line 80 and line 402. ADR-012 covers both once accepted.
  - The ADR-007 amendment covers SC-35 only. Line 344 (SC-40: nested models keep "their own models and defaults") also narrows ADR-007's "Every field is required ... replay never depends on a default that could change" and its rejected alternative "Payload fields with defaults". The amendment should say so in one sentence.
  - Both amendments read "(drafted with spec v1.10; the human accepts it with ADR-012)" and will read that way after acceptance. The acceptance needs a `docs/decisions.md` row, as the 2026-10-09 rows for ADR-010 and ADR-011 did.
- Strongest alternative: have `apply_spec.sh` refuse while any ADR is proposed. It is workflow tuning and not needed for this version.
- Conflicts: ADR-007 (Decision, fourth bullet) and ADR-011 (Decision, fifth bullet), as quoted, until the amendment and ADR-012 are accepted.
- Recommendation: the proposed fix, plus one sentence on SC-40 in the ADR-007 amendment and an acceptance row in `docs/decisions.md` — it keeps the spec free of ADR ids and leaves acceptance with the human (priority 3).
- Class: drift is acceptable; it is a precondition of applying, not a defect in the proposal's text.
- Verdict: AGREE
