## Findings

### F-1 · gap · a git command that fails during the repair
- **Section:** "Execution" › "`run`" and "Restart"
- **Evidence:** "It refuses with one line on standard error and exits 1, before any event", with `git failed: <error>` "when a git command fails before any task is taken". The repair runs after the refusals and removes a worktree (Restart step 1: "moves to `passed`, and its worktree is removed"), so a git failure there comes after events were recorded. It fits neither that bullet nor "A git command that fails while a task is `running` or `gating`".
- **Proposed fix:** "A git command that fails during the repair ends `run` with `git failed: <error>` on standard error, exit 1; the events already recorded stand."

### F-5 · gap · who creates the directory of a run
- **Section:** "Execution" › "Adapter interface"; "Gates and remediation"; "Domain model and storage" (the M3 paragraph after "Ids")
- **Evidence:** "The adapter writes the runtime's result envelope to `<output_dir>/transcript.json`" and "The file is `.openfactory/runs/<run id>/<gate>.txt`, written through the `RunFiles` port". There are two writers under `.openfactory/runs/<run id>/`, and `RunFiles` only "writes a file of a run". Nothing says who creates the directory or where the use case gets `output_dir`.
- **Proposed fix:** "`RunFiles` gives the directory of a run, creating it; the use case passes it to the executor as `output_dir`."

### F-7 · gap · (advisor) where the use case gets the worktree's path
- **Section:** "Domain model and storage" (the M3 paragraph after "Ids")
- **Evidence:** "`WorkspaceManager` ... creates and removes a task's worktree and branch", and the `GitProvider` operations "take the worktree's path". Nothing says where the use case gets the `workdir` it passes to `AgentExecutor.run` and to those operations. It is the same hole as F-5.
- **Proposed fix:** add "creating it returns the worktree's path".

### F-4 · drift · "before their results merge"
- **Section:** "Spec diff and impact analysis" › "Mid-execution change"
- **Evidence:** "any that fall in the impacted set are invalidated before their results merge" against "Execution": "The orchestrator never merges". The sentence is M6 text, unchanged from v1.11.
- **Proposed fix:** no change in v1.12; add it to the "before M6 is planned" line under "Later" in `docs/progress.md` (replan mechanics).

### F-6 · drift · the planner prompt does not state the path pattern syntax
- **Section:** "Task contract" › "Planning"
- **Evidence:** "The prompt states the path pattern syntax." `src/openfactory/app/planner_prompt.py:31-32` says only "the path patterns the task may change".
- **Proposed fix:** change the code, in an M3 task. The prompt text changes, and with it the `context_hash` of new planner runs.

### F-8 · drift · (advisor) "branching from the last commit of the untouched work"
- **Section:** "Spec diff and impact analysis" › step 4
- **Evidence:** "After approval, only the new tasks run, branching from the last commit of the untouched work" against "Base and branches": `<base>` is taken "among the tasks of the plan", so a replanned plan with no commit starts from `HEAD`. M6, not M3.
- **Proposed fix:** no change in v1.12; add it to the same "before M6 is planned" line as F-4.

### F-2 · wording · order of the two events for an interrupted task
- **Section:** "Execution" › "Restart"
- **Evidence:** step 2 moves the task to `failed` and gives its unfinished run an `AgentRunFinished`, without the order of the two events; "The events of the repair have no `causation_id`", so nothing else orders them.
- **Proposed fix:** "`AgentRunFinished` is recorded first, then the `TaskStateChanged`."

### F-3 · wording · two descriptions that "Execution" has overtaken
- **Section:** "CLI commands" (table); "Task state machine"
- **Evidence:** the table row "`openfactory run [--task ID]` | Executes ready tasks in dependency order" against "It then repeatedly takes the `ready` task with the lowest task id". The two are equivalent, since a ready task's dependencies have passed. The state list says "`failed`: the run errored, timed out, or a gate failed; output is saved", which does not cover the reasons `no changes`, `git: ...` or `interrupted`.
- **Proposed fix:** table row "Executes the ready tasks of the approved plan, lowest task id first"; state line "`failed`: the attempt did not pass; `reason` says why".

## Advisor

### Q1: DISAGREE
Real: the only git command in the repair is the worktree removal of Restart step 1, and it runs after `gating` to `passed` is recorded. The same hole is in "Per-task sequence" step 6, where the worktree is also removed after `passed`, and `TRANSITIONS` has no `passed` to `failed`. The fix covers the repair only, and extending its end-the-run rule to step 6 would stop the loop over a leftover directory.
Instead: one sentence for both places: "A worktree removal that fails after its task has passed (step 6 or the repair) changes no state: `run` writes a warning log line and goes on." This adds no new exit path and the leftover worktree is never touched again.

### Q2: AGREE
Real: the M3 close test asserts event order, and repair events have no `causation_id` to order them. Run finish first matches the normal sequence (`AgentRunFinished` before `running` to `failed`).

### Q3: AGREE
Both are two wordings of a rule "Execution" now fixes. The proposed lines change no behaviour and match the reasons of SC-60.

### Q4: AGREE
It is M6 text that M3 neither builds nor tests. `docs/progress.md` line 90 ("before M6 is planned", F-6 replan mechanics) is the right place, as SC-81 did for the other deferred gaps.

### Q5: AGREE
Real: the use case must hand `output_dir` to `AgentExecutor.run`, `app` may not touch the filesystem (ADR-006), and `RunFiles` as worded only "writes a file". If adopted, the same sentence is needed in the M3 paragraph after "Ids" (proposal line 436) and in the `RunFiles` bullet of ADR-014 (proposed).
