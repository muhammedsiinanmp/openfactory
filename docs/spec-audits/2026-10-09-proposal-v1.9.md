### Q1: F-1 — when the recorder's catch-up fails, does the command print a one-line message or let the exception propagate, and must v1.9 say which?
- Proposed: a real but non-blocking gap; no fix in M1; leave it under Later.
- Challenge:
  - The gap is real but narrow. Letting the exception propagate already meets all three sentences: the message names the seq (`/Users/apple/Projects/openfactory/src/openfactory/adapters/sqlite_recorder.py:99-108`), Python exits 1, and the traceback goes to standard error.
  - No M1 command can produce the state. After SC-12 no valid M1 payload makes the projector fail, so only a hand-edited log reaches it.
  - "Leave it under Later" assumes a line exists. It does not: `/Users/apple/Projects/openfactory/docs/progress.md:45` covers the missing repair path, not the message form.
  - One risk for task 2: the sentence is new in v1.9, so a test-writer may treat it as an acceptance criterion of the `validate` command. Under Typer's `CliRunner` an uncaught exception gives exit code 1 and `result.exception`, with nothing on standard error (from memory, not run here), which would push the implementer to add a handler.
- Strongest alternative: add one sentence to Output now ("prints `stored event seq N cannot be applied` to standard error"). It needs a try/except and a test in task 2 for a state only a hand-edited log reaches.
- Conflicts: none. ADR-010 (accepted) fixes the exception and its text, not what the CLI prints.
- Recommendation: the proposed answer — it is hardening against an input no M1 command produces (priorities 4), and the spec as written is satisfied either way. Two conditions: write the Later line, and have task 2's record put the catch-up failure out of scope.
- Verdict: AGREE

- Conflicts: none. It supersedes the TASK-014 row (2026-10-09) "Whether `init` or the `validate` command repairs such a file is decided in the `validate` task"; SC-20 is the newer row and settles it.
