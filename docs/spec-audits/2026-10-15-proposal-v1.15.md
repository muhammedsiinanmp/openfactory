## Findings

### F-1 · gap · the read behind Restart step 2's exception
- **Section:** "Execution" › "Restart" step 2
- **Evidence:** step 2 now fails a `gating` task with reason `path_check` or `secret found` when "its latest implementer run has a failed `path_check` `GateEvaluated`" (or `gitleaks`). Step 3 names its read ("The reason is read from the task's stream through the `EventStore` port"); step 2 names none. The `Plans` read added in v1.14 gives only "the last gate result of a task", which is not enough to see a failed `path_check` behind a later gate.
- **Proposed fix:** "The gate results are read from the task's stream through the `EventStore` port, as in step 3."

### F-2 · wording · line 70 names only the failed reviewer process
- **Section:** "Tech stack and repo layout" (line 70)
- **Evidence:** "A failed reviewer process is the exception: it fails the `review` gate and `run` goes on", against "The review gate": "A failed reviewer process, or a second rejected reply, fails the gate". Line 70's "If a reply fails Pydantic validation or has no structured result, the call is retried once with the validation error in the prompt, then fails" does not say what "fails" means for the reviewer.
- **Proposed fix:** "A failed reviewer process, or a reviewer reply rejected twice, is the exception: it fails the `review` gate and `run` goes on."

### F-3 · gap · (advisor) "latest implementer run" in Restart step 2 cannot be found on the task stream
- **Section:** "Execution" › "Restart" step 2
- **Evidence:** runs are on `run:<id>` streams; the only implementer run id on the task stream is `GateEvaluated.run_id`, so for a `gating` task killed before its current run recorded any gate, "latest implementer run" picks an earlier attempt's results. Attempt 1 fails `ruff` with a gitleaks error (reason `ruff`, retried); attempt 2 is killed after `running` to `gating`; a naive read finds attempt 1's failed `gitleaks` and escalates as `secret found`. The same after a `resolve --retry` that followed a path violation.
- **Proposed fix:** replace "latest implementer run" with "whose `GateEvaluated` events recorded after its last `running` to `gating` include a failed `path_check`" (the same for `gitleaks`).

### F-4 · gap · (advisor) `GateOutput` cannot carry a gitleaks finding
- **Section:** "Gates and remediation" › "Running a gate that starts a process"; ADR-015 "Ports and adapters"; ADR-016
- **Evidence:** `GateOutput` holds `passed`, `text` and the pytest marker lines, with no exit status or finding flag; "Events of one task" needs the use case to choose `secret found` over the reason `gitleaks`, and `app` cannot read an exit status. SC-115 and ADR-016 define the rule and leave the port unable to carry it.
- **Proposed fix:** add `finding: bool` to `GateOutput`, true only when `gitleaks` exits 3; state it in the spec and in ADR-016's Decision (accepted ADR-015 fixes the `GateOutput` fields).

### F-5 · drift · (advisor) the tag-rule lines when `pytest tests/` itself failed
- **Section:** "Gates and remediation" › "The pytest gate and `req` markers", against SC-109
- **Evidence:** the SC-109 row says the lines are added "also when `pytest tests/` itself failed"; the text says only "When the tag rule fails", and "fails when ... or when ..." can be read as not checking the tag rule once pytest failed.
- **Proposed fix:** add ", also when `pytest tests/` itself failed".

### F-6 · drift · (advisor) no `review` `GateEvaluated` after a cost-limit failure
- **Section:** "Metrics"; "Execution" › "Events of one task", against SC-107
- **Evidence:** the SC-107 row says "A cost-limit failure after the reviewer's run has no `review` `GateEvaluated`"; "Metrics" says only "no further gate runs", which does not clearly rule it out once the review gate has started.
- **Proposed fix:** add to "Metrics": "after a reviewer run, no `review` `GateEvaluated` is recorded".

### F-7 · wording · (advisor) the gitleaks row's "Blocks on"
- **Section:** "Gates and remediation", gate table
- **Evidence:** "any finding" against "Running a gate that starts a process", where any other non-zero exit also fails the gate.
- **Proposed fix:** "a finding (exit 3), or any other failure of the scan".

## Advisor

## Second pass: audit of proposal v1.15

Both findings in the draft are real, and I agree with both. I found 5 more in the changed sections that the draft does not have. Line numbers refer to `docs/spec-proposals/phase1-spec-v1.15.md`.

### F-1: real problem, proposed fix right — AGREE (with one addition)
Step 2 (line 646) does not say where it reads its gate results from. The `Plans` read (line 443) gives only "the last gate result of a task (for `status`)". That cannot show a failed `path_check` or `gitleaks` result sitting behind a later gate. `GateEvaluated` events are on the `task:<id>` stream (line 356), so "through the `EventStore` port, as in step 3" is the right fix. It is not enough on its own, though. See M-1 for the scope the read also needs.

### F-2: real problem (minor), proposed fix right — AGREE
Line 70 lists only the failed reviewer process as the exception. It leaves "then fails" undefined for a reviewer reply that is rejected twice. Line 703 and SC-105 make that case fail the gate too. The fix brings line 70 in line with line 703 and SC-105. Classing it as wording is correct.

### What the draft missed

**M-1 · gap · "Restart" step 2 (line 646)**
- **Evidence:** the task stream has no `AgentRunStarted`, because runs are on `run:<id>` (line 355). The only implementer run id in the task stream is `GateEvaluated.run_id`. That leaves "latest implementer run" ambiguous whenever a `gating` task was killed before its current run recorded any gate.
- **How it goes wrong:**
  - Attempt 1 fails `ruff` with `gitleaks` exiting with a non-3 error. The reason is `ruff` and the task retries.
  - Attempt 2 is killed after `running` to `gating`, before any `GateEvaluated`.
  - A naive read takes the last `gitleaks` result in the stream, which is attempt 1's failure. The task then escalates as `secret found`, which is wrong.
  - The same happens with a `path_check` failure from before a `resolve --retry`.
- **Fix:** "...whose `GateEvaluated` events recorded after its last `running` to `gating` include a failed `path_check`..." Use the same scope for `gitleaks`. This replaces "latest implementer run".

**M-2 · gap · "Running a gate that starts a process" (line 687); ADR-015 "Ports and adapters"; ADR-016**
- **Evidence:** `GateOutput` holds `passed`, `text` and, for `pytest`, the marker lines. It has no exit status and no finding flag. Yet line 635 needs the use case to choose between `secret found` and the reason `gitleaks`. `app` has no I/O, so it cannot tell exit 3 from any other failure. SC-115 and ADR-016 define the rule and leave the port unable to carry it.
- **Fix:** add a field to `GateOutput`, for example `finding: bool`, true only when `gitleaks` exits 3. State it at line 687 and in ADR-016's Decision, since accepted ADR-015 fixes the `GateOutput` fields.

**M-3 · drift · "The pytest gate and `req` markers" (line 691), against SC-109**
- **Evidence:** SC-109 says the tag-rule lines are added "also when `pytest tests/` itself failed". The text says only "When the tag rule fails". The gate's "fails when ... or when ..." can be read as stopping early, so that the tag rule is not checked once `pytest tests/` has failed.
- **Fix:** add ", also when `pytest tests/` itself failed".

**M-4 · drift · "Metrics" (line 794) / "Events of one task" (line 636), against SC-107 (second sentence)**
- **Evidence:** SC-107 says "A cost-limit failure after the reviewer's run has no `review` `GateEvaluated`". Line 794's "no further gate runs" is unchanged from v1.14. The review gate has already started at that point, so the phrase does not clearly rule out its `GateEvaluated`. The v1.14 advisor raised this exact case.
- **Fix:** add to line 794: "after a reviewer run, no `review` `GateEvaluated` is recorded."

**M-5 · wording · gate table, `gitleaks` row (line 682)**
- **Evidence:** "Blocks on: any finding" disagrees with line 687, where any other non-zero exit also fails the gate. The row was edited in this version.
- **Fix:** "a finding (exit 3), or any other failure of the scan".

**Not counted (a precondition, not text):** v1.15 contradicts accepted ADR-015 ("A gitleaks finding (exit 1)"; "only exit status 1 of gitleaks is a finding") until ADR-016 is accepted. ADR-016's Consequences already say it must be accepted before the apply. If M-2 is taken, ADR-016 has to be amended before that acceptance.

**Code drift:** none beyond pending M4 work. `src/openfactory/app/context_pack.py` (line 28) and `src/openfactory/app/planner_prompt.py` do not yet say tests go under `tests/` (SC-110). The planner prompt does not mention tagged tests at all yet (SC-93). The M4 tasks are expected to build both.

Second pass: F-1 AGREE, F-2 AGREE; missed: 2 gap, 2 drift, 1 wording; total missed 5.
