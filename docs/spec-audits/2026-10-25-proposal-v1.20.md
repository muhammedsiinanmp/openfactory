## Findings

### F-1 · gap · an eval case whose `impact` fails
- **Section:** "Evaluation plan"; "Spec diff and impact analysis" › Classifier checks
- **Evidence:** a second rejected reply or a failed process makes `impact` "record no `ImpactComputed`, and exit 1" (Classifier checks). The eval compares "the case's `ImpactComputed`" with its labels (Procedure) and writes "one row per case and run" (Run), but no rule says how a run scores a case that has no `ImpactComputed`.
- **Proposed fix:** "A case whose `impact` fails counts as a miss in that run: its predicted sets are empty and its kinds wrong." (The advisor points out that empty predicted sets would pass the cosmetic target. It proposes "A case whose `impact` fails makes its run miss every target; its row shows `classifier call failed` in place of its figures.")

### F-2 · gap · ground truth of the new-requirement case (advisor)
- **Section:** "Evaluation plan" › Ground truth, Metrics
- **Evidence:** "Ground truth: the human's list of the tasks, files and tests the change truly affects" (line 944) against "A case with empty ground truth (the cosmetic and new-requirement cases) is left out of the pooled figures" (line 946). With labels independent of the traversal (SC-215), a human may judge that a new requirement affects existing files, while an `added` requirement is never a seed (Step 3).
- **Proposed fix:** "The new-requirement case is labelled with empty tasks, files and tests: an `added` requirement is not a seed, and its work is new work." Or drop the parenthesis.

### F-3 · wording · accuracy over all runs or per run
- **Section:** "Evaluation plan" › Metrics, Run
- **Evidence:** "Accuracy is the share of modified requirements, over all cases and runs, ..." (line 946) against "then, per run, the pooled file and test precision and recall, the accuracy ..." (line 948). The SC-212 and SC-213 rows carry the same clash.
- **Proposed fix:** "over all cases of a run" in Metrics, so accuracy has a minimum and maximum like the other pooled figures; or drop accuracy from the per-run line.

### F-4 · wording · the labelled kind is not a label (advisor)
- **Section:** "Evaluation plan" › Cases, Ground truth
- **Evidence:** accuracy compares with "the labelled kind" (line 946), but a case's labels are "tasks, files and tests" (lines 943-944).
- **Proposed fix:** line 944: "... the tasks, files and tests the change truly affects, and the kind of each modified requirement;".

## Advisor

### Q1: Is N-1 real? "Metrics" defines one classification accuracy over all cases and all three runs, but "Run" puts an accuracy in the results file for each run. Is the proposed fix right?
- Proposed: wording. Change Metrics to "over all cases of a run", or drop "per run" for accuracy in Run.
- Challenge: The finding is real. Line 946 says "Accuracy is the share of modified requirements, over all cases and runs, whose `kind` equals the labelled kind". Line 948 says "then, per run, the pooled file and test precision and recall, the accuracy and whether the cosmetic cases triggered no work". One number cannot be both. The two options are not equal. The classifier is the only part that varies, so three accuracy figures carry the information. "Per run" also fits line 948's "minimum and maximum of each pooled figure over the runs". The proposal leaves one thing open: whether accuracy counts as a "pooled figure" that gets a min and max. The words "over all cases of a run" make it one, which is the reading you would want. The second option throws away the per-run spread for the one figure the eval exists to vary.
- Strongest alternative: Keep "over all cases and runs" and remove accuracy from the per-run line, which matches SC-212 word for word.
- Conflicts: The 2026-10-25 rows SC-212 ("over all cases and runs") and SC-213 ("per run the pooled figures, accuracy and the cosmetic outcome") contradict each other. Each fix departs from one of them. The first option means correcting the wording of SC-212.
- Recommendation: The first option, "over all cases of a run". Accuracy then has a min and max like the other figures, and the change is one phrase.
- Verdict: AGREE

### Q2: Is N-2 real? If a case's `impact` fails with `classifier call failed`, no `ImpactComputed` is recorded, and nothing says how that run is scored. Is the proposed rule right?
- Proposed: gap. The case counts as a miss in that run: its predicted sets are empty and its kinds wrong.
- Challenge: The gap is real and not exotic. Line 833 lets a second rejected reply or a failed process end `impact` with no `ImpactComputed`. The eval runs the real classifier up to 24 times. Line 948 needs a row per case and run, written before the targets are checked. The fix has a flaw, though. "Predicted sets empty" makes a failed cosmetic case pass the cosmetic target, because line 947 defines that target as empty `tasks`, `downstream`, `files` and `tests`. So a failure would be scored as a success. For non-cosmetic cases, empty predictions add nothing to pooled precision, so the miss shows only in recall. The fix also adds scoring machinery for a run that has already failed in practice.
- Strongest alternative: "A case whose `impact` fails makes its run miss every target; its row shows `classifier call failed` in place of its figures." This needs no fake predictions, fits "Each of the three runs must meet the targets" (line 947), and keeps the results file written.
- Conflicts: none with the spec, an accepted ADR or an earlier row. The proposed wording does clash in substance with the cosmetic target on line 947, as described above.
- Recommendation: The alternative. A failed call should fail the run outright rather than be scored, and that also closes the cosmetic loophole.
- Verdict: DISAGREE

### Q3: What did the audit miss in the changed sections and the sections they rely on? Does the proposal agree with SC-203 to SC-225 and ADR-020?
- Proposed: none. There is no proposed answer, so my list below is the only option on the table.
- Challenge: I found two misses.
  - **M-1 · gap · "Evaluation plan" › Ground truth and Metrics.** Evidence: line 944 says "Ground truth: the human's list of the tasks, files and tests the change truly affects". Line 946 says "A case with empty ground truth (the cosmetic and new-requirement cases) is left out of the pooled figures". SC-215 makes the labels independent of the traversal ("so the eval can find a blind spot"). The parenthesis assumes those independent labels are empty for the new-requirement case. But a human can judge that a new requirement truly affects existing files (for example, rate limiting in `login.py`). An `added` requirement is never a seed (line 835), so the case would then count as a certain miss for behaviour the spec intends. The spec does not say which way it goes. Fix: "The new-requirement case is labelled with empty tasks, files and tests: an `added` requirement is not a seed, and its work is new work." Alternatively, drop the parenthesis and let the human decide.
  - **M-2 · wording · "Evaluation plan" › Cases and Ground truth against Metrics.** Evidence: line 946 scores accuracy against "the labelled kind", but lines 943-944 list the labels as "tasks, files and tests" only. Nothing says a case labels the kind of each modified requirement. Fix: in line 944, "...the tasks, files and tests the change truly affects, and the kind of each modified requirement;".
- Agreement with the SC rows and ADR-020: The text agrees with SC-203 to SC-207, SC-209 to SC-219 and SC-222, and the version-history row names them correctly. SC-208, SC-220, SC-221 and SC-223 to SC-225 changed no text, and none was needed. The only clash between rows is SC-212 against SC-213 (Q1). The Metrics bullet on line 878 matches ADR-020's Decision: latest `PlanCreated`, the planner runs found through the `causation_id` chain, and the classifier runs of the latest `ImpactComputed` before a replan's `PlanCreated`. The ports paragraph on line 488 also matches ADR-020. The rule "Latest `ImpactComputed` before" in Metrics and ADR-020 has no version filter, unlike "Approving a replan" (line 867). I checked this: with the current refusals the two always pick the same event, so it is not a finding. ADR-020 is still Status: proposed. The spec text carries its rule, so nothing is inconsistent, but the human should accept or amend it together with v1.20.
- Strongest alternative: Fold M-2 into the M-1 fix as one sentence about labels.
- Conflicts: M-1 rests on the 2026-10-25 row SC-215 ("Labels independent of the traversal"). Otherwise none.
- Recommendation: Add M-1 and M-2. M-1 decides whether the new-requirement case can be scored at all, and M-2 gives the accuracy figure its labels.
- Verdict: DISAGREE
