## Findings

### F-2 · drift · `run_task` lets a failed removal after a pass propagate
- **Section:** "Execution" › "Events of one task"
- **Evidence:** the new bullet: "A worktree removal that fails after its task has moved to `passed` ... changes no state and records no event: `run` writes the warning ...". `src/openfactory/app/run.py:189` calls `workspace.remove_worktree(task.id)` after `gating` to `passed` with no handling, so a `GitError` propagates. Known: `docs/progress.md` "Later", "Until TASK-053 `run_task` lets every `GitError` propagate".
- **Proposed fix:** change the code, in TASK-053; the removal failure is returned as data and `cli.py` writes the line.

### F-6 · gap · (advisor) a git command after the repair while a task is still `ready`
- **Section:** "Execution" › "`run`" and "Events of one task"
- **Evidence:** the refusal now covers "a git command [that] fails before the repair", and the `git:` reason covers "while a task is `running` or `gating`". A git command run after the repair while a task is `ready` is under neither. The candidate is the `HEAD` read for `<base>` "when the task starts"; step 1 records `ready` to `running` first and `run.py` reads the base after it, so in practice the `git:` reason applies, settled only by the order of the steps.
- **Proposed fix:** no spec change; TASK-053's record states that the base is read after `running` is recorded.

### F-3 · drift · (advisor) the TASK-042 "two unfinished runs" line in `docs/progress.md`
- **Section:** "Execution" › "Restart" step 2
- **Evidence:** `docs/progress.md` "Later", the TASK-042 line: two unfinished runs "can arise only if a `run` is interrupted inside the repair, between the two events of 'Restart' step 2 (audit F-2)". With SC-83 (`AgentRunFinished` first) an interrupted repair leaves a `running` task with no unfinished run, so the case no longer arises.
- **Proposed fix:** no spec change; the "Later" line says the case was closed by SC-83 (v1.13).

## Advisor

### Q1: Does "the repair prints nothing but that warning" in "Execution" › "Restart" have an unclear antecedent, since the warning is defined in a different subsection ("Events of one task")? If so, should it name the warning explicitly?
- Proposed: Replace it with "the repair prints nothing but the warning of a worktree removal that fails (see Events of one task)".
- Challenge: The problem is real but small. The new bullet in "Events of one task" names "step 1 of Restart", so a careful reader can link the two. In the other direction, though, "Restart" has no antecedent for "that". "That warning" sits two subsections and about eight paragraphs below the bullet that defines it. A test-writer working from the Restart paragraph alone cannot tell what output is allowed. The fix costs one clause in a proposal that is still being drafted. There is one follow-on: SC-82 (row 2026-10-14, still uncommitted) quotes the old wording "The repair prints nothing but that warning", so the row should be changed in the same edit or the decisions log will drift from the spec.
- Strongest alternative: Leave the text as it is and record the point as non-blocking. This follows the "prefer shipping" memory, but here the edit is cheaper than the record.
- Conflicts: none. The fix restates SC-82 and the 2026-10-14 F-1 row (row 14) without changing their meaning.
- Recommendation: Apply the proposed fix and update the SC-82 row's quoted sentence to match. It makes the Restart paragraph readable and testable on its own at no cost.
- Verdict: AGREE

### Q2: The code doesn't match v1.13 yet. `run_task` in `src/openfactory/app/run.py:189` calls `workspace.remove_worktree(task.id)` after `gating` to `passed` and does not catch `GitError`, so a failed removal propagates. The spec now says it should be a warning. Should this be fixed in the code in TASK-053?
- Proposed: Change the code, in TASK-053.
- Challenge: The drift is real but already known and scheduled. Three records cover it: the 2026-10-14 TASK-052 split row (row 9) gives TASK-053 "a worktree removal that fails after a pass (F-1)"; the 2026-10-14 F-1 row (row 14) asks for this exact `/spec-change` before TASK-053 is planned; and progress.md Later says "Until TASK-053 `run_task` lets every `GitError` propagate". So the finding adds no new problem. What the fix leaves unsaid is how. The `run.py` docstring says "The use case returns data and prints nothing", and SC-82 says "The spec does not name the layer that writes the warning". So TASK-053 has to carry the removal error out as data, for example as a field on the frozen `TaskRunResult`, which currently has `extra="forbid"`. `cli.py` then writes the line. Outline item 2 needs the same arrangement for the repair's step 1 removal.
- Strongest alternative: Write the warning inside `run_task` through a logger. That conflicts with the module's prints-nothing rule, and the "structlog warning line" option was rejected in SC-82, so it is weaker.
- Conflicts: none. The code drift is expected under the 2026-10-14 TASK-052 split row.
- Recommendation: Fix it in TASK-053, with the removal failure returned as data and the warning line written by `cli.py`. This is already the planned route and keeps the app layer free of printing.
- Verdict: AGREE

### What the audit missed (changed sections and the sections they rely on)

1. **Stale progress.md Later line (decision drift, non-blocking).** `docs/progress.md` line 118 still says two unfinished runs "can arise only if a `run` is interrupted inside the repair, between the two events of 'Restart' step 2 (audit F-2)". With SC-83's order (`AgentRunFinished` first), that case can no longer happen. An interrupted repair leaves a `running` task with no unfinished run, and the next repair records only the `TaskStateChanged`. The line should say the case was closed by SC-83 / v1.13. The TASK-042 "highest run number" answer is then moot, though harmless.

2. **`--task ID` refusal with a warning before it (consistency and testability, non-blocking; affects outline items 2 and 3).** The `--task` refusals (`unknown task <ID>`, `<ID> is <state>, not ready`) come "After the repair". The repair can now write `worktree of <id> not removed: ...` first, so standard error holds two lines. The first refusal bullet says "refuses with one line on standard error … before any event", which covers only the pre-repair refusals, but a reader may carry "one line" over. The documents don't say whether the `--task` refusal is "one line" when a warning comes before it. A test asserting standard error equals exactly one line would break. A one-line note in item 2's task record is enough; this does not need a spec change.

3. **Where the warning comes from (ambiguity, non-blocking; affects TASK-053 and item 2).** The spec says "`run` writes" the warning, but the use cases print nothing. Both `run_task` (step 6) and the repair (item 2) must return removal failures as data, and `cli.py` must write them in the order they happened. Neither the spec nor SC-82 fixes the order of the warning against the `task_id  passed` line. That matters only within standard error, because the task line goes to standard output. TASK-053 should state its choice in a decisions row.

4. **Narrowing the `git failed` refusal to "before the repair" leaves one theoretical gap (non-blocking).** A git command that runs after the repair while a task is still `ready` is now covered by no rule: not the refusal, and not "while a task is `running` or `gating`". The candidate is the `HEAD` read for `<base>` "when the task starts". "Per-task sequence" step 1 records `ready` to `running` first, and `run.py` reads the base after that event, so in practice the failure falls under the `git:` reason. The documents settle this only through the order of the steps. TASK-053's record should say the base is read after `running` is recorded.

5. **Repair step 1 removal and the `passed`-but-interrupted case (completeness, non-blocking).** A run killed after `gating` to `passed` but before the removal leaves a worktree that no repair removes (step 1 covers only `gating`). The same happens after a failed removal, which now only warns. The F-1 row (row 14) already accepts a leftover worktree as harmless. Nothing to do; noted only so it is not re-raised.

None of the findings above blocks TASK-053 or M3 outline item 2. Items 2 and 3 should go into the task records of TASK-053 and item 2. Item 1 is a one-line progress.md edit.
