## Findings

### F-1 · blocker · `trace_links` has no DDL, kinds, direction or event mapping
- **Section:** "Domain model and storage" › Projections, Projection rules; "Traceability"
- **Evidence:** the only definition is the row at line 236, "`trace_links` | from_kind, from_id, to_kind, to_id, source (spec, trailer, contract, diff, test_tag)", and line 334, "`trace_links` is built in M5". "The tables built in M1 to M4" (line 240) has no DDL for it, so it has no primary key, yet a rebuild is identical when the rows "read in primary-key order are equal" (line 333). There is no closed list of kinds and no stored direction per link: the table at lines 715-723 writes "test → requirement", while the traversal at line 770 walks requirement → tests. No rule says which event writes which edge.
- **Proposed fix:** add the DDL `trace_links(from_kind, from_id, to_kind, to_id, source, PRIMARY KEY (from_kind, from_id, to_kind, to_id, source))`; the kinds `requirement, adr, task, run, commit, file, test`; one stored direction per link, as in the Traceability table; and a mapping: `SpecApproved` → requirement→adr (`spec`); `PlanApproved` → requirement→task and task→task (`contract`); `AgentRunStarted` with a task → task→run; `CommitRecorded` → run→commit and commit→file (`diff`); the test tags → test→requirement (`test_tag`), per F-3. (The advisor disagrees: write task→run and run→commit at `CommitRecorded`, fix the task→task direction, and add test→file; see Q1.)

### F-2 · blocker · requirement versions and the life of an edge
- **Section:** "Domain model and storage" › Projection rules; "Traceability"
- **Evidence:** ADR-003 (accepted), Consequences: "Requirement ids repeat across spec versions while `from_id` and `to_id` have no version. Gap G14 lists this as a question that needs an answer by M5." The spec does not answer it. A draft's `SpecImported` content is replaced under the same id (line 171), a draft plan is superseded and its tasks removed (line 532), and `constrained_by` can change between approved versions. Nothing says whether the edges of a replaced draft, a superseded plan or an older approved version stay.
- **Proposed fix:** node ids carry no version. `spec` edges hold the latest approved version only: each `SpecApproved` replaces every `spec` row with those of that version's requirements. `contract` edges are written at `PlanApproved`, so drafts never produce edges. Edges of invalidated or abandoned tasks stay, as history. The alternative is a `spec_version` column on `trace_links`.

### F-3 · blocker · test → requirement edges have no event source
- **Section:** "Traceability"; "Gates and remediation" › "The pytest gate and `req` markers"; "Domain model and storage" › Event payloads
- **Evidence:** the marker lines exist only in `GateOutput` (line 687); they are used for the tag rule and then dropped (`src/openfactory/app/run.py:595`). `GateEvaluated` (lines 417-422) holds no tests. The projector uses "no file reads" (line 333), and a payload "carries everything its projections hold" (line 365). The plugin writes `{file, req}` per test (line 691), with no test name, while the impact sample counts "tests/auth/test_login.py (4 tests)" (line 779).
- **Proposed fix:** a new event `TestsTagged` (stream `task:<task id>`, actor `orchestrator`), recorded after the `pytest` `GateEvaluated` of a run, with payload `{run_id, task_id, tests: [{node_id, file, req}]}`, sorted. The plugin adds the node id. The `test_tag` edges are the collection of the latest run whose task passed, and replace the earlier `test_tag` rows (the collection is the whole suite). Needs an ADR; a database made before M5 is discarded, as for M4. (The advisor disagrees: record it once every gate has passed, just before `CommitRecorded`, carry untagged tests too, and note that `node_id` amends ADR-015; see Q3.)

### F-4 · blocker · `coverage` has no source for "passing"
- **Section:** "Traceability" › Queries
- **Evidence:** "`openfactory coverage`: requirements with no passing tagged test" (line 749). Only `gate_results.passed` per gate is stored; no per-test result is recorded. Which requirements count (the latest approved version only? deprecated ones?) is not stated.
- **Proposed fix:** a tagged test passes when it is in the collection of a run whose task passed (its `pytest` gate passed, so the whole suite passed at that commit). The requirements are the ones that are not deprecated in the latest approved spec version. The output is one line per requirement id, ascending as strings, and the command exits 0.

### F-6 · blocker · "rebuild links from git trailers alone" (2026-10-09 F-35)
- **Section:** "Traceability"; "Milestones and definition of done"; "Domain model and storage" › Projection rules
- **Evidence:** M5 "rebuild links from git trailers alone" (line 863); line 741, "Trailers make the graph rebuildable from git history alone, even if the SQLite file is lost". The trailers carry `Task`, `Requirements`, `Acceptance-Criteria`, `Agent-Run` and `Spec-Version` (lines 732-736), but not `depends_on`, `constrained_by` or test tags, so they cannot rebuild "the graph". The spec does not say where rebuilt links go, and writing them to `trace_links` would break "Projection tables are never written in any other way" (line 324) and ADR-002. It does not say which commits are read (every `openfactory/*` branch, or the branch that passed last, which holds the chain), or through which port.
- **Proposed fix:** a function, not a command. It reads the commits that have a `Task` trailer and are reachable from `openfactory/*` branches. It returns the edges task→requirement, task→run, run→commit and commit→file, with the files taken from the commit's diff against its parent. M5 is met when that set equals the matching rows of `trace_links`; the function never writes the table. Reword line 741 to name those links.

## Advisor

### Q1: Is F-1 real? `trace_links` has no DDL, no closed set of node kinds, no storage direction and no rule saying which event writes which edge. Is the proposed DDL, kinds and event mapping right?
- Proposed: add DDL with a 5-column PK, kinds `requirement, adr, task, run, commit, file, test`, one direction per link, and an event mapping (SpecApproved, PlanApproved, AgentRunStarted, CommitRecorded, test tags).
- Challenge: The problem is real and the quotes are right (236, 238, 240, 333, 334, 715-723, 770). The fix has three slips:
  - It drops the `test → file` link. The spec lists it ("test → file | the test file path", line 723) and so does ADR-003. Step 3 needs it to find "tests ... touching those files" (line 770).
  - It leaves `task → run` open ("contract? or trailer, see F-7") and writes it at `AgentRunStarted`. That event also starts failed attempts and reviewer runs. The trailers name only the committed implementer run (`Agent-Run`, line 739), so the F-6 equality check would fail unless the rows were filtered.
  - "One direction as in the Traceability table" does not fix `task → task`. The table says "contract `depends_on`" without saying which end is `from`. Step 3 walks to "downstream dependent tasks", so the stored direction matters.

  On direction, the earlier advisor already noted the table names links, not storage direction; a recursive CTE can walk either way. The real need is one fixed convention.
- Strongest alternative: The same DDL and kinds, with these changes:
  - `CommitRecorded` writes `task → run` and `run → commit` (its payload has `task_id`, `run_id` and `sha`), so that set equals what the trailers give.
  - `task → task` is stored as `from` = the task, `to` = its `depends_on`, the same as `task_deps`.
  - Add `test → file`, written with the test edges of F-3.
- Conflicts: none with the spec. It is a storage schema, so CLAUDE.md requires an ADR, and it answers ADR-003's open G14 question.
- Recommendation: The alternative above. It closes the fix's open fork and makes the rows match the trailers exactly.
- Verdict: DISAGREE

### Q2: Is F-2 real? Requirement ids repeat across spec versions, but edges carry no version, and the spec does not say which edges survive a draft being replaced, a draft plan being superseded, or a later approved version. Is "no version in node ids; `spec` edges for the latest approved version only; `contract` edges at PlanApproved; old edges stay as history" right?
- Proposed: Node ids carry no version. SpecApproved replaces all `spec` rows. `contract` edges are written at PlanApproved, so drafts never produce edges. Edges of invalidated or abandoned tasks stay.
- Challenge: The ADR-003 quote ("Gap G14 ... needs an answer by M5") and lines 171 and 532 are right. The proposal assumes M6 never needs historical `constrained_by` edges. Step 3 starts only from changed requirements (line 770), and ADR contradiction detection is deferred (line 43), so that holds. One side effect: `why` on a file built under sv_01 shows the ADRs of the latest version. That is acceptable, but the spec should say so.
- Strongest alternative: Add a `spec_version` column to `trace_links`. It keeps full history but puts a version filter on every query. Priority 6 argues against it.
- Conflicts: none. It answers ADR-003's open question; the answer belongs in the M5 ADR.
- Recommendation: The proposed answer. It is the smallest design that answers G14, and nothing in M5 or M6 needs versioned edges.
- Verdict: AGREE

### Q3: Is F-3 real? `test → requirement` edges have no event source: marker lines exist only in `GateOutput` and are dropped after the tag rule. Is a new `TestsTagged` event, recorded after the pytest `GateEvaluated`, with node ids added by the plugin, the right fix?
- Proposed: Record `TestsTagged {run_id, task_id, tests: [{node_id, file, req}]}` after the pytest `GateEvaluated`. The edges come from the latest run whose task passed and replace the earlier ones. Needs an ADR. A pre-M5 database is discarded.
- Challenge: The evidence checks out (687, 417-422, 333, 365, 691, 779, `run.py:595`). The design has three problems:
  - Recording after every pytest `GateEvaluated` means the projector cannot know yet whether the task will pass. "The latest run whose task passed" would need a staging table or a look-back at a later `CommitRecorded`. Simpler: record `TestsTagged` only once every gate has passed, just before `CommitRecorded`, so a crash between them leaves no orphan. Restart step 1 keys on `CommitRecorded`. This also changes "Events of one task" (line 630), the event list (line 336) and the Streams table.
  - Adding `node_id` changes the plugin line `{"file", "req"}`, which accepted ADR-015 fixes. `MarkerLine` is `extra="forbid"`, so the model has to change too.
  - The payload should carry untagged tests as well (`req: []`). That gives them `test → file` edges, and line 770's "tests ... touching those files" needs those.

  A new event type does not invalidate stored events, so a discard is not needed for that reason. It is needed for the reason in Q14 miss 2.
- Strongest alternative: The same event, recorded once per passing attempt just before `CommitRecorded`. Its collection replaces all `test_tag` rows, including the `test → file` edges.
- Conflicts: ADR-015 (accepted), Decision: the plugin writes `{"file", "req"}` per collected test. The human must amend it before the plugin adds `node_id`. Spec line 691 changes too.
- Recommendation: The alternative. The projector applies one event without look-ahead, and the restart behaviour stays simple.
- Verdict: DISAGREE
