## Findings

### F-1 · gap · the other figures of a run with a failed case
- **Section:** "Evaluation plan" › Targets, Run
- **Evidence:** SC-226: a case whose `impact` fails "makes its run miss every target; its row shows `classifier call failed` in place of its kinds and figures". Run still asks "per run, the pooled file and test precision and recall, the accuracy and whether the cosmetic cases triggered no work" and "the minimum and maximum of each pooled figure over the runs", and the file is written before the targets are checked. Nothing says what those figures are for a run with a failed case.
- **Proposed fix:** append to the SC-226 sentence: "; that run's pooled figures and accuracy are computed over its other cases."

### F-2 · wording · min and max of the accuracy
- **Section:** "Evaluation plan" › Run, Metrics
- **Evidence:** SC-228 makes accuracy per run ("over all cases of a run") and its row says "the results give its minimum and maximum", but Run gives "the minimum and maximum of each pooled figure over the runs", and Metrics calls only recall and precision "pooled".
- **Proposed fix:** "then the minimum and maximum of each pooled figure and of the accuracy over the runs."

### F-3 · wording · what a "part" of the `report` text is (advisor)
- **Section:** "CLI commands" › Output, `report` bullet
- **Evidence:** "Parts are separated by one blank line" (SC-231) does not say what a part is. `_report_lines` (src/openfactory/cli.py:525-548) puts a blank line after the title, after the plan line, after `## Requirements`, between each `###` heading and its fence, after each closing fence, and after `## Cost`; none inside a fence or between table rows. Read with "a heading … and a fenced block" as one part, there is no blank line between a heading and its fence.
- **Proposed fix:** "The title, the plan line, each heading, each fenced block and the table are separated by one blank line."

### F-4 · wording · the `total` row sums unrounded figures (advisor)
- **Section:** "CLI commands" › Output, `report` bullet
- **Evidence:** "a row `total` with an empty `Kind` cell and the sums of the rows above, in the same format" can be read as the sum of the printed, rounded cells; `app/report.py:108` sums the unrounded figures and rounds once, so `Cost USD` can differ by 0.0001.
- **Proposed fix:** "the sums of the plans' figures" in place of "the sums of the rows above".

## Advisor

### Q1: When one case's `impact` fails, SC-226 already fails that run on every target. But Run still asks, for that run, for pooled precision and recall, accuracy, and a min and max over the runs, and nothing defines those figures when a case has no `ImpactComputed`. Is that a real gap, and is "computed over its other cases" the right fix?
- Proposed: append "; that run's pooled figures and accuracy are computed over its other cases." to the SC-226 sentence.
- Challenge: The gap is real. The results file is written before the targets are checked (line 948), so the per-run line and the min/max must have values even for a run that failed. The fix assumes it is fine for a failed run's figures, worked out over 7 cases, to feed the min/max next to runs worked out over 8. That can make the max look better than any complete run, although the run is already marked as failed, so nobody is misled about pass or fail. The fix also says nothing about the per-run "whether the cosmetic cases triggered no work" when the failed case is cosmetic. SC-226 ("miss every target") already settles that: it is a miss. So no extra text is needed, but the human should know that is how it reads.
- Strongest alternative: show `classifier call failed` on that run's per-run line too, and leave the run out of the min and max. This keeps the spread to complete runs only, but needs special cases in two places.
- Conflicts: none. It agrees with the 2026-10-25 row SC-226, and with SC-213 ("per run the pooled figures, accuracy and the cosmetic outcome; then min and max over the runs").
- Recommendation: the proposed fix. It is the smallest rule that gives every reported figure a value: just skip the failed case (priorities 6). The run's failure is already recorded by SC-226.
- Verdict: AGREE

### Q2: SC-228 makes accuracy a per-run figure that gets a min and max. The Run text only gives a min and max for "each pooled figure", and Metrics calls only precision and recall "pooled". Should Run name accuracy explicitly?
- Proposed: "then the minimum and maximum of each pooled figure and of the accuracy over the runs."
- Challenge: The problem is real. Metrics (line 946) says "Recall and precision are pooled"; accuracy is defined separately, "over all cases of a run". So on a strict reading accuracy gets no min/max, while SC-228 says "the results give its minimum and maximum". The fix assumes nobody wants accuracy to be called "pooled" itself. Calling it that would blur the separate rule that empty-truth cases are left out of the pooled figures, and accuracy counts the cosmetic cases.
- Strongest alternative: in Metrics, call accuracy a pooled figure ("accuracy is pooled over all cases of a run"). This keeps Run unchanged, but mixes it up with the exclusion of empty-truth cases.
- Conflicts: none. The proposed text puts into the spec what the 2026-10-25 row SC-228 already decided ("the results give its minimum and maximum").
- Recommendation: the proposed fix. It is one phrase, and it matches SC-228 without changing what "pooled" means.
- Verdict: AGREE

### Q3: What did the audit miss in the changed sections (the Evaluation plan, the `report` bullet, the version-history row) and in the sections they rely on? This includes checking the `report` bullet against `_report_lines` and the new text against SC-203..SC-233 and ADR-020.
- Proposed: no proposed answer was given, so the list below is the only option on the table.
- Challenge: I found three misses.
  - **M-1 · wording · "Version history".** The table is newest-first: the v1.20 spec has `| 1.20 |` on line 978 above `| 1.19 |` on line 979. The proposal puts the new `| 1.21 |` row on line 979, *below* 1.20 and above 1.19. Fix: move the 1.21 row above the 1.20 row.
  - **M-2 · wording · "CLI commands" › Output, `report` (line 933).** "Parts are separated by one blank line" never says what a part is. `_report_lines` (src/openfactory/cli.py:525-548) puts a blank line:
    - between the title and the plan line, and between the plan line and `## Requirements`;
    - between `## Requirements` and the first `###`;
    - between each `### <id>  <title>` heading and its fence;
    - between a closing fence and the next `###` or `## Cost`;
    - between `## Cost` and the table.

    It puts none inside a fence and none between table rows. If "a heading … and a fenced block" is read as one part (the sentence lists them together), there would be no blank line between a `###` heading and its fence, and the code would not match. Fix: "The title, the plan line, each heading, each fenced block and the table are separated by one blank line." This matches the code exactly. The rest of the bullet matches the code: `### <id>  <title>` with two spaces, ` (deprecated)`, `plan <id> · spec <id>` with U+00B7, the header and separator rows, plain fences, the empty block (SC-233), the empty `Kind` cell on `total` (SC-230), and `.4f` cost (SC-232).
  - **M-3 · wording (minor) · same bullet.** "then a row `total` … the sums of the rows above, in the same format" can be read as the sum of the rounded values printed in the rows. The code (src/openfactory/app/report.py:108) sums the unrounded `Figures` and rounds once, so `Cost USD` can differ from the sum of the printed cells by 0.0001. SC-231 aims at byte-for-byte testability, so a one-word fix closes this: "the sums of the plans' figures". Under priorities 4 this is low-stakes, so record it rather than block on it.
  - Agreement checks: the Evaluation plan text agrees with SC-226 to SC-229. SC-212's "over all cases and runs" is now replaced, as SC-228 says. The `report` bullet agrees with SC-205, SC-216 and SC-230 to SC-233. The version row names SC-226 to SC-233 correctly. ADR-020 is now Status: accepted. "the plan's figures as for `stats`" and the Metrics attribution bullet (line 878) follow its Decision, so there is no conflict.
- Strongest alternative: put M-2 and M-3 in progress.md "Later" as non-blocking, since the code already behaves the clearer way, and fix only M-1. This follows the "prefer shipping" preference.
- Conflicts: M-2 and M-3 rest on the 2026-10-25 row SC-231 ("Makes `report` testable byte for byte from the spec"). Otherwise none.
- Recommendation: add M-1 and M-2, and M-3 if the human wants it, since each is a one-line edit. M-1 is a plain ordering error, and M-2 is the only reading gap that breaks SC-231's byte-for-byte goal.
