## Blockers

### F-1 · blocker (M1) · when `validate` records `SpecValidated`
- **Section:** Spec input format › Spec versions
- **Evidence:** the five bullets under "`openfactory validate` loads the files and hashes the spec set" (spec lines 163-167): "If the hash equals the latest approved version's, nothing is imported and the command says so." / "If the hash equals the current draft's, nothing is imported." / "Otherwise it records `SpecImported`." / "It then runs the rules and records `SpecValidated` with the result."
  - Reading A: "It then" follows only the "Otherwise" bullet, so an unchanged draft or an unchanged approved version records nothing.
  - Reading B: "It then" applies to every loadable run, so an unchanged draft gets a new `SpecValidated` each run, and an unchanged approved version gets a `SpecValidated` on the approved version's stream.
  - The exit code and the output for the two "nothing is imported" cases are not stated. The readings differ in the event log, and from M2 in behaviour: the deleted-requirement rule depends on task state, so the same draft can pass one day and fail the next.
  - Also unstated: the files equal the latest approved version while a draft exists (an edit was validated, then reverted). The draft stays with content the files no longer hold.
  - This is item 1 of the M1 outline in `docs/progress.md`, the next task.
- **Proposed fix:** replace the bullets with three explicit cases. (1) Hash equals the latest approved version's: record nothing, print "no changes since sv_NN", exit 0 unless there are policy problems; an existing draft is left as it is and is replaced by the next import. (2) Hash equals the current draft's: record no `SpecImported`, run the rules, record `SpecValidated` on the draft. (3) Otherwise: record `SpecImported`, run the rules, record `SpecValidated`. State that the exit code is 1 when there is any violation or policy problem.

### F-2 · blocker (M2) · `agent_runs` has no DDL
- **Section:** Domain model and storage › "The tables built in M1 and M2"
- **Evidence:** "Each milestone adds the tables for the events it introduces: M1 `spec_versions`, `requirements`, `adrs`; M2 `plans`, `tasks`, `task_deps`, `agent_runs`" (line 295), but the DDL block headed "The tables built in M1 and M2" (lines 238-285) has no `CREATE TABLE agent_runs`. The Projections table gives only column names. Already noted in `docs/progress.md` under Later ("Spec gap (before M2 is planned)"). `tests/unit/test_spec_conformance.py` compares DDL blocks with the projector (decisions row 2026-10-09), so M2 has nothing to compare against.
- **Proposed fix:** add `CREATE TABLE agent_runs` to the block: `id TEXT PRIMARY KEY`, `task_id TEXT` (nullable), `role`, `runtime`, `context_hash`, `started_at` NOT NULL; `model`, `ended_at`, `exit`, `tokens_in`, `tokens_out`, `cost_usd` nullable, since a row exists from `AgentRunStarted` until `AgentRunFinished` fills them.

### F-3 · blocker (M3) · worktree base branch and where task branches end up
- **Section:** Execution › Per-task sequence; Spec input format › Policies
- **Evidence:** "`git worktree add .openfactory/worktrees/AUTH-002 -b openfactory/AUTH-002 <base>`, where `<base>` is the branch holding the task's dependencies" (line 498). Each task has its own branch, so a task with two dependencies has two branches and none holds both; Scope defers "Parallel execution, merge-conflict handling" (line 38). No base is given for a task with no dependencies. No step ever moves a passed task's commit off `openfactory/<task>`, yet "running tasks finish, then any that fall in the impacted set are invalidated before their results merge" (line 610) and replan's "branching from the last commit of the untouched work" (line 608) both assume an integration point. "`protected_branches` lists branches the orchestrator refuses to commit on" (line 191) has no step that could ever commit on a non-task branch, so no test can exercise it.
  - Reading A: a linear chain. Execution is sequential, so each task branches from the tip of the task that passed before it.
  - Reading B: one integration branch that each passed task is fast-forwarded or merged into, and every task branches from it.
- **Proposed fix:** decide between A and B and state it in step 1: the base for a task with no dependencies, the base for a task with several, and what happens to the branch after `passed`. Then say exactly when `protected_branches` is checked (for example, `run` refuses to start when the integration branch is protected), or remove the key.

### F-4 · blocker (M4) · `resolve` has no event, actor or input
- **Section:** Task state machine; Domain model and storage › Streams and actors; CLI commands
- **Evidence:** "`openfactory resolve TASK-ID` | Human action on an escalated task: retry or abandon" (line 636) against "only the orchestrator moves it between them; every transition is a `TaskStateChanged` event" (line 462) and the streams table "`TaskStateChanged` | `task:<task id>` | `orchestrator`" (line 315), against "`human` is used only where a human decision is the event: approvals, and later `resolve`" (line 318). The event type list (line 297) has no resolve event.
  - Reading A: `resolve` records `TaskStateChanged` with actor `human`, contradicting lines 315 and 462.
  - Reading B: a twelfth event type records the decision with actor `human`, and the orchestrator's `TaskStateChanged` points at it through `causation_id`, as `approve plan` does.
  - How the human chooses between retry and abandon is not defined (no flag or argument), nor whether a retry resets the attempt count, without which a retried task escalates again on its first failure.
- **Proposed fix:** reading B: add `TaskResolved` (stream `task:<id>`, actor `human`, payload `task_id`, `decision: retry | abandon`), followed by an orchestrator `TaskStateChanged` with `causation_id`. Define `resolve TASK-ID --retry | --abandon`, the error when the task is not `escalated`, and that a retry allows `max_attempts` more attempts.

### F-5 · blocker (M5) · `trace_links` schema, node kinds and requirement versions
- **Section:** Domain model and storage › Projections; Traceability
- **Evidence:** the only definition is the row "`trace_links` | from_kind, from_id, to_kind, to_id, source (spec, trailer, contract, diff, test_tag)" (line 232). There is no DDL, no list of `kind` values, no edge direction ("test → requirement" at line 550 points the opposite way from the traversal "requirement → ... → tests" at line 594), and no event-to-edge mapping. ADR-003 (accepted), Consequences: "Requirement ids repeat across spec versions while `from_id` and `to_id` have no version. Gap G14 lists this as a question that needs an answer by M5." The spec does not answer it.
  - "Trailers make the graph rebuildable from git history alone, even if the SQLite file is lost" (line 565) and M5's "rebuild links from git trailers alone" (line 676): trailers carry task, requirements, criteria, run and spec version, but not `depends_on` or `constrained_by`. No test can pass "the graph" as written; a test can pass a named subset of links.
  - "`openfactory coverage`: requirements with no passing tagged test" (line 573): no table or event holds per-test results, only `gate_results.passed` per gate.
- **Proposed fix:** add the `trace_links` DDL, the closed list of kinds (`requirement`, `adr`, `task`, `run`, `commit`, `file`, `test`), one direction per link type, which event produces each edge, and whether a requirement node is `REQ-ID` or `(spec_version, REQ-ID)`. Reword line 565 to name the links trailers rebuild (commit → task, requirement, criterion, run, spec version, plus commit → file from git). Define where `coverage` gets "passing".

### F-6 · blocker (M6) · replan mechanics
- **Section:** Spec diff and impact analysis › Step 4; Task contract › Planning, Plan checks
- **Evidence:**
  - "It fails if an approved plan already exists for that spec version; changing an approved plan is `replan`" (line 441). After sv_02 is approved no approved plan exists for sv_02, so `plan` is allowed and would plan the whole spec again beside the sv_01 tasks. Nothing says `plan` or `replan` is the right command at that point.
  - "the planner ... proposes new or revised tasks" (line 608): not stated whether replan records a new `PlanCreated` with a new plan id, what happens to the old plan's status (`superseded` is defined only for a replaced draft, line 447), or which `plan_id` untouched tasks keep. The `PlanCreated` projector rule "marks the earlier draft `superseded` and removes its tasks" covers drafts only.
  - The plan check "a requirement that is not deprecated, or one of its acceptance criteria, appears in no task" (line 456) cannot hold for a replan that emits only new tasks unless untouched tasks count.
  - "A task id is unique among all tasks in the `tasks` projection" (line 446) is not in the plan checks list (lines 449-456), which has only "two tasks share a `task_id`" within one reply.
  - Which event invalidates: `replan` records `TaskStateChanged` to `invalidated` before the planner call, so a rejected replan leaves tasks invalidated with no new plan; not stated whether that is intended.
- **Proposed fix:** add a "Replan" subsection: `plan` fails when any approved plan exists (use `replan`); `replan` requires an approved spec version newer than the current plan's; it records `ImpactComputed`, then the planner runs, then one `PlanCreated` (new plan id, draft) carrying only the new tasks, and the `TaskStateChanged` to `invalidated` events are recorded at `approve plan`, caused by `PlanApproved`, so a rejected replan changes nothing. Coverage is checked over new tasks plus untouched tasks. Add "a `task_id` already in the `tasks` projection" to the plan checks.

## Gaps

### F-7 · gap · "any task not currently running can be invalidated" contradicts `TRANSITIONS`
- **Section:** Task state machine; Spec diff and impact analysis › Mid-execution change
- **Evidence:** "Any task not currently running can be invalidated by a spec change" (line 476) against `"gating": {"passed", "failed"}` and `"abandoned": set()` (lines 483, 488): a `gating` or `abandoned` task is not running and cannot be invalidated. "running tasks finish, then any that fall in the impacted set are invalidated before their results merge" (line 610): nothing merges in Phase 1 (see F-3), and Phase 1 is "sequential", so it is not stated how a spec version is approved while `run` is in progress (a second process) or when `run` notices.
- **Proposed fix:** reword line 476 to "A task in `pending`, `ready`, `failed`, `escalated` or `passed` can be invalidated; a `running` or `gating` task finishes first; `abandoned` and `invalidated` are terminal." Reword line 610 to say invalidation happens at `replan`, never during `run`, and drop "before their results merge".

### F-8 · gap · the path check is described twice and its command cannot see every changed path
- **Section:** Execution › Per-task sequence; Gates and remediation
- **Evidence:** step 4 "the orchestrator runs `git status --porcelain` and checks every changed path against `allowed_paths` and `forbidden_paths`. Any violation fails the run" (line 501), then step 5 "Run the required gates", whose first gate is "path_check | built in: diff paths vs contract" (line 529).
  - Reading A: one check, step 4 is the `path_check` gate, run in state `gating`, recorded by `GateEvaluated`.
  - Reading B: two checks, step 4 fails the run from `running` with no gate result, then the gate repeats it on a diff.
  - `git status --porcelain` omits ignored files and prints an untracked directory as one line (`dir/`). The baseline forbids `.env` (line 188), which target repos normally list in `.gitignore`, so a written `.env` is not a "changed path" for the command as given, and files in a new directory are not listed one by one.
- **Proposed fix:** make step 4 the `path_check` gate (reading A) and give one command that lists every path: `git status --porcelain=v1 -z --untracked-files=all --ignored`, with renames counted on both paths.

### F-9 · gap · glob syntax of `allowed_paths` and `forbidden_paths` is never defined
- **Section:** Task contract; Spec input format › Policies
- **Evidence:** "It uses the same glob syntax as the paths in a task contract" (line 189); the contract section shows `app/auth/**`, `.env`, `.env.*` (lines 388-394) and defines no syntax.
  - Reading A (gitignore style): `.env` matches at any depth, `app/auth/**` matches everything below `app/auth/`.
  - Reading B (anchored at the repo root, `fnmatch` style): `.env` matches only the root file, and `*` may or may not cross `/`.
  - The path check is "the real enforcement" (line 505), so the two readings accept different agent output.
- **Proposed fix:** add to Task contract: patterns are matched against the POSIX path relative to the repo root, anchored at the root; `*` matches within one segment, `**` any number of segments; a pattern with no `/` matches only at the root. Say whether baseline `.env` should then be `**/.env`. A path that matches both lists is forbidden.

### F-10 · gap · `tasks.attempt` and the cost limit have no defined source
- **Section:** Domain model and storage › Projections, Event payloads; Gates and remediation; Metrics
- **Evidence:** `tasks` holds `attempt INTEGER NOT NULL DEFAULT 0` (line 278), and the projector "uses only data in the event" (line 294), but `TaskStateChanged` carries only `task_id`, `from`, `to`, `reason` (lines 350-354). "After `max_attempts` (default 2), it moves to `escalated`" (line 535). "A task's `max_cost_usd` is checked after each run; exceeding it escalates the task" (line 618).
  - Attempt: incremented on each change to `running`, or on each change to `failed`? Both satisfy the text and differ by one while a task runs.
  - Cost, reading A: each run's cost is compared with the limit. Reading B: the sum over the task's runs. Not stated whether the reviewer run counts, or which state the task escalates from (`TRANSITIONS` reaches `escalated` only from `failed`).
- **Proposed fix:** "The projector sets `attempt` to the number of `TaskStateChanged` events to `running` for the task." "`max_cost_usd` is compared with the sum of `cost_usd` over all the task's runs, reviewer runs included; a task over the limit moves `failed` → `escalated` with no retry."

### F-11 · gap · retry and restart: worktree lifecycle and tasks left mid-run
- **Section:** Execution › Per-task sequence; Gates and remediation › Remediation; Milestones › Phase 1 is done when
- **Evidence:** step 1 "`git worktree add .openfactory/worktrees/AUTH-002 -b openfactory/AUTH-002 <base>`" (line 498) fails on a second attempt, because the worktree and branch already exist; "back to `ready` with the gate output attached to its next context pack" (line 535) does not say whether attempt 2 continues in the same worktree with attempt 1's changes or starts clean. "Killing the process mid-run and restarting resumes from the event log without duplicate commits" (line 685): a killed process leaves a task in `running` or `gating` and an `AgentRunStarted` with no `AgentRunFinished`; `TRANSITIONS` allows only `running → gating | failed`, and no rule says what `run` does when it finds such a task, or a commit made just before the kill with no `CommitRecorded`.
- **Proposed fix:** state that a retry reuses the worktree after `git reset --hard` and `git clean -fd` to the base (or keeps the changes; decide). Add a "Restart" rule: on start, `run` moves every `running` or `gating` task to `failed` with reason "interrupted", records `AgentRunFinished` with `exit: error` for an open run, and before committing checks the task branch for a commit whose `Agent-Run` trailer is already there, recording `CommitRecorded` for it without committing again.
