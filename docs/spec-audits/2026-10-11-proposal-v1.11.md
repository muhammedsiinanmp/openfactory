## Gaps

### F-4 · gap · the text behind `<error>` is not defined
- **Section:** CLI commands › Output; Tech stack and repo layout
- **Evidence:** line 695 "`<error>` is the first line of the failure's text; for a planner call that text is `AgentRunFinished.error`." and line 70 "the run is recorded with `exit: error` or `timeout` and `error` set". Nothing says what text a failed process or a timeout puts in `error`, or what the text of a failed `git ls-files` is. A non-zero exit with empty standard error would print `planner call failed: ` with nothing after it.
- **Proposed fix:** none in the spec now. Decision rows in the tasks for outline items 7 (LLM adapter) and 8 (`GitProvider`), each making the text non-empty; item 9 copies the adapter's text unchanged into `AgentRunFinished.error`.

### Q2: Is F-2 real (the `schema` row's "Rejected when" cell covers only a Pydantic rejection, while a missing structured result is also a `schema` rejection), and is the new cell text right?

- Verdict: AGREE

### Q3: Is F-3 real ("A `schema` rejection has the field path in its message" against the message `no structured result`), and is the proposed rewording right?
- Proposed: "A `schema` rejection for a Pydantic error has the field path in its message".
- Challenge: The problem is real. The fix as worded is not right, because it edits only the first half of a two-clause sentence. The result reads "A `schema` rejection for a Pydantic error has the field path in its message, and when there is one the other checks are not run." "One" now points at a rejection for a Pydantic error, so a reply with no structured result no longer clearly stops the other checks. That has a visible effect: `check_plan` on an empty task list returns one `uncovered` line per requirement and criterion, and those lines would land in `AgentRunFinished.error`, the retry prompt and the output of `plan`.
- Strongest alternative: split the sentence: "A `schema` rejection for a Pydantic error has the field path in its message. When there is any `schema` rejection, the other checks are not run."
- Conflicts: none.
- Recommendation: the split form — it fixes the field-path claim without narrowing the skip-the-other-checks rule.
- Verdict: DISAGREE

### Q4: Is F-4 real (no text is defined behind `<error>` for `git ls-files`, or for `AgentRunFinished.error` on a failed process or timeout), and is "no spec change; decision rows in the tasks for items 7 and 8, each making the text non-empty" right?

- Conflicts: none. It is consistent with the SC-50 row and with ADR-005, Consequences ("the envelope's field names are pinned by a captured fixture rather than by the spec").
- Recommendation: the proposed fix, plus a few words on outline items 7, 8 and 9 in `docs/progress.md` so the rows get written — the text depends on what the adapters can capture.
- Verdict: AGREE
