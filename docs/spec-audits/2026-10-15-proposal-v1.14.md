## Findings

### F-1 · gap · a reviewer reply rejected twice
- **Section:** "Gates and remediation" › "The review gate"; "Tech stack and repo layout" (line 70)
- **Evidence:** "a rejected reply is retried once, as for a planner call. A failed reviewer process fails the gate and `run` goes on." For a planner call, a second rejected reply makes `plan` exit 1 with no `PlanCreated` (line 541 of "Plan checks"). For the reviewer nothing says what a second rejected reply does: fail the gate (and retry the task), or end `run`. Line 70 "the call is retried once with the validation error in the prompt, then fails" does not say what "fails" means for a gate.
- **Proposed fix:** "A second rejected reply fails the `review` gate, as a failed process does."

### F-2 · gap · the `review` gate's output file when there is no verdict
- **Section:** "Gates and remediation" › "The review gate"
- **Evidence:** "The gate's output file holds the verdict and the comments." A failed reviewer process, or a reply rejected twice (F-1), has no verdict, yet the gate fails and the failure report reads "the text of its output file".
- **Proposed fix:** "When there is no verdict, the file holds the run's `error` (for a rejected reply, its rejection lines)."

### F-3 · gap · the reviewer's run events in the order of one task's events
- **Section:** "Execution" › "Events of one task"
- **Evidence:** the ordered list "`running` to `gating`, one `GateEvaluated` per gate run, and either `CommitRecorded` then `gating` to `passed`, or `gating` to `failed`" (line 641) has no place for the reviewer's `AgentRunStarted` and `AgentRunFinished` (on `run:<reviewer run id>`), which come between the `gitleaks` `GateEvaluated` and the `review` one, nor for a retried reviewer call (a second pair). The `causation_id` bullet ("the event recorded just before it for the same task") does not say whether the reviewer's run events count as events of the task, as the implementer's do.
- **Proposed fix:** add to the list: "before the `review` `GateEvaluated`, the reviewer's `AgentRunStarted` and `AgentRunFinished` (a second pair when its reply is retried)"; they belong to the task's chain for `causation_id`, like the implementer's.

### F-4 · wording · "It holds no file contents" against the failure report
- **Section:** "Execution" › "The context pack"
- **Evidence:** "It holds no file contents; the agent reads files with its tools." (after the bullet list) against "Remediation": the failure report holds, for each failed gate, "the text of its output file", which the pack includes on a retry. The meaning is clear (no contents of the repo's files), the text is not.
- **Proposed fix:** "It holds no contents of the repo's files; the agent reads them with its tools. A retry's failure report holds the text of the gates' output files."

### F-5 · gap · (advisor) the tag rule's failure is not in the gate's text
- **Section:** "Gates and remediation" › "The pytest gate and `req` markers"; "Remediation"
- **Evidence:** when the tag rule fails, both pytest commands exit 0, so the gate's text ("for each command, its command line, then its standard output, then its standard error") shows a clean run, and the retry's failure report names `pytest` with no hint of the uncovered requirement. ADR-015 has the use case apply the rule, and nothing says it writes the result anywhere.
- **Proposed fix:** "When the tag rule fails, the use case adds one line per uncovered requirement, `no tagged test in a changed file: <REQ id>`, to the gate's text before writing it."

### F-6 · gap · (advisor) tests must live under `tests/`
- **Section:** "Task contract" › "Planning"; "Execution" › "The context pack"; gate table
- **Evidence:** the gate collects only `tests/`; neither the planner prompt sentence ("every task adds tests that carry a `req` marker") nor the implementer's instructions say tests live there. A contract that puts tests next to the code passes the path check and fails the tag rule on every attempt; only the example contract shows `tests/auth/**`.
- **Proposed fix:** add "under `tests/`" to the planner sentence and to the implementer's instructions.

### F-7 · gap · (advisor) where the `<tool> not found` check lives
- **Section:** "Execution" › "`run`" (refusals); "Domain model and storage", the M4 paragraph after "Ids"
- **Evidence:** the refusal is a `PATH` lookup; `app` has no I/O, and the M4 paragraph lists the new operations exactly, with none for it. ADR-015 states the refusal but not where it lives.
- **Proposed fix:** name it, either `GateRunner.missing_tool() -> str | None` or "checked in `cli.py` before the use case runs" (which stretches ADR-011), and record the choice in ADR-015.

### F-8 · gap · (advisor) a run killed between a failed `path_check` or `gitleaks` result and `gating` to `failed`
- **Section:** "Execution" › "Restart" steps 2 and 3
- **Evidence:** a run killed after a failed `path_check` or `gitleaks` `GateEvaluated` but before `gating` to `failed` is failed by step 2 with reason `interrupted`, and step 3 then retries it, against accepted ADR-008 ("A path violation or a gitleaks finding escalates at once, with no retry"). SC-89 closed the window between `failed` and `escalated`; this one is narrower but of the same kind.
- **Proposed fix:** in step 2, a `gating` task whose latest implementer run has a failed `path_check` result fails with reason `path_check`, one with a failed `gitleaks` result with `secret found` (failing safe, since `GateEvaluated` cannot tell a gitleaks error from a finding); or record the window as an accepted limit in `docs/decisions.md`.

### F-9 · gap · (advisor) `causation_id` of the repair's `failed` to `ready`
- **Section:** "Execution" › "Restart" against "Gates and remediation" › "Remediation"
- **Evidence:** "The events of the repair have no `causation_id`" against "Remediation": `failed` to `ready` is recorded "pointing at the `failed` event", and Restart step 3 records exactly that move inside the repair. The two rules contradict each other for repair events.
- **Proposed fix:** add "outside the repair" to "pointing at the `failed` event".

### F-10 · gap · (advisor) a database made before M4
- **Section:** "Domain model and storage" › "Projection rules"; "CLI commands" › "Other commands"; "Hashing"
- **Evidence:** M4 adds a column to an existing table. "A command creates a missing `openfactory.db`, and the tables it uses" does not cover a `tasks` table that exists without `cost_usd`, so the projector fails on an M3 database; rebuild is not a CLI command.
- **Proposed fix:** "A database made before M4 is discarded, as for a change to the canonical form" (or say how opening the database adds the column).

### F-11 · gap · (advisor) gitleaks's exit code for its own errors (to verify on the tool)
- **Section:** "Gates and remediation" › "Running a gate that starts a process"
- **Evidence:** "exit status 1 is a finding; any other failure of it is a failed gate that is not a finding" assumes gitleaks exits with another code on its own errors. The advisor believes gitleaks 8 exits 1 on fatal errors too, as its default `--exit-code`. Checked on 8.30.1 only partly (see Counts).
- **Proposed fix:** check on 8.30.1; if errors also exit 1, pass `--exit-code <n>` with a code gitleaks does not use for errors, and say "exit status `<n>` is a finding".

### F-12 · gap · (advisor) the target repo must ignore `.venv` and tool caches
- **Section:** "Gates and remediation" › "Target repo"
- **Evidence:** the agent will run `uv run pytest` while it works, before the path check; a `.venv` or cache directory the repo does not ignore is a changed path outside `allowed_paths`, a path violation that escalates at once. The precondition says nothing about ignores.
- **Proposed fix:** add "and its `.gitignore` covers `.venv` and the tool caches" to the precondition.

### F-13 · wording · (advisor) the parenthesis of "Remediation"
- **Section:** "Gates and remediation" › "Remediation"
- **Evidence:** "after a `failed` event that does not escalate at once (path violation, secret found, cost limit)" reads as examples of failures that do not escalate, the opposite of what is meant.
- **Proposed fix:** "after a `failed` event, unless it escalates at once (path violation, secret found, cost limit), ...".

### F-14 · wording · (advisor) "since its last retry" in the `tasks` DDL
- **Section:** "Domain model and storage", the `tasks` DDL
- **Evidence:** the comment "since its last retry (M4)" can be read as resetting on every remediation retry, which would make the cost limit a limit per attempt; "Metrics" is precise ("since its last retry by `resolve`").
- **Proposed fix:** "since its last `resolve --retry`".

### F-15 · wording · (advisor) rejection lines of a reviewer reply
- **Section:** "Gates and remediation" › "The review gate" against "Task contract" › "Plan checks"
- **Evidence:** "retried once, as for a planner call" brings in "`exit: ok` and `error` set to its rejection lines", which are defined only with plan-check rules and subjects; F-2's fix relies on them.
- **Proposed fix:** "a rejected reviewer reply has `exit: ok` and `error` set to its rejection lines, `schema  reply  <message>`, as for a planner reply with no task".

## Advisor

### Q1: Is F-1 a real problem? Nothing says what happens when the reviewer's reply is rejected a second time. Is "a second rejected reply fails the `review` gate" the right fix?
- Proposed: add "A second rejected reply fails the `review` gate, as a failed process does."
- Challenge: The problem is real. Line 703 sends the reader to the planner rule ("as for a planner call"), but there a second rejection makes the command exit 1 (line 552). Line 70 just says "then fails". By line 70's own definition a rejected reply is not a failed process, so the exception for a failed reviewer process does not cover it. One reader could have `run` exit 1; another could fail the gate. The fix copies how SC-87 handles a failed process, so it adds no new idea.
- Strongest alternative: end `run` with exit 1, as the planner does. That would leave one malformed model reply able to stop the whole loop, which goes against SC-87's "`run` goes on".
- Conflicts: none.
- Recommendation: the proposed fix. It closes the gap and stays in line with SC-87.
- Verdict: AGREE

### Q2: Is F-2 a real problem? The `review` gate's output file is supposed to hold "the verdict and the comments", but sometimes there is no verdict. Is "the file holds the run's `error`" the right fix?
- Proposed: "When there is no verdict, the file holds the run's `error` (for a rejected reply, its rejection lines)."
- Challenge: The problem is real. Line 709 says the gates other than `path_check` write their file on a pass and on a failure. Line 707's failure report reads "the text of its output file", and since `review` runs only when the other three gates passed, it is the only failed gate in that report. Leaving `output_path` null (as `path_check` does on a pass) would give the retry an empty report. The fix assumes that a rejected reviewer reply has defined "rejection lines". For the planner these are `rule  subject  message` lines built from plan-check rules and subjects (line 552), and nothing defines them for a reviewer reply (see miss M-11). The fix is right; M-11 makes its parenthesis meaningful.
- Strongest alternative: write no file (`output_path` null) and have the failure report use the `failed` reason alone. That loses the cause.
- Conflicts: none.
- Recommendation: the proposed fix, together with M-11. It keeps line 709 true and gives the retry a cause.
- Verdict: AGREE

### Q3: Is F-3 a real problem? The ordered list of one task's events has no slot for the reviewer's run events, and the `causation_id` rule does not say whether they count. Is the proposed insertion right?
- Proposed: put the reviewer's `AgentRunStarted`/`AgentRunFinished` (a second pair on a retry) before the `review` `GateEvaluated`, and count them in the task's `causation_id` chain like the implementer's.
- Challenge: The problem is real, and the evidence matches line 630 and line 641. The fix also has to fit the cost check. A reviewer `AgentRunFinished` can be followed directly by `gating` to `failed` with `cost limit` (line 636, line 794), with no `review` `GateEvaluated` at all. The fix's wording "before the `review` `GateEvaluated`" should read "after `gitleaks`'s `GateEvaluated`" so it still holds in that case.
- Strongest alternative: leave the run-stream events out of the task's chain. The implementer's run events are already in it, so this would be inconsistent.
- Conflicts: none.
- Recommendation: the proposed fix, anchored after the `gitleaks` `GateEvaluated`. It gives one chain per task, as the implementer's run already has.
- Verdict: AGREE

### Q4: Is F-4 a real problem? "It holds no file contents" seems to clash with a failure report that includes gate output text. Is the rewording right?
- Proposed: "It holds no contents of the repo's files; the agent reads them with its tools. A retry's failure report holds the text of the gates' output files."
- Challenge: The finding is real but minor. ruff's default output and pytest tracebacks quote source lines, so the pack does carry fragments of repo files through the report. The new wording ("the gates' output files") makes that explicit without claiming more. It is low value, and it can wait if the round needs to stay short.
- Strongest alternative: leave it as it is. The meaning can be inferred.
- Conflicts: none.
- Recommendation: the proposed fix. It costs one sentence and removes a literal contradiction.
- Verdict: AGREE
