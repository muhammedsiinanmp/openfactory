## Findings

### F-1 · blocker · applying v1.17 fails the conformance tests
- **Section:** "Domain model and storage" › Event types; "Task contract" › Path patterns
- **Evidence:** `./scripts/apply_spec.sh` runs CI. With v1.17 as the spec, three tests in `tests/unit/test_spec_conformance.py` fail: `test_event_types_match_the_spec_list` (`TestsCollected` is not an `EventType`); `test_payload_fields_match_the_spec_block` (the `TestsCollected` entry makes `events(event)` raise before the skip check); and both `test_path_pattern_statement_in_the_planner_prompt_matches_the_spec` and `..._in_the_context_pack_...` (SC-153 rewords the `*` bullet, line 537; `src/openfactory/app/planner_prompt.py:37` and `src/openfactory/app/context_pack.py:40` hold the old text). `test_projection_table_matches_the_spec_create_table` does not fail: it is parametrised over fixed tuples (lines 22-24), so no test holds the `trace_links` DDL yet.
- **Proposed fix:** change the code, not the proposal: one task committed on `spec/v1.17` before the apply, as TASK-058 did for v1.14. At minimum it adds the `EventType` value `TestsCollected` and the two prompt lines. It edits `tests/unit/test_m4_payloads.py:42-44` (the count of event types), an approved test edit like TASK-058's. The TASK-058 branch exception was "for this task only", so it needs a new decisions row from the human. The new prompt text changes later `context_hash` values. Alternative: drop SC-153's `*` wording, which fixes only the two prompt tests.

## Advisor

### Q1: Is P-1 real, and is the proposed fix right? Applying v1.17 as it stands would fail the conformance tests in `./scripts/apply_spec.sh`'s CI step. The proposed fix is a code task committed on spec/v1.17 before the apply, following the TASK-058 precedent.
- Proposed: change the code, not the proposal: one task on spec/v1.17 before the apply that adds the TestsCollected payload model, the trace_links table and the two prompt texts. The fallback is to drop SC-153's `*` wording.
- Challenge: The blocker is real, but the evidence needs four corrections:
  - **`test_projection_table_matches_the_spec_create_table` does not fail.** It is parametrised over the fixed tuples `M1_TABLES + M2_TABLES + M3_TABLES` (tests/unit/test_spec_conformance.py:22-24, 61). The spec DDL is only run through `executescript`, and the new `trace_links` block (proposal 318-325) is valid SQL. So no test holds the `trace_links` DDL at all. The M5 projector task should add `M5_TABLES = ("trace_links",)`.
  - **`test_payload_fields_match_the_spec_block` fails for certain, not "possibly".** `SPEC_PAYLOAD_ENTRIES` picks up `TestsCollected` (proposal 438). Then `events(event)` (line 117) raises `ValueError` before the skip check is reached, because `EventType` has no such value.
  - **`test_event_types_match_the_spec_list` fails**, as stated.
  - **Both path-pattern tests fail**, as stated. The old bullet with its full stop, "`*` matches any run of characters except `/`.", is not a substring of the new one (proposal 537). The old text is at planner_prompt.py:37 and context_pack.py:40.

  The minimum code to make the suite green is smaller than proposed: the `EventType` value `TestsCollected` plus the two prompt lines. With no `PAYLOAD_MODELS` entry the payload test skips, and the projector skips the event (proposal 333). The trace_links table and the payload model are not needed. That code task must edit fixed tests: tests/unit/test_m4_payloads.py:42-44 (`len(list(EventType)) == 12`), and test_m4_payloads.py:77 (eleven keys) if a payload model is added. That is the same kind of approved edit as the 2026-10-15 TASK-058 rows. The TASK-058 branch exception was granted "for this task only" (decisions.md 2026-10-15 TASK-058 row), so this needs a new decisions row from the human. Changing the two prompt texts also changes later planner and implementer `context_hash` values (SC-110 precedent).

  The fallback, dropping SC-153's `*` wording, fixes two of the four failures at most. It also reverts a decision the human made (SC-153).
- Strongest alternative: the same pre-apply task, limited to the `EventType` value and the two prompt texts (plus the fixed-test edits), leaving the payload model and table to the M5 tasks.
- Conflicts: decisions.md 2026-10-15 TASK-058 row ("for this task only"), so reusing the precedent needs a new row. Beyond that, none.
- Recommendation: the proposed fix (code change on spec/v1.17 before the apply), with the evidence corrected, a new decisions row, and the scope either minimal or as proposed. The code and spec can only be green together, and the fallback does not get there.
- Verdict: AGREE

### Q2: Is P-2 real, and is the proposed fix right? P-2 says the TestsCollected payload line `tests: [ { node_id, file, req } ]` lacks field types, unlike every other payload line.
- Proposed: `tests: [ { node_id: "<pytest node id>", file: "<path>", req: ["<id>", ...] } ]`.
- Challenge: The premise is false. `SpecValidated` uses the same untyped form for `violations: [ { rule, subject, message } ]` and `warnings: [ { check, subject, message } ]` (proposal 390-391), and `SpecImported.spec` is `{ components, requirements, adrs }` (385). The element shape and types are also stated where they are produced: the plugin line `{"node_id": "<pytest node id>", "file": "<path>", "req": ["<id>", ...]}` (proposal 713). The fix is harmless (the conformance regex `^  (\w+):` still yields `tests`), but it fixes nothing that is ambiguous.
- Strongest alternative: no change. At most, append "each as the plugin's line (see The pytest gate and `req` markers)" to the comment on line 441.
- Conflicts: none.
- Recommendation: no change. The shape is defined at line 713 and the untyped list form has precedent.
- Verdict: DISAGREE

### Q3: Is P-3 real, and is the proposed fix right? P-3 says the context pack lists the path pattern syntax as its own bullet (proposal 638), while the code keeps it inside the implementer's instructions (context_pack.py `_INSTRUCTIONS`).
- Proposed: fold it into the first bullet: "the implementer's instructions, which state the path pattern syntax as under Path patterns, require ...".
- Challenge: There is no contradiction.
  - **The order matches.** The bullets list what the pack holds, in order. The code's order is the rules, then the "Path patterns:" block (context_pack.py:28-46), then `## Task contract`, requirements, ADRs, tracked files and the failure report. That is exactly the order of the bullets (proposal 637-642).
  - **Nothing depends on the grouping.** No section heading or test depends on whether the syntax counts as part of the instructions. The conformance test checks only that the lines are present word for word.
  - **The current form is consistent.** "Planning" also states it as a separate fact ("The prompt states the path pattern syntax", line 549), so a separate bullet is the consistent form.
- Strongest alternative: no change.
- Conflicts: none (decisions.md 2026-10-22 SC-147 says only that "The context pack states the path pattern syntax").
- Recommendation: no change. The spec and the code agree on content and order.
- Verdict: DISAGREE

- Challenge: Four new items, none in docs/spec-audits/2026-10-22-M5.md:
