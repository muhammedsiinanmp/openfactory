### F-1 · blocker · M3 cannot pass a task with the contract as defined
- **Section:** "Milestones and definition of done"; "Gates and remediation"; "Task state machine"
- **Evidence:** line 720 "**Executor.** One task end to end: worktree, context pack, Claude Code run, path check, commit with trailers" and line 721 "**Gates and remediation.** ruff, pytest with req markers, gitleaks, reviewer". Against line 464 "sets `required_gates` to `[path_check, ruff, pytest, gitleaks, review]`", line 563 "A task passes only when every required gate passes", line 506 "`passed`: all gates passed; the orchestrator has committed" and line 541 "If all gates pass, the orchestrator itself commits". Reading A: in M3 a task is committed after the path check alone, which contradicts 563. Reading B: M3 never reaches `passed` or a commit, which contradicts 720. (2026-10-09 F-13.)
- **Proposed fix:** add to "Milestones and definition of done": "Until M4 builds them, `run` evaluates only `path_check`. The other required gates are not run and no `GateEvaluated` is recorded for them; a task whose path check passes is committed and moves to `passed`. The contract still lists all five gates." Tasks passed under M3 are development data and are discarded with the development database, as line 159 does for hashes.

### F-2 · blocker · behaviour of `run`
- **Section:** "CLI commands" (table and "Output"); "Task state machine"
- **Evidence:** line 668 "`openfactory run [--task ID]` | Executes ready tasks in dependency order" is all there is. "Output" (lines 691-700) has a bullet for `validate`, `approve spec`, `plan`, `approve plan` and `events`, none for `run`. Not stated: that it works on the approved plan and what it writes when there is none; the order among several `ready` tasks; whether a task made `ready` by a pass runs in the same invocation; whether `run` goes on to the next task after one fails; what `--task ID` does for an unknown id or a task that is not `ready`; the lines it prints; the exit code when a task fails. Line 512 "A task with dependencies stays `pending` until they have passed" names no actor, moment or `causation_id` for the `pending` to `ready` event. (2026-10-09 F-32.)
- **Proposed fix:** add an "Output" bullet and a paragraph under "Execution": "`run` works on the approved plan and refuses with `no approved plan` on standard error, exit 1. It takes the `ready` tasks in ascending task id as strings, one at a time. After a task passes, every `pending` task of the plan whose dependencies have all passed moves to `ready` (one `TaskStateChanged` each, in ascending task id, `causation_id` the `gating` to `passed` event) and is taken in the same invocation. A task that does not pass does not stop the others. `--task ID` runs that task only and refuses with `unknown task <ID>` or `<ID> is <state>, not ready`. `run` prints one line per task it took, `task_id  <final state>`, and exits 0 when every task it took passed, otherwise 1; with no `ready` task it prints nothing and exits 0."

### F-3 · blocker · worktree base, where task branches end up, and `protected_branches`
- **Section:** "Execution" › "Per-task sequence"; "Policies"; "Spec diff and impact analysis"
- **Evidence:** line 536 "`<base>` is the branch holding the task's dependencies". A task with no dependencies has no such branch; a task with two dependencies has two, and line 38 defers "merge-conflict handling". Line 646 "branching from the last commit of the untouched work" and line 648 "before their results merge" assume one line of work and a merge that no section defines. Line 194 "`protected_branches` lists branches the orchestrator refuses to commit on", yet by line 536 it only ever commits on `openfactory/<task id>`, so nothing can test the key. (2026-10-09 F-3.)
- **Proposed fix:** make execution a single chain, which sequential execution (line 38) allows: "`<base>` is the branch `openfactory/<task id>` of the task that passed most recently in the plan, or, for the first task, the commit `HEAD` of the repo points at when the task starts. Each task branch therefore contains every earlier passed task, and the last passed task's branch holds the whole build. The orchestrator never merges, and never commits on or moves a branch it did not create, so no branch of the human's changes. `protected_branches` is checked against the task branch name: a task whose branch `openfactory/<task id>` is listed is refused with `openfactory/<task id> is a protected branch`." The alternative is an integration branch `openfactory/main` that each passed task is fast-forwarded into; it adds a branch update per task and gives `protected_branches` the same meaning.

### F-5 · blocker · the path check is described twice, and its command cannot see every changed path
- **Section:** "Execution" › "Per-task sequence"; "Gates and remediation"
- **Evidence:** line 539 "the orchestrator runs `git status --porcelain` and checks every changed path against `allowed_paths` and `forbidden_paths`. Any violation fails the run" (step 4), then line 540 "Run the required gates" (step 5), whose first gate is line 567 "path_check | built in: diff paths vs contract". Reading A: step 4 is the `path_check` gate. Reading B: two checks, one `GateEvaluated`. And `git status --porcelain` prints an untracked directory as one line `dir/`, a rename as `old -> new`, quotes unusual names, and shows nothing for work the agent committed itself. (2026-10-09 F-8, F-31.)
- **Proposed fix:** "Step 4 is the `path_check` gate; it is evaluated once, first, and records one `GateEvaluated`. The changed paths are every path that differs between the `<base>` commit and the worktree, tracked or untracked and not ignored: `git status --porcelain=v1 -z --untracked-files=all`, with both names of a rename, plus `git diff --name-only -z <base> HEAD` when the branch tip is not `<base>`. A path is a violation when it matches a `forbidden_paths` pattern or matches no `allowed_paths` pattern. The gate's output file lists the violating paths, one per line."

### F-6 · blocker · glob syntax of `allowed_paths` and `forbidden_paths`
- **Section:** "Task contract"; "Policies"
- **Evidence:** line 192 "It uses the same glob syntax as the paths in a task contract"; "Task contract" defines none. The examples are `app/auth/**`, `specs/**`, `.env` and `.env.*` (lines 417-423). Reading A, gitignore rules: `.env` matches at any depth. Reading B, `fnmatch` on the whole path: `.env` matches only at the root and `*` crosses `/`. Reading C, `pathlib` matching: `**` needs a following segment. The planner is told only "the path patterns the task may change" (`src/openfactory/app/planner_prompt.py:31-32`), and the real `plan` run and the fixtures use `app/`, which matches nothing under B. (2026-10-09 F-9.)
- **Proposed fix:** add to "Task contract": "A path pattern is matched against a path relative to the repo root, with `/` separators, case-sensitively. `*` matches any run of characters except `/`; `**` as a whole segment matches zero or more segments; `?` matches one character except `/`. A pattern that ends with `/` is the same as that pattern followed by `**`. A pattern with no `/` matches a file of that name in any directory, so `.env` and `.env.*` cover every directory. There are no negations and no character classes." State the syntax in the planner prompt's instructions.

### F-7 · gap · the event sequence of one task, and what M3 does with a task that does not pass
- **Section:** "Task state machine"; "Execution"; "Domain model and storage" › "Streams and actors"
- **Evidence:** lines 338-340 give the events and `causation_id` of `plan` and `approve plan`; nothing does so for `run`. Line 514 "path or secret violations skip the retry and escalate at once" against `TRANSITIONS` (lines 517-527), which has no `running` or `gating` to `escalated`, so it is two events through `failed`. Line 539 runs the path check "After the agent exits" and does not say whether the task is then `running` or `gating`. "Retry with failure context" and "escalation" are M4 (line 721), so M3 has no stated end for a failed task. `TRANSITIONS` "is data; nothing here enforces it" (`src/openfactory/domain/states.py:3-4`) and the projector sets any state (`src/openfactory/adapters/sqlite_projector.py:146-149`).
- **Proposed fix:** "For one task `run` records, in order: `TaskStateChanged` `ready` to `running`; `AgentRunStarted`; `AgentRunFinished`; then, when the run's `exit` is `ok`, `running` to `gating`, one `GateEvaluated` per gate run, and either `CommitRecorded` then `gating` to `passed`, or `gating` to `failed`. A run whose `exit` is `error` or `timeout` goes `running` to `failed` with no gate. A path violation is `gating` to `failed`, then `failed` to `escalated`. Each event's `causation_id` is the event recorded just before it for the same task. The use case checks every transition against `TRANSITIONS` before recording it. `TaskStateChanged.reason` holds the cause of a move to `failed` or `escalated`. Until M4, a `failed` task that is not escalated stays `failed`."

### F-9 · gap · restart, and the life of a worktree
- **Section:** "Execution"; "Milestones and definition of done"
- **Evidence:** line 731 "Killing the process mid-run and restarting resumes from the event log without duplicate commits" has no mechanism. A killed `run` leaves a task `running` or `gating`, from which `TRANSITIONS` allows only `gating`, `failed` or `passed`; an `AgentRunStarted` with no `AgentRunFinished`; a worktree and a branch that make line 536's `git worktree add ... -b` fail on the next start; and possibly a commit made with no `CommitRecorded`. - **Proposed fix:** "`run` starts by repairing the approved plan from the log, in this order. A `pending` task whose dependencies have all passed, or that has none, moves to `ready`. Any other task in `running` or `gating` moves to `failed` with reason `interrupted`, and its unfinished run gets `AgentRunFinished` with `exit: error` and `error: interrupted`. Before each attempt the task's worktree and branch are removed if they exist and created again from `<base>`. A worktree is removed when its task passes; the branch stays." Whether an interrupted attempt counts against `max_attempts` follows from F-8 (it does).
