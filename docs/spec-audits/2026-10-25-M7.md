## Advisor

### Q1: Is F-1 real? The spec never says what `stats` prints, how it formats and orders its lines, or how it behaves with no runs. Is the proposed Output item right?
- Proposed: blocker. Add an Output item with `task`/`plan`/`role` lines, then `latency  p50  p95` (nearest rank over finished runs); a null counts as 0; no events, no repair; with no run it prints `latency  p50 -  p95 -` and exits 0.
- Challenge: The evidence is correct (lines 874, 895, 909-929; F-39; the 2026-10-13 SC-81 row). The fix does not say which plans get a `plan` line. Under F-2 a draft superseded by a second `plan` has planner runs but no task runs, and a plan may have no run at all. It also puts the repair's `duration_s: 0` runs (line 687) into the percentiles, which pulls p50 down. "A null counts as 0" also hides unreported cost, but that is acceptable.
- Strongest alternative: The same item, plus "a plan line for each `PlanCreated` that has a run, in ascending plan id". Optionally leave runs finished by the repair out of the percentiles.
- Conflicts: none
- Recommendation: The proposed item, plus a sentence naming which plans get a line. Without its output, `stats` cannot be tested.
- Verdict: AGREE

### Q2: Is F-2 real? After a replan, `tasks.plan_id` no longer shows which plan a task came from, so per-plan totals need a rule. Is the proposed rule right?
- Proposed: blocker. A plan's totals are the runs of the tasks its `PlanCreated.tasks` lists ("task ids are unique across plans"), plus the planner runs found through the `causation_id` chain. Classifier runs and twice-rejected `plan` runs belong to no plan.
- Challenge: The problem is real, and ADR-019 (accepted), Consequences, binds the source to `PlanCreated.tasks`. But the parenthesis "task ids are unique across plans" is false. "Planning" (line 571) says a draft superseded by a new `plan` has its tasks removed and "The new draft may reuse their ids". `task-id-in-use` also excludes "the draft being replaced" (line 586). Running `plan` twice before approving is a normal path. When it happens, the runs of a reused id would be counted under both plans. Leaving classifier runs out of every plan is a choice, not a given. 2026-10-09-all F-36 proposed counting them, and the "saving" line 876 describes arguably includes the cost of `impact`.
- Strongest alternative: "A task's runs count for the latest `PlanCreated` that lists the task", or count only plans that have a `PlanApproved`. Keep the causation-chain rule for planner runs. State openly whether the classifier runs of `impact` count toward the replan.
- Conflicts: none with ADR-019 or the 2026-10-11 SC-37 row. The parenthesis contradicts "Task contract" › Planning (line 571).
- Recommendation: The alternative. Attribute a task to the latest `PlanCreated` listing it, so the demo's ordinary re-plan does not double-count.
- Verdict: DISAGREE
