## Findings

### F-1 · blocker · what plan the replanned work lives in, and what "the approved plan" is after `replan`
- **Section:** "Spec diff and impact analysis" › Step 4; "Task contract" › Planning; "Execution" › `run`; "Domain model and storage" › Ids, Projection rules
- **Evidence:** line 811, "the planner ... proposes new or revised tasks. Untouched tasks keep their state and commits. After approval, only the new tasks run". Nothing says whether `replan` records a `PlanCreated` of a new `plan_NN`, what its `tasks` hold (the new tasks only, or new plus untouched), or what happens to the earlier approved plan (`plans.status` has `superseded`, used today only for drafts, line 553). `run`, `status` and `resolve` all work on "the approved plan" (lines 615, 865, 866), and a task has one `plan_id` (DDL line 278). Code is plan-scoped: the promotion rule's `passed` set is built from the plan's own tasks (`src/openfactory/app/run.py:252`, tasks from `plans.tasks(plan.id)` at `run.py:713`), so a new task depending on an untouched task of the earlier plan would never become `ready`. `SqlitePlans.approved()` returns the approved plan with the highest number (`docs/decisions.md` 2026-10-11, TASK-025: "Only one approved plan can exist before `replan` (M6)").
- **Proposed fix:** `replan` records `PlanCreated` for a new draft `plan_NN` for the latest approved spec version, holding only the new tasks; `PlanCreated` gains `replaces: null | "plan_NN"` (the approved plan it replans). On its `PlanApproved` the projector marks the replaced plan `superseded` and moves every task of it that is not `invalidated` or `abandoned` to the new plan (`tasks.plan_id`), so "the approved plan" stays one plan holding the untouched and the new tasks. A payload change: ADR, and the development database is discarded.

### F-2 · blocker · `<base>` after a replan, and "branching from the last commit of the untouched work"
- **Section:** "Execution" › Base and branches; "Spec diff and impact analysis" › Step 4
- **Evidence:** line 633, "`<base>` is the `sha` of the `commits` row with the highest run id ... among the tasks of the plan; when the plan has no commit, it is the commit `HEAD` of the repo points at"; line 811, "only the new tasks run, branching from the last commit of the untouched work". On the single chain the invalidated tasks' commits sit between and after untouched ones, so "the last commit of the untouched work" is not the chain tip unless the invalidated commits are dropped, which needs a rebase the orchestrator never does ("The orchestrator never merges"). If the replan's plan holds only new tasks (F-1 alternative), `<base>` is the human's `HEAD`, without the build. Already under Later: "Spec wording (before M6) ... F-10 'branching from the last commit of the untouched work' against the single chain" (`docs/spec-audits/2026-10-13-proposal-v1.12.md`).
- **Proposed fix:** `<base>` stays the tip of the chain: the latest commit among all tasks of the approved plan, invalidated tasks' commits included (with F-1, the moved tasks carry their commits). The new tasks start from a tree that still holds the invalidated work and change it. Reword line 811 to "branching from the tip of the chain, which still holds the invalidated work".

### F-3 · blocker · which versions `impact` compares, whether it records anything, and how `replan` gets the impact
- **Section:** "CLI commands" (table); "Spec diff and impact analysis"; "Domain model and storage" › Event types, Event payloads
- **Evidence:** CLI row, "`openfactory impact` | Diffs the latest two spec versions"; line 460, "The payload of `ImpactComputed` is defined when its milestone is planned"; line 350 lists `ImpactComputed`, but the Streams and actors table has no row for it. Readings of "latest two": the two highest approved versions, or the approved plan's version against the latest approved. With sv_01 planned and sv_02, sv_03 approved since, the first reading misses the sv_01→sv_02 change. Not said: whether `replan` reads a recorded impact or recomputes it (a second classifier call can classify differently from the report the human read); line 795, "The human can override any classification before approving", has no command, input or event.
- **Proposed fix:** `impact` diffs the approved plan's spec version against the latest approved version, and refuses (`no approved plan`; `no spec change since sv_NN`) otherwise. It records `ImpactComputed` (stream `spec:<new version id>`, actor `orchestrator`) holding `from_version`, `to_version`, the diff, the classifications and the traversal result. `replan` uses the latest `ImpactComputed` whose versions match and refuses without one (`run openfactory impact first`). Drop the override sentence for Phase 1 and list it under Deferred, or give `impact --kind REQ-ID=<kind>`.

### F-4 · blocker · the classifier call is not defined
- **Section:** "Spec diff and impact analysis" › Step 2; "Tech stack and repo layout" (line 70); "Metrics"
- **Evidence:** "For each `modified` requirement, the LLM returns: `class ChangeClass(BaseModel)`" with no `model_config = ConfigDict(extra="forbid")`, no reply wrapper (`--json-schema` needs an object at the top), no prompt content, and nothing saying whether there is one call per requirement or one for all. No checks on the reply: `req_id` matching the modified requirements, one entry each, `obsolete_criteria` being AC ids of the old version of that requirement. Line 70 gives limits, retry and failure for "a classifier call", and line 819 the run events, so only the call's content is missing. `docs/decisions.md` 2026-10-11 (TASK-032): the retry helper shared with the classifier waits for M6.
- **Proposed fix:** one classifier call per `impact`, made only when some requirement is `modified`. Prompt: fixed instructions defining the three kinds, then each modified requirement old and new with its acceptance criteria. Reply `{"changes": [ChangeClass]}`, `extra="forbid"`. Rejected (rule `schema`, plus a check set like the plan checks) when an entry's `req_id` is not a modified requirement, a modified requirement has no entry or two, or an `obsolete_criteria` id is not a criterion of the old version of that requirement. Retried once like a planner reply; a second rejection or a failed process exits 1 with `classifier call failed: <error>`.

### F-5 · blocker · the traversal: seeds, direction, which tasks and how far
- **Section:** "Spec diff and impact analysis" › Step 3, Step 4
- **Evidence:** "Starting from each non-cosmetic changed requirement, walk `trace_links` ...: requirement → tasks → downstream dependent tasks → commits → files → tests tagged with the requirement or touching those files". (a) Seeds: only `modified` requirements are classified; nothing says whether `removed`, `added` requirements, changed ADRs or a newly `deprecated` requirement seed the walk. (b) task → task is stored from a task to the task it depends on (line 341), so "downstream" walks it backwards; the sample prints "Tasks invalidated: AUTH-002, AUTH-003" and "Downstream tasks: AUTH-005" apart, so it is unclear whether downstream tasks are invalidated, and whether their commits and files are in "Files". (c) "No row is removed when a task is invalidated or abandoned" (line 344): on a second change the walk reaches the tasks of earlier plans and their commits; nothing filters by task state or plan. (d) "touching those files": a test has one test → file link, its own file (line 746), so "touching" can only mean the test's file is among those files; two readers could also read it as tests that exercise those files.
- **Proposed fix:** seeds are the `modified` requirements classified `behavioral` or `replacement` and the `removed` ones; a requirement whose ADR changed (status or body) counts as modified for classification; an `added` requirement seeds nothing and is new work. Walk requirement → task (`contract`), restricted to tasks of the approved plan not `invalidated` or `abandoned`; downstream tasks are those that reach an impacted task through `depends_on`, transitively, and are invalidated too; then their commits (`trailer`), files (`diff`), and tests with a `test_tag` link to a seed requirement or whose own file is one of those files. Reword "touching".

## Advisor

### Q1: Is F-1 real (what plan holds the replanned work, and what "the approved plan" is after `replan`), and is its fix right?
- Proposed: `replan` creates a draft `plan_NN` holding only the new tasks. `PlanCreated` gains `replaces`. On `PlanApproved` the projector supersedes the old plan and moves its tasks that are not `invalidated` or `abandoned` to the new plan.
- Challenge: The problem is real. `run`, `status` and `resolve` all work on one plan, and the code is scoped to one plan. The fix clashes with F-6, though. F-6 records the invalidations after `PlanApproved`. So when the projector applies `PlanApproved`, the impacted tasks are still `passed` and get moved too. That makes "not invalidated or abandoned" meaningless. F-2 also needs the invalidated tasks' commits to be inside the plan, and this filter would leave them out. The `replaces` field is not needed either. Line 553 already supersedes a draft by reading the projections, with no payload field. A draft made while an approved plan exists can only come from `replan`, because `plan` refuses then (line 546). The projector may read earlier projections (ADR-018 amendment of ADR-002). Evidence slips: run.py:256 is the subset test; the `passed` set is built at run.py:252. The plan-scoped promotion after a pass reads `plans.tasks(plan.id)` at run.py:713; run.py:342 is in `repair_plan`.
- Strongest alternative: On `PlanApproved`, when another plan is approved, the projector marks it `superseded` and moves all of its tasks to the new plan, whatever their state. No payload field is added. The order should be stated: the move first, then the `contract` links of the new tasks. Moving every task makes the ordering question with F-6 go away. The `<base>` rule (F-2) and `status` keep working unchanged. Invalidated tasks show in `status` with their state.
- Conflicts: none with an accepted ADR, if no field is added. With `replaces` it is an ADR-007 payload change (new ADR, development database discarded). It retires the premise of decisions.md row 2026-10-11 (TASK-025) "Only one approved plan can exist before `replan` (M6)". It does not conflict with it.
- Recommendation: Supersede and move every task of the old plan, derived from the projections, with no `replaces` field. This removes the clash with F-6 and F-2 and follows the line 553 precedent with less to build.
- Verdict: DISAGREE

### Q2: Is F-2 real (`<base>` after a replan against "branching from the last commit of the untouched work"), and is its fix right?
- Proposed: `<base>` stays the chain tip, invalidated tasks' commits included. Line 811 is reworded to "branching from the tip of the chain, which still holds the invalidated work".
- Challenge: Real. It is already under Later (progress.md line 147). The fix only holds if the invalidated tasks stay in the approved plan (my Q1 version). Under F-1 as written, their commits drop out of `latest_commit`, and `<base>` could fall back to an older commit. It also has a consequence the finding leaves out: the tip still holds the obsolete code and tests. That has to be handled in the replan prompt (see Q13 M-2).
- Strongest alternative: Branch from the parent of the earliest invalidated commit. That needs a rebase of the untouched tasks that passed later. "The orchestrator never merges" (line 633) and priority 6 both rule it out.
- Conflicts: none. It removes a contradiction with "Base and branches" (line 633).
- Recommendation: Keep the chain tip, together with my Q1 version of the move. It is the only reading the single chain supports without a rebase.
- Verdict: AGREE

### Q3: Is F-3 real (which versions `impact` compares, whether it records anything, how `replan` gets the impact), and is its fix right?
- Proposed: `impact` compares the approved plan's version with the latest approved version, with two refusals. It records `ImpactComputed` (stream `spec:<new id>`, actor `orchestrator`) holding the versions, the diff, the classifications and the traversal. `replan` uses the latest matching `ImpactComputed` and refuses without one. The override sentence goes to Deferred.
- Challenge: Real. Reusing the recorded impact saves a classifier call (priority 5) and keeps `replan` on the report the human read. One gap: a `run` between `impact` and `replan` can pass tasks and so change the walk. The fix should say that `replan` uses the impact as recorded (see Q13 M-7). Dropping line 795 changes what the spec means, so it needs a decisions row or an ADR, and the CLI table row "Diffs the latest two spec versions" has to be reworded. The evidence checks out.
- Strongest alternative: `impact` stays read-only, and `replan` runs the diff and the classifier again. That costs a second call and can contradict the report.
- Conflicts: the CLI table row for `impact`, and line 795 under "Spec diff and impact analysis" › Step 2 (a change to what the spec means). It fills line 460 and does not conflict with it.
- Recommendation: As proposed, plus one sentence that `replan` uses the recorded traversal as is. It costs one call and is deterministic downstream.
- Verdict: AGREE

### Q4: Is F-4 real (the classifier call is undefined), and is its fix right?
- Proposed: One call per `impact`, only when some requirement is `modified`. The reply is `{"changes": [ChangeClass]}` with `extra="forbid"`. Three content checks, one retry, then `classifier call failed: <error>` and exit 1.
- Challenge: Real. One call is the fewest calls. The fix leaves "a check set like the plan checks" unnamed.
