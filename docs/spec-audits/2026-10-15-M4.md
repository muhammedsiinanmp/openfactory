## Findings

### F-1 · blocker · the port, adapters and process rules of the gates that start a process
- **Section:** "Tech stack and repo layout"; "Gates and remediation"; "Execution" › "Per-task sequence"
- **Evidence:** line 87 "The gates that start a process (ruff, pytest, gitleaks) are adapters behind a port that is defined in M4." The port lists (line 80) and adapter lists (line 81) have no entry for it. Line 596 "Run the other required gates in the worktree (from M4)." The table (lines 661-667) gives a command and "Blocks on" per gate and nothing else. Not stated:
  - the port's name, method and result (a pass flag and output text, or an exit code);
  - which interpreter and environment run `ruff` and `pytest`: the target repo is a FastAPI service (line 48) with its own dependencies, so `pytest` from OpenFactory's own environment cannot import it. Reading A: the executables first on `PATH`. Reading B: `uv run pytest` / `uv run ruff` in the worktree, with the target repo's environment;
  - what a non-zero exit means per tool: `pytest` exits 5 when no test is collected, 2 or 4 on a usage or internal error; `ruff format --check` exits 1 when a file would change; `gitleaks` exits 1 on a finding (its `--exit-code` default) and other codes on its own errors;
  - what happens when a tool cannot be started (gitleaks not installed): a failed gate, a failed task with a `git:`-like reason, or a refusal of `run`;
  - the time limit of a gate process; `max_runtime_s` is the agent's limit ("a time limit of the contract's `max_runtime_s`", line 611), and a hanging test suite would block `run` forever;
  - what the gate's output file holds (standard output, standard error, both, in which order) and whether it is written on a pass; `path_check` writes it only on a failure (line 613), and `output_path` is "null when the gate wrote no file" (line 417);
  - `ruff` runs two commands (line 664): one gate result or two, one file or two.
- **Proposed fix:** add a paragraph under "Gates and remediation": "The gates `ruff`, `pytest` and `gitleaks` run behind the `GateRunner` port, `run(gate, worktree, output_dir) -> GateOutcome` (`passed`, `output_path`), adapter `process_gates`. Each command runs in the worktree with the target repo's environment as `uv run <command>` for `ruff` and `pytest`, and `gitleaks` from `PATH`; a gate passes when every command it runs exits 0. A command that cannot be started, or that runs past `max_runtime_s`, fails its gate. The output file holds each command line, then its standard output and standard error as printed, and is written on a pass and a failure. `ruff` is one gate; its two commands both run and write to one file." Add `GateRunner` and `process_gates` to the layout lists. An ADR (new port and adapter).

### F-2 · blocker · the pytest gate's tag rule (2026-10-09 F-16)
- **Section:** "Gates and remediation"; "Traceability"
- **Evidence:** line 665 "any failure, or zero tests tagged with the task's requirements" against line 705 "the pytest gate fails if a task produces no test tagged with its requirements" (and ADR-003 lines 35-36, the same words).
  - Reading A: the gate fails when the collected suite holds no test tagged with any of the task's requirements; tests from earlier tasks count.
  - Reading B: the gate fails when this task's change adds no such test.
  - Either way "its requirements" can mean at least one of them, or every one.
  - Under reading A, a second task on the same requirement passes the tag rule with no test of its own; under reading B, a task whose criterion is already covered by an earlier task's test must still add one.
- **Proposed fix:** "The `pytest` gate fails when the run of `pytest tests/` fails or collects no test, or when, for a requirement in the contract, no collected test carries `@pytest.mark.req("<id>")` for it. Tests from earlier tasks count." (reading A, every requirement), and the same words in "Traceability".

### F-3 · blocker · how the orchestrator reads `req` markers
- **Section:** "Traceability"; "Gates and remediation"
- **Evidence:** line 684 "pytest marker `@pytest.mark.req("REQ-AUTH-001")`, collected with `pytest --collect-only`"; line 665 the gate's command is `pytest tests/`. `pytest --collect-only` prints test node ids, not marker arguments, so a marker's requirement id cannot be read from its output without code running inside pytest (a plugin or a `conftest.py`). The spec does not say which. The marker is not registered in the target repo either: an unregistered marker gives `PytestUnknownMarkWarning`, and a target repo with `--strict-markers` fails collection. (In OpenFactory's own `pyproject.toml:34` the marker is registered; nothing says the target repo does the same.)
- **Proposed fix:** "The orchestrator reads markers with a pytest plugin shipped in OpenFactory and loaded with `-p openfactory.pytest_req`, which registers the `req` marker and writes each collected test's node id and `req` arguments as JSON lines to a file in the run's directory. The `pytest` gate runs `pytest -p openfactory.pytest_req tests/` once, and reads the tag rule from that file." Or, if a separate collection is preferred, state the second command and when it runs. The plugin has to be importable from the target repo's environment (F-1), which is a choice to make with F-1.

### F-4 · blocker · the review gate (2026-10-09 F-33)
- **Section:** "Gates and remediation"; "Tech stack and repo layout"; "Domain model and storage" › "Event payloads"; "Metrics"
- **Evidence:** line 667 "reviewer agent reads diff + contract, returns structured verdict | `reject` verdict (advisory if `approve` but gates fail)". Not stated:
  - whether the reviewer goes through `LLMProvider` (one prompt, structured output, no tools: line 62 names `LLMProvider` for "Planner and diff LLM calls") or `AgentExecutor` (line 611 describes only the implementer run); line 70 sets limits for "A planner or classifier call" only;
  - the verdict model (line 37 "Three agent roles: planner, implementer, reviewer"; role `reviewer` exists at line 428) and its JSON schema;
  - which diff: the staged changes against `<base>` (`git diff --cached <base>`) or something else, and through which `GitProvider` method (the "Ids" paragraph, line 436, lists `GitProvider`'s operations exactly, and none returns a diff's text);
  - the run's events: `AgentRunStarted` with `role: reviewer` and `task_id` set, its `context_hash`, whether a rejected reply is retried once (line 70);
  - what a failed reviewer process does: fail the gate, fail the task with `run error`, or skip;
  - what the gate's output file holds (the verdict and its comments);
  - "advisory if `approve` but gates fail" implies the reviewer runs even after a deterministic gate failed, a model call whose result cannot change the outcome; F-5 decides whether it runs at all then;
  - whether a `reject` is a failed gate that triggers a retry with the reviewer's comments as the failure report.
- **Proposed fix:** "The review gate is one `LLMProvider` call with no tools, the 300 second limit and the default model, in a new empty directory, like a planner call. Its prompt is the task contract and the output of `git diff --cached <base>` in the worktree (a new `GitProvider` operation). It replies `ReviewVerdict { verdict: "approve" | "reject", comments: str }`. It is recorded as an agent run with `role: reviewer` and the task's id; a rejected reply is retried once; a failed process fails the gate. The gate's output file holds the verdict and comments. `reject` is a failed gate, retried like the others." Add `ReviewVerdict` to "Task contract" or a new block, and the diff operation to the "Ids" paragraph. An ADR if `ReviewVerdict` is a new stored shape.

### F-6 · blocker · the retry: which failures, which events, in which command, with which failure report
- **Section:** "Task state machine"; "Gates and remediation" › "Remediation"; "Execution" ("The context pack", "Events of one task", "Restart", "`run`"); "CLI commands" › "Output"
- **Evidence:**
  - Line 559 "Failures loop back to `ready` until attempts run out" (any failure) against line 669 "on a failed gate, the task moves to `failed` and, if attempts remain, back to `ready`" (gate failures only). Line 552 "`failed`: the run errored, timed out, or a gate failed". Reading A: `run error`, `run timeout`, `no changes`, `git: ...` and `interrupted` retry too. Reading B: only a failed gate retries.
  - The `failed` to `ready` event: not stated who records it (the same `run`, right after the failure, or the next `run`'s repair), its `reason` and `causation_id`, nor whether the task is taken again in the same invocation (line 584 "repeatedly takes the `ready` task with the lowest task id" would take it at once). Under `--task ID` (line 587), whether the retry runs.
  - Escalation when attempts run out: line 669 "After `max_attempts` (default 2), it moves to `escalated`" gives no reason text, and line 624 would make it null.
  - "Restart" (lines 628-632) has no step for a `failed` task with attempts left, so a task left `failed` by an interrupted run (reason `interrupted`, line 631, which "counts as an attempt", line 634) is never retried; nor for a `failed` task with no attempts left that a killed run did not escalate.
  - The failure report: line 607 "the last failure report if this is a retry (from M4)" and line 669 "with the gate output attached to its next context pack", against line 609 "It holds no file contents". Not stated: what the report holds (the failed gate's name and its output file's text, or only the path), what it holds for a failure that has no gate (run error, timeout, no changes, git, interrupted), and how the use case reads it: `RunFiles` only writes (line 436), and a retry in a later `run` cannot take it from memory.
  - Line 798 "`run` prints one line per task it took as `task_id  <final state>`": a task taken twice gives one line or two.
- **Proposed fix:** "A `failed` task that is not escalated moves to `ready` when it has attempts left, else to `escalated` with reason `attempts exhausted`, in the same command right after the `failed` event and pointing at it; a task made `ready` this way is taken again in the same invocation, also under `--task`. This applies to every failure reason except those that escalate at once. 'Restart' gains a step after step 2: every `failed` task that is not escalated moves to `ready` or `escalated` by the same rule, in ascending task id. The failure report is the `reason` of the last `failed` event and, when a gate failed, the text of its output file, read through a new `RunFiles.read(path) -> str`. `run` prints one line per task, at its final state." An ADR if `RunFiles` gains a method (ADR-014).

### F-9 · gap · the cost limit: the read it needs, its reasons, and which runs count
- **Section:** "Metrics"; "Domain model and storage" › "Ids"; "Execution" › "Events of one task"
- **Evidence:** line 756 "After each `AgentRunFinished` of a task, the orchestrator sums `cost_usd` over the task's finished runs ... the task goes to `failed` and then to `escalated` with reason `cost limit`, and no gate runs."
  - The `Runs` port "gives the next run id and the unfinished run of a task" (line 434), a list that is exact; the sum needs a new read.
  - "goes to `failed` and then to `escalated` with reason `cost limit`": whether both events carry `cost limit`, or only the second (a path violation gives the two different reasons, line 621).
  - A run with `exit: error` whose cost exceeds the limit: reason `run error` or `cost limit`, and whether it escalates.
  - Whether a reviewer run (F-4) counts toward the task's sum, and whether its `AgentRunFinished` (recorded in `gating`) triggers the check, which would need `gating` to `failed`.
  - A failed process's cost is read from its standard output when it is a JSON object (decision of 2026-10-14, TASK-049); the spec does not say so, and it decides the sum.
- **Proposed fix:** "The `Runs` port also gives the sum of `cost_usd` over a task's finished runs, a null counting as 0. The check runs after the implementer's `AgentRunFinished`, before the `exit` is looked at: over the limit, the task goes `running` to `failed` and `failed` to `escalated`, both with reason `cost limit`. Reviewer runs count toward the sum and do not trigger the check." Add the TASK-049 rule to "Event payloads" (F-14).

### Q1: Is F-1 (the port, adapters and process rules for ruff, pytest and gitleaks) a real problem, and is the fix right?
