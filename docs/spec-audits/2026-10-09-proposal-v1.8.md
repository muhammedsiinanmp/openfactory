## Gaps

### F-1 · gap (M1) · order of lines that share a rule and a subject
- **Section:** CLI commands › Output
- **Evidence:** "first the violation lines, sorted by rule name and then by subject, as strings; then the policy lines" (line 651). The loader reports one `schema` violation per Pydantic error, so an item with two rejected fields gives two lines with the same rule and subject (decisions row 2026-10-08, TASK-007; `src/openfactory/app/spec_loader.py:99-106`), and every policy line has rule `schema` and subject `specs/policies.yaml` (`spec_loader.py:236-237`). The order of such lines is not given, and no order at all is given for the policy lines.
  - Reading A: a stable sort, so ties keep the order the loader or `validate_spec` produced them in.
  - Reading B: ties are sorted by message.
  - A CLI test with two errors on one item asserts one of them.
- **Proposed fix:** "sorted by rule name, then by subject, then by message, as strings; the policy lines are sorted the same way."

### F-2 · gap (M1) · what `approve spec` prints when there is nothing to approve
- **Section:** Spec input format › Spec versions; CLI commands › Output
- **Evidence:** "If the files equal the latest approved version, it records no events and exits 1 with `nothing to approve`, also when a draft exists" (line 168); "`validate` and `approve spec` print one line per violation and per policy problem ... then a count line that is always printed" (line 651); "Failure messages (`nothing to approve`, ...) ... go to standard error" (line 657).
  - Reading A: the command still prints the policy lines and the count line (`0 violations, M policy problems`) on standard output, then `nothing to approve` on standard error.
  - Reading B: it prints only `nothing to approve` on standard error, since it fails before the rules run.
  - "always printed" supports A; "The rules are not run" in the matching `validate` case (line 164) and the failure exit support B.
- **Proposed fix:** add to the `approve spec` bullet in Output: "When there is nothing to approve it still prints the policy lines and the count line."

## Wording

### F-3 · wording · "prints `approved sv_NN`" is said twice with different positions
- **Section:** CLI commands › Output
- **Evidence:** line 651 makes `approved sv_NN` the status line, printed last, after the count line; line 653 says "`approve spec` prints `approved sv_NN` and exits 0 on success". The same holds for `matches approved sv_NN` at line 164 ("prints `matches approved sv_NN` and exits 0") against line 651. The meaning is clear from line 651, but a reader of line 164 or 653 alone could print the status line with no count line before it.
- **Proposed fix:** in lines 164 and 653, replace "prints `...`" with "ends with the status line `...`".

### F-4 · drift · (advisor) two sentences of SC-10 are not in the proposal
- **Section:** CLI commands › Output; Domain model and storage › Event payloads
- **Evidence:** SC-10 row (2026-10-09): "The sort applies to the printed lines only; the order stored in `SpecValidated` is unchanged. A refused `approve spec` prints no status line." Line 651 has neither sentence, and the payload block (line 332) gives `violations` no order.

  - The second sentence is implied by "when there is one", but line 657 gives its failure messages as examples, so a refusal message is not excluded.
- **Proposed fix:** add to the first Output bullet: "The sort applies to the printed lines only; `SpecValidated.violations` is recorded in the order the rules returned it. A refused `approve spec` prints no status line."

### F-5 · gap (M1) · (advisor) exact text of the violation lines and the count line
- **Section:** CLI commands › Output
- **Evidence:** "a count line that is always printed, `N violations, M policy problems`" and "as `rule  subject  message`" (line 651).
  - Count line with N = 1 or M = 1: `1 violations, 1 policy problems` (the literal text) or `1 violation, 1 policy problem`.
  - Separator: exactly two spaces, or columns padded to align.
  - Line 657 makes these lines the results a script parses, and outline item 4 in `docs/progress.md` asserts them. SC-10 was raised because "a CLI test had nothing to assert"; these two points still leave it open.
- **Proposed fix:** "The three fields are separated by exactly two spaces, with no padding. The count line is not inflected: `1 violations, 0 policy problems`."

### F-6 · drift · (advisor) the subject of each content rule is stated only for `deleted-requirement`
- **Section:** Spec input format › Spec field rules
- **Evidence:** line 140: "each with the rule name, the ID it concerns, and a message", then "`deleted-requirement` (from M2; its subject is the requirement id)". Naming the subject for one rule leaves it open for the other five.
  - `constrained-by`: the requirement or the ADR.
  - `undeclared-component`: the requirement or the component name, which is not an ID.
  - The code has settled it: the offending id for `id-format` and `id-unique` (`src/openfactory/domain/spec_validation.py:56`, `:79`), and the requirement id for the other three (`:91`, `:105`, `:123`).
  - The subject is now a sort key (line 651), so it decides the order of the printed lines.
- **Proposed fix:** add to line 140: "The subject of `id-format` and `id-unique` is the offending id; the subject of the other content rules is the requirement id."

### F-7 · wording · (advisor) "canonical JSON" for an `events` line carries two things the same bullet does not mean
- **Section:** CLI commands › Output; Spec input format › Hashing
- **Evidence:** line 655: "`events` prints one stored event per line ... as canonical JSON", and line 146: "Canonical JSON is the model dumped in JSON mode".
  - `StoredEvent` dumped in JSON mode writes a UTC `created_at` with a `Z` suffix. The same bullet requires "the offset `+00:00`", which is the stored form (`src/openfactory/adapters/sqlite_events.py:54`). A reader who follows the definition fails the `created_at` sentence.
  - In the code, the canonical form also sorts every list (`src/openfactory/domain/spec_hash.py:29-40`), and line 327 speaks of "canonical order". `events` must keep `violations` in stored order (see F-4).
- **Proposed fix:** drop the term and keep the explicit list: "as one JSON object with the keys ..., with sorted keys at every level, separators `,` and `:` with no spaces, and non-ASCII characters left as they are; lists keep their stored order."

## Advisor

The advisor's reply, unedited. Its "Missed" items M-1 to M-4 are F-4 to F-7 above.

#### F-1
- Restated: the output sort (rule, then subject) gives no order for lines that tie on both, and no order at all for the policy lines.
- Proposed: sort by rule, then subject, then message, as strings; policy lines sorted the same way.
- Challenge: the quote at line 651 and the TASK-007 row (2026-10-08) check out. Two refinements to the evidence:
  - `spec_loader.py:99-106` is the path for top-level, ADR and policy errors; a requirement with two rejected fields goes through `spec_loader.py:149-157`. `236-237` is right for the policy.
  - Ties are not limited to `schema`. A requirement constrained by two bad ADRs gives two `constrained-by` lines with the same subject (`src/openfactory/domain/spec_validation.py:99-115`), and likewise `undeclared-component` (`118-129`). So the tie is an ordinary case, not an exotic one.
- Strongest alternative: a stable sort that keeps production order. That order (Pydantic's error order, the comprehension order in `validate_spec`) is stated nowhere in the proposal, so a test would pin an implementation detail.
- Conflicts: none. The fix says more than the SC-10 row (2026-10-09), which fixes the sort as "by rule name and then by subject", so it is an amendment to SC-10 for the human, not a pure wording fix.
- Recommendation: the proposed fix — the message tie-break makes the output depend only on content, and the messages already differ (field path, ADR id).
- Class: gap (M1) is right.
- Verdict: AGREE

#### F-2
- Restated: when `approve spec` has nothing to approve, it is not said whether the policy lines and the count line are still printed on standard output.
- Proposed: add to the `approve spec` bullet in Output: "When there is nothing to approve it still prints the policy lines and the count line."
- Challenge: the quotes at lines 168, 651 and 657 check out, and both readings are tenable. Reading A assumes the policy is loaded before the command decides to stop. That holds, since line 651 makes `approve spec` print policy problems and line 653 says they do not change its exit code. The fix should also say that no status line follows and the exit code stays 1.
- Strongest alternative: reading B, only `nothing to approve` on standard error. It is less output, but it makes "always printed" false and hides policy problems that `validate` prints for the same files.
- Conflicts: none. Reading A is the one consistent with the SC-10 row ("a count line that is always printed").
- Recommendation: the proposed fix (reading A) — `validate` and `approve spec` then share one printing path, and the matching `validate` case already prints `0 violations, M policy problems`.
- Class: gap (M1) is right.
- Verdict: AGREE

#### F-3
- Restated: lines 164 and 653 say "prints" the status line without the position that line 651 gives it.
- Proposed: in lines 164 and 653, replace "prints `...`" with "ends with the status line `...`".
- Challenge: the quotes check out. This is not a contradiction: line 651 governs the order, and lines 164 and 653 only name the content. A reader who reads the whole Output list cannot get it wrong, so the finding is marginal. The replacement needs a subject ("its output ends with the status line ...") to read correctly in line 164.
- Strongest alternative: leave both lines as they are; nothing a test asserts changes.
- Conflicts: none. The SC-1 and SC-2 rows also say "prints", and the rewording does not change their meaning.
- Recommendation: the proposed fix, worded "its output ends with the status line" — it costs two phrases and removes the only place the order can be misread. It is the lowest priority of the three.
- Class: wording is right.
- Verdict: AGREE
