## Findings

### F-1 · wording · a pooled figure that is `-` against its target
- **Section:** "Evaluation plan" › Targets, Run
- **Evidence:** Run (SC-243): "a per-run figure with no denominator is `-`"; Targets: "recall ≥ 0.9 on files and tests …; precision ≥ 0.7". Nothing says whether a `-` meets its target. `_meets` (src/openfactory/domain/eval_scoring.py:130-131) treats `None` as a miss, and tests/unit/test_eval_scoring.py pins that.
- **Proposed fix:** append to Targets: "; a pooled figure that is `-` misses its target".

### F-2 · wording · a cosmetic case's task, file and test labels
- **Section:** "Evaluation plan" › Cases, Metrics
- **Evidence:** Metrics calls the cases with empty labelled tasks, files and tests "(the cosmetic and new-requirement cases)", but Cases (SC-241) defines a cosmetic case by its kinds only. A cosmetic case labelling files would contradict the cosmetic target. The human's TASK-112 Q3 answer (progress.md Later) makes TASK-116 check it.
- **Proposed fix:** in Cases, after the SC-241 sentence: "A cosmetic case labels no tasks, files or tests."

### F-3 · wording · which tasks are the predicted tasks (advisor)
- **Section:** "Evaluation plan" › Ground truth, Run
- **Evidence:** Run asks for "the task … precision and recall of the case", and Ground truth counts downstream tasks as affected, but the spec never says the predicted tasks are `ImpactComputed.tasks` together with `downstream`. `score_case` (src/openfactory/domain/eval_scoring.py:84) uses the union. The task figures have no target.
- **Proposed fix:** in Ground truth: "…count as affected, with their files and tests, and the predicted tasks are the `ImpactComputed`'s `tasks` and `downstream`."

## Advisor

### Q1: Is F-1 a real problem? A run's pooled figure can print `-`, and nothing says whether a `-` meets the recall ≥ 0.9 or precision ≥ 0.7 target. Is appending "; a pooled figure that is `-` misses its target" to Targets the right fix?
- Proposed: append to Targets "; a pooled figure that is `-` misses its target".
- Challenge: The gap is real but almost never matters. A pooled precision is `-` only when nothing was predicted. Then there are no hits, so recall is 0 (already a miss) or also `-`. A pooled recall is `-` only when no pooled case labels any file, or any test. With the specified mix (3 behavioral and 2 replacement cases with ground truth), that is a labelling slip, not a real outcome. So the clause only decides runs that are degenerate. One could argue a `-` recall "vacuously" meets the target, since no affected test could be missed. Failing it is the safer signal for an eval with no labelled tests, though. The fix matches `_meets` (eval_scoring.py:130-131). It also gives a spec basis to the TASK-112 tests that pin `{"fp": None}` and `{"tr": None}` as misses (tests/unit/test_eval_scoring.py:216-221). Today those tests rest on no spec text.
- Strongest alternative: no spec change. Record in progress.md "Later" that a `-` pooled figure is unreachable with the specified mix and is treated as a miss in code. This fits the "prefer shipping" preference.
- Conflicts: none. It agrees with SC-243 (2026-10-26: "a per-run figure with no denominator is `-`") and SC-235/SC-226 ("misses every target").
- Recommendation: the proposed fix. It is one clause in a round that is already open, it matches the code and the tests, and it closes the reading before TASK-116 relies on it.
- Verdict: AGREE

### Q2: Is F-2 a real problem? Metrics calls the empty-truth cases "(the cosmetic and new-requirement cases)", but no rule says a cosmetic case labels no tasks, files or tests. Should Cases say so?
- Proposed: in Cases, "A case is cosmetic when it labels at least one kind and every labelled kind is `cosmetic`; it labels no tasks, files or tests."
- Challenge: The problem is real. SC-241 defines a cosmetic case only by its kinds. A cosmetic case that labelled files would sit in both pools, and its labels would contradict the cosmetic target, which requires empty `files`/`tests` in `ImpactComputed`. Only one of the two could be met. The human already answered this way (progress.md Later, TASK-112 Q3: "TASK-116 checks ... that every cosmetic case labels no tasks, files or tests"), so this writes a decided answer into the spec. Two weak points. (a) The sentence says what a case must label, not what happens when it does not. SC-234 defines "malformed" only for refusals, so how TASK-116 reports a violation (an assertion failure or a malformed-case stop) is left to the task. That is acceptable, because Procedure leaves the case file format to the eval task. (b) The "; it" after a definition reads a little loosely. "A cosmetic case labels no tasks, files or tests." would be clearer. That is a wording tweak, not a different option.
- Strongest alternative: drop the parenthetical "(the cosmetic and new-requirement cases)" from Metrics. Then nothing presumes the labels, and the pooling rule (SC-239) handles any cosmetic case by its labels. This adds no rule, but it leaves the cosmetic target and a labelled cosmetic file in conflict, and it drops the human's TASK-112 Q3 answer from the spec.
- Conflicts: none. It is consistent with SC-241, SC-239, SC-227 and the TASK-112 decisions row (2026-10-25). ADR-021 is not touched, since no new label key is added.
- Recommendation: the proposed fix, optionally worded "A cosmetic case labels no tasks, files or tests." It writes the human's TASK-112 Q3 answer into the spec and removes the clash between the cosmetic target and cosmetic labels.
- Verdict: AGREE

### Q3: What did the audit miss in the changed sections and the sections they rely on?

- Challenge: I found one minor miss and nothing else.
  - **M-1 · wording (minor) · "Evaluation plan" › Run, Ground truth.** Run asks for "the task ... precision and recall of the case", and Ground truth says the downstream tasks count as affected in the labels. Possible fix: in Ground truth, "...count as affected, with their files and tests, and the predicted tasks are the `ImpactComputed`'s `tasks` and `downstream`." Recording it as a Later line is equally defensible.
  - Checked and consistent: the `report` bullet against `_report_lines` (cli.py:525-548): blank lines as SC-237 says, none inside fences or the table, `total` with an empty `Kind`.
