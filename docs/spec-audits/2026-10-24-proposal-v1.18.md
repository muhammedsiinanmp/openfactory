## Findings

### F-1 · gap · an empty replan reply is rejected (advisor)
- **Section:** "Task contract" › Planning; Plan checks; "Spec diff and impact analysis" › Step 5
- **Evidence:** line 589, "A reply with no tasks is accepted only when the spec set has no requirement that is not deprecated (otherwise `uncovered` rejects it)." A replan whose only seeds are `deprecated` or `removed` requirements lists tasks, so `nothing to replan` does not fire; the right reply is `{"tasks": []}`, which the replan `uncovered` rule accepts, but line 589 rejects it, so `replan` makes two calls and exits 1. Approving an empty draft is the only way to invalidate those tasks.
- **Proposed fix:** "A reply with no tasks is accepted only when `uncovered` accepts it; for a first plan, that is when the spec set has no requirement that is not deprecated."

### F-2 · gap · a new task may depend on an invalidated untouched task (advisor)
- **Section:** Plan checks (`unknown-dependency`, line 578); Step 5 (replan prompt, line 862)
- **Evidence:** "The untouched tasks are the other tasks of the approved plan" (line 839); after the SC-158 move that set includes tasks invalidated by an earlier replan, so "an untouched task that is not `abandoned`" accepts a dependency on an `invalidated` task, which never passes: the new task stays `pending` for ever, on any second replan. The 2026-10-24 SC-163 row says "not `abandoned`" too.
- **Proposed fix:** "an untouched task that is neither `abandoned` nor `invalidated`", at line 578 and line 862.

### F-3 · gap · `cosmetic` for a requirement that gained a criterion (advisor)
- **Section:** "Spec diff and impact analysis" › Classifier checks (`cosmetic-with-work`, line 828)
- **Evidence:** the check catches a `cosmetic` entry for a requirement that lost a criterion, not one that gained one. Such a requirement is no seed; if nothing else changed, `replan` refuses with `nothing to replan` and the new criterion is never planned, with no error. Widens the 2026-10-24 SC-171 row.
- **Proposed fix:** "...or is for a requirement that lost or gained a criterion". Optional if treated as exotic.

## Advisor

### Q1: Is F-1 real (the approve-plan read says "the latest `ImpactComputed` recorded before the draft's `PlanCreated`", but the two events sit on different streams and nothing names the order key), and is its fix right?
- Proposed: Replace it with "the `ImpactComputed` with the highest `seq` below that of the draft's `PlanCreated`".
- Challenge: The problem is real but small. `seq` is the only total order across streams, and `EventStore.read` already returns events in ascending `seq` (`src/openfactory/ports/event_store.py:27`), so an implementer would almost certainly read it that way anyway. The bigger issue is that the fix covers only one spot. The proposal uses the same unkeyed cross-stream words elsewhere: "the latest `ImpactComputed` whose `from_version` ..." in Step 5 (line 860), "the latest such event" in the `replan` refusal (line 925), and "Each `impact` records a new" (line 841). If line 864 needs a key, those need one too. Patching only line 864 suggests the others mean something different.
- Strongest alternative: Add one sentence to "Event envelope rules", after the `seq` bullet at line 359: "Between events, 'latest', 'before' and 'after' compare `seq`." This covers every use, costs one line and leaves line 864 as it is.
- Conflicts: none.
- Recommendation: The envelope sentence. It fixes every cross-stream "latest" and "before" at once, for the same cost.
- Verdict: DISAGREE

### Q2: Is F-2 real (the three `approve plan` refusals are listed with no stated check order, unlike `plan`, `run`, `resolve` and `replan`), and is its fix right?
- Proposed: Add "checked in this order" in the order listed, and have the `running`/`gating` refusal name the lowest such task id.
- Challenge: Real. A stale replan draft and a task left `running` by a crashed `run` can happen together, and the two refusals give different advice (`run openfactory replan` against `run openfactory run first`). The order also matters for a second reason: the stale check must come before the `ImpactComputed` read, because that read matches the draft's `to_version`. The listed order (no draft, stale, running/gating) is the only sensible one and matches the code (`src/openfactory/app/approve_plan.py:57-65`). Naming the lowest id is needed because several tasks can be `running` or `gating`. Both changes are one line.
- Strongest alternative: Leave the order unstated and let the task that builds it settle it in a decisions row. That makes the outcome less testable from the spec, for no saving.
- Conflicts: none.
- Recommendation: As proposed. It is cheap, matches the precedent and the existing code, and makes the outcome testable.
- Verdict: AGREE

### Q3: Is F-3 real (the section opens "Impact analysis is two steps" but now has Step 1 to Step 5), and is its fix right?
- Proposed: "Impact analysis rests on two deterministic steps, a structural diff ... and a graph traversal ...; the LLM only classifies the change between them."
- Challenge: Mostly cosmetic, and older than this proposal: v1.17 already had "two steps" over Step 1 to Step 4 (spec line 780). Nothing can be tested against the sentence. Still, v1.18 rewrote this section and added a numbered Step 5, so the count is now clearly wrong. The fix keeps the meaning (the deterministic parts decide, the LLM only classifies) and costs one sentence.
- Strongest alternative: No change, recorded as a no-text row in the style of SC-183. That is defensible under the preference for short rounds.
- Conflicts: none.
- Recommendation: As proposed. It is a one-sentence fix in a section this round already rewrites.
- Verdict: AGREE
