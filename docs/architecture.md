# Architecture

## Layers
domain → ports ← adapters; app uses domain + ports.

## Components
<!-- one short section per component as it is built -->

### Domain events
`src/openfactory/domain/events.py`. Pure Pydantic v2 models, no I/O.
- `EventType`: the closed set of 12 Phase 1 event type names.
- `Event`: a new event with no `seq`; its fields cannot be reassigned and unknown fields are rejected. Fields mirror the `events` table columns: `event_id` (any UUID; required), `stream` (non-empty), `type`, `payload` (a JSON object; `NaN`, `Infinity`, strings that are not valid Unicode and integers too large to read back are rejected), `actor` (`human`, `orchestrator` or `agent:<role>`), `causation_id` (optional), `created_at` (an aware datetime or ISO 8601 string, normalised to UTC; naive datetimes and numeric timestamps are rejected).
- `Event.new(...)`: builds a new event with a generated UUID4 `event_id` and the current UTC time as `created_at`.
- `StoredEvent`: an `Event` plus the required `seq` assigned by the store, a strict integer of at least 1.

### EventStore port
`src/openfactory/ports/event_store.py`. The append-only event log interface.
- `EventStore` (Protocol): two methods. `append(event: Event) -> StoredEvent` assigns a `seq` and stores the event; if its `event_id` is already stored with identical content, it returns the original row; if content differs, it raises `EventConflictError`. `read(stream: str | None = None) -> list[StoredEvent]` returns stored events in ascending `seq`, optionally filtered by stream.
- `EventConflictError`: raised when an `event_id` is appended with different content than what is already stored.

### SQLite event store
`src/openfactory/adapters/sqlite_store.py`. Implements `EventStore` over SQLite. Its SQL for the `events` table comes from `sqlite_events`.
- `SqliteEventStore(path)`: opens the database file (creating it if it does not exist), creates the `events` table if missing using the spec's DDL, and sets WAL mode.
- Idempotency enforced by `event_id UNIQUE NOT NULL` constraint and `INSERT ... ON CONFLICT(event_id) DO NOTHING`.
- Rows read back are validated as `StoredEvent` before they are returned; `close()` releases the connection.

### Spec models
`src/openfactory/domain/models.py`. Pure Pydantic v2 models for a spec set, no I/O.
- `AcceptanceCriterion`: `id` and `text`.
- `Requirement`: `id`, `title`, `statement`, `priority`, `constrained_by` (list of ADR ids), `components`, `acceptance_criteria` (list of `AcceptanceCriterion`), and `deprecated` (boolean, optional, defaults to `false`); `constrained_by`, `components` and `acceptance_criteria` default to empty lists.
- `Adr`: `id`, `status` (closed set: `proposed`, `accepted`, `superseded`), and `body` (string, optional, defaults to empty string).
- `Priority`: closed set (`must`, `should`, `could`), enforced by enum.
- `SpecSet`: `components` (list of strings), `requirements` (list of `Requirement`), and `adrs` (list of `Adr`).
- All models are frozen. `AcceptanceCriterion`, `Requirement` and `SpecSet` reject unknown fields; `Adr` ignores them, since ADR front matter normally has more than `id` and `status`.

### Spec validation
`src/openfactory/domain/spec_validation.py`. Pure function that validates a spec set against deterministic rules.
- `Rule` enum: `id-format`, `id-unique`, `missing-acceptance-criteria`, `constrained-by`, `undeclared-component`, `deleted-requirement`, `schema`. `schema` is reported by the spec loader and `deleted-requirement` by the validate use case; `validate_spec` returns neither.
- `SpecViolation`: `rule` (a `Rule`), `subject` (the id the violation concerns), and `message`.
- `validate_spec(spec: SpecSet) -> list[SpecViolation]`: applies the first four deterministic validation rules from the spec (the fifth, on deleted requirements, needs the tasks and is applied by the validate use case) and returns every violation in a fixed rule order, collecting all violations in one run.
- `deleted_requirements(approved: SpecSet, spec: SpecSet) -> list[str]`: the ids in the approved set that are absent from the loaded one, in ascending order.
- `deleted_requirement_violation(requirement_id: str, task_ids: list[str]) -> SpecViolation`: rule `deleted-requirement`, subject the requirement id, message `requirement '<id>' is deleted but tasks still reference it: <task ids sorted and joined by ", ">`.

### Spec hashing
`src/openfactory/domain/spec_hash.py`. Pure functions that compute canonical JSON and SHA-256 hashes of spec items and of the policy.
- `canonical_json(item: SpecItem) -> bytes`: the model dumped in JSON mode with sorted keys, separators `,` and `:` with no spaces, non-ASCII characters left as they are, and encoded as UTF-8.
- `content_hash(item: SpecItem) -> str`: the SHA-256 of the canonical JSON, written as 64 lowercase hex characters.
- `SpecItem`: `AcceptanceCriterion`, `Requirement`, `Adr`, or `SpecSet`.
- Before hashing, lists are sorted innermost first; items with an `id` sort by `(id, canonical JSON of the item)`, and every list of strings is sorted by value, including each requirement's `components` and `constrained_by`. Omitted optional fields hash the same as their defaults.
- `policy_hash(policy: Policy) -> str`: the SHA-256 of the policy dumped in JSON mode and serialised with the same `_dumps`, as 64 lowercase hex characters. It does not sort lists: `forbidden_paths` and `protected_branches` are hashed in file order, because their order reaches the task contracts. It covers the five keys with defaults filled in, not the baseline paths.

### Event payloads
`src/openfactory/domain/payloads.py`. Pure Pydantic v2 models for the payloads of the three M1 spec events, the five M2 plan, task and agent run events and the two M3 gate and commit events, no I/O. Its only first-party imports are from `openfactory.domain`.
- `SpecImportedPayload`: `spec_version`, `hash` and `spec` (a `SpecSet`).
- `SpecValidatedPayload`: `spec_version`, `hash`, `violations` (list of `RecordedViolation`) and `warnings` (list of `SpecWarning`).
- `SpecApprovedPayload`: `spec_version` and `hash`.
- `RecordedViolation`: `rule`, `subject` and `message`, all strings. `rule` is a plain `str`, not the `Rule` enum, so a stored event stays valid if a rule is later renamed or removed. `SpecWarning`: `check`, `subject` and `message`, all strings.
- `SpecVersionId` is a string matching `^sv_\d{2,}$`; `ContentHash` is a string of 64 lowercase hex characters. Only the form of `hash` is checked; it is not compared with `spec`.
- `PlanCreatedPayload`: `plan_id` (`PlanId`), `spec_version`, `policy_hash` (`ContentHash`), `run_id` (`RunId`) and `tasks` (list of `TaskContract`, kept in the order given). `PlanApprovedPayload`: `plan_id`.
- `TaskStateChangedPayload`: `task_id` (`TaskId`), `from_`, `to` (both `TaskState`) and `reason` (`str | None`). `from_` has the alias `from`; the config sets `serialize_by_alias=True` and `validate_by_name=True`, so a plain `model_dump(mode="json")` writes `from` and `from_=` works at run time, though pyright rejects it in typed code (an input key `from_` also validates). A validator rejects a null `reason` when `to` is `invalidated`; a text `reason` with another `to` is allowed. `from` to `to` is not checked against `TRANSITIONS`.
- `AgentRunStartedPayload`: `run_id`, `task_id` (`TaskId | None`, null for a planner or classifier run), `role` (`RunRole`), `runtime` and `context_hash`. `AgentRunFinishedPayload`: `run_id`, `exit` (`RunExit`), `model`, `tokens_in`, `tokens_out`, `cost_usd` (all nullable), `duration_s` (float) and `error` (`str | None`). No link between `exit` and `error` is checked.
- `GateEvaluatedPayload`: `run_id` (`RunId`), `task_id` (`TaskId`), `gate` (`GateName`), `passed` (`bool`) and `output_path` (`str | None`, null when the gate wrote no file). `CommitRecordedPayload`: `sha` (`CommitSha`), `task_id` (`TaskId`), `run_id` (`RunId`), `branch` (`str`), `spec_version` (`SpecVersionId`) and `files` (`list[str]`, kept in the order given; sorting is the use case's job). No check across fields is made.
- `TaskResolvedPayload`: `task_id` (`TaskId`) and `decision` (`ResolveDecision`, a `Literal` of `retry`, `abandon`). A human's resolve of an escalated task; closed set, widened only.
- `GateName` is a `Literal` of `path_check`, `ruff`, `pytest`, `gitleaks`, `review`, repeating the five names of `REQUIRED_GATES` (a test ties the two); `CommitSha` is a string matching `^[0-9a-f]{40}$` (lowercase only).
- `PlanId` matches `^plan_\d{2,}$`, `RunId` `^run_\d{4,}$` and `TaskId` `^[A-Z]+-\d{3}$` (repeating the pattern of `PlannedTask.task_id`). `RunRole` is a `Literal` of `planner`, `implementer`, `reviewer`, `classifier`; `RunExit` is a `Literal` of `ok`, `error`, `timeout`. The closed sets, `GateName` included, are widened only (ADR-007 amendment).
- All fields are required. The models are frozen and reject unknown fields. The `SpecImportedPayload` model does not reorder `spec`, and `PlanCreatedPayload` does not reorder `tasks`.
- `PAYLOAD_MODELS: dict[EventType, type[BaseModel]]` maps `SpecImported`, `SpecValidated`, `SpecApproved`, `PlanCreated`, `PlanApproved`, `TaskStateChanged`, `AgentRunStarted`, `AgentRunFinished`, `GateEvaluated`, `CommitRecorded` and `TaskResolved` to these models (eleven entries). Only `ImpactComputed` has no entry yet.

### SpecFiles port
`src/openfactory/ports/spec_files.py`. The read-only interface to the spec files. It returns plain text and does no parsing. It imports nothing from `adapters` or `app`.
- `SpecFiles` (Protocol): two methods. `read(path: str) -> str | None` returns the text of the file at `path`, a POSIX-style path relative to `specs/` (`requirements.yaml`, `policies.yaml`, `adrs/<name>.md`), or `None` if the file does not exist, so a missing file can be told from an empty one. `list_adrs() -> list[str]` returns the paths relative to `specs/` of the `*.md` files directly in `adrs/`, in ascending order, or an empty list if there are none.

### Filesystem spec files
`src/openfactory/adapters/filesystem_spec_files.py`. Implements `SpecFiles` over a directory.
- `FilesystemSpecFiles(specs_dir: Path)`: takes the `specs/` directory itself.
- `read` opens the file with `encoding="utf-8"` and `newline=""`, so the text does not depend on the platform's default encoding and line endings are returned as they are on disk (normalising an ADR body to `\n` is left to the loader).
- `list_adrs` returns sorted `adrs/<name>` for every `*.md` file directly in `adrs/`, whatever its name; sub-directories are not searched. It returns `[]` if `adrs/` is missing or empty.

### Spec loader
`src/openfactory/app/spec_loader.py`. Application-layer function that loads the spec files into a `SpecSet`. It reads only through the `SpecFiles` port and imports nothing from `adapters`.
- `load_spec(files: SpecFiles) -> SpecLoadResult`: reads `requirements.yaml` and every file `list_adrs` returns, and collects every problem in one run.
- `SpecLoadResult`: a frozen model with `spec` (a `SpecSet` or `None`) and `violations` (a list of `SpecViolation`). It holds either the spec set or violations, never both. Requirements keep file order and ADRs follow `list_adrs` order. `load_spec` does not read `policies.yaml`.
- YAML is parsed with `yaml.load` and a `SafeLoader` subclass that rejects a mapping with the same key twice. An ADR file is split at its first two `---` lines into front matter and body; line endings are normalised to `\n` in the body, which is not trimmed, and a `body` key in the front matter is ignored.
- Every problem is a `SpecViolation` with rule `schema`: a missing file, a file that is not valid UTF-8, a YAML syntax error or duplicate key, an ADR file without front matter, front matter or a top level that is not a mapping, and a value the models reject. A top-level `adrs` key in `requirements.yaml` is rejected as an unknown field. Each requirement and each ADR is validated on its own, and there is one violation per Pydantic error, with the field path in the message.
- The subject is the nearest enclosing item with a readable string `id` (acceptance criterion, then requirement or ADR); otherwise it is the file path relative to the repo, which is the port's path prefixed with `specs/`.

### Policy model
`src/openfactory/domain/policy.py`. Pure Pydantic v2 model of `specs/policies.yaml` and the baseline forbidden paths, no I/O. It imports nothing from `adapters`, `app` or `ports`.
- `Policy`: `protected_branches` (list of strings, default `["main", "master"]`), `forbidden_paths` (list of strings, default `[]`), `max_attempts` (integer, default 2), `max_runtime_s` (integer, default 1200) and `max_cost_usd` (float, default 1.50). The three limits must be greater than zero. The model is frozen and rejects unknown fields. Entries in the lists are plain strings; their glob syntax is not checked. The matcher for them is in `domain/path_patterns.py`.
- `BASELINE_FORBIDDEN_PATHS`: the tuple `("specs/**", ".openfactory/**", ".env", ".env.*")`. It is not a field of `Policy` and cannot be set from the policy file. `Policy.forbidden_paths` holds only the file's list; nothing is merged in the model.

### Policy loader
`src/openfactory/app/spec_loader.py`, next to the spec loader and using its read, YAML and violation helpers.
- `load_policy(files: SpecFiles) -> PolicyLoadResult`: reads only `policies.yaml` through the `SpecFiles` port.
- `PolicyLoadResult`: a frozen model with `policy` (a `Policy` or `None`) and `violations` (a list of `SpecViolation`); it holds either the policy or violations, never both.
- An empty or comment-only file is a valid policy with all defaults. Every problem is a `schema` violation with subject `specs/policies.yaml`: a missing file ("missing; run openfactory init"), a file that is not valid UTF-8, a YAML syntax error or duplicate key, a top level that is not a mapping, and a value or unknown key the model rejects (one violation per Pydantic error).

### SQLite projector
`src/openfactory/adapters/sqlite_projector.py`. Builds the projection tables from stored events: `spec_versions`, `requirements`, `adrs`, `plans`, `tasks`, `task_deps`, `agent_runs`, `gate_results` and `commits`. It imports only from `openfactory.domain` and the standard library. It has no port and no `TYPE_CHECKING` conformance assertion (ADR-009; ADR-001 rejected a projector port).
- `SqliteProjector(conn)`: takes an open `sqlite3.Connection`. It never commits or rolls back; the caller owns the transaction.
- `create_tables()`: creates the nine tables with the spec's DDL if missing (no foreign key, no `CHECK`).
- `apply(event: StoredEvent)`: validates the payload against its model in `PAYLOAD_MODELS` before any write, and raises `pydantic.ValidationError` on a mismatch. `SpecImported` writes the draft version row and its requirement and ADR rows, replacing the content of an existing draft with the same id; item hashes come from `content_hash`. When the payload holds two requirements, or two ADRs, with one id, the first in the payload's order is kept and the others are skipped (`INSERT OR IGNORE`; spec v1.9), so such a version imports and gets its `id-unique` violation. `SpecApproved` sets `status` to `approved` and `approved_at` from the event's `created_at`. `PlanCreated` deletes the `task_deps` and `tasks` rows of every `draft` plan and marks those plans `superseded`, then inserts the new plan as `draft`, one `tasks` row per contract (`pending`, `attempt` 0, `contract` as JSON of the validated contract) and one `task_deps` row per `depends_on` entry, all with plain `INSERT`. `PlanApproved` sets the plan's `status` to `approved`. `tasks` also has a last column `cost_usd` (`REAL NOT NULL DEFAULT 0`), written by two rules (SC-90, SC-91; ADR-015). `TaskResolved` with `decision` `retry` sets `attempt` and `cost_usd` of its task to 0 in one `UPDATE`; with `abandon` it writes nothing (the `TaskStateChanged` that follows sets the state). `TaskStateChanged` sets the task's `state` to `to` and, when `to` is `running`, adds 1 to its `attempt` (SC-61; only `to` is looked at, in one `UPDATE`); for a task not in `tasks` it changes no row. `AgentRunStarted` inserts an `agent_runs` row (`id`, `task_id`, `role`, `runtime`, `context_hash` from the payload, `started_at` from the event's `created_at` as `isoformat()`, the other columns null) with a plain `INSERT`. `AgentRunFinished` sets `model`, `exit`, `tokens_in`, `tokens_out`, `cost_usd`, `duration_s` and `ended_at` (its event's `created_at` as `isoformat()`) on the row whose `id` is `run_id`; for a run not in `agent_runs` it changes no row, and its `error` is not projected (no column). It then adds the event's `cost_usd` (null counts as 0) to `tasks.cost_usd` of the run's task, found through `agent_runs.task_id` (reviewer runs count; a run with no task adds nothing). `GateEvaluated` inserts one `gate_results` row (`run_id`, `gate`, `passed` as 0 or 1, `output_path`); its `task_id` is not projected (no column). `CommitRecorded` inserts one `commits` row (`sha`, `task_id`, `run_id`, `branch`); its `spec_version` and `files` are not projected (no column). Both are plain `INSERT`. `SpecValidated` is validated and writes nothing. Event types with no entry in `PAYLOAD_MODELS` are ignored.
- `rebuild(events)`: drops the nine tables, recreates them and applies the given events in `seq` order. The caller passes the events (for example `EventStore.read()`).
- It does not check event sequences (a `from` against the stored state, a `PlanApproved` for an unknown or non-draft plan, an `AgentRunFinished` for an unknown or finished run, a second `AgentRunStarted` for one run id, a repeated `(run_id, gate)` of a gate result or a repeated `sha` of a commit, each of which ends in `sqlite3.IntegrityError`), a payload's `hash` against its `spec`, or the last applied `seq`.

### EventRecorder port
`src/openfactory/ports/event_recorder.py`. The one call a use case makes to record an event (ADR-001). It imports from `openfactory.domain` only.
- `EventRecorder` (Protocol): one method, `record(event: Event) -> StoredEvent`. The event is stored and applied to the projections as one unit. A repeated `event_id` behaves like `EventStore.append`: the same content returns the stored event without applying it again, and different content raises `EventConflictError` (from `ports/event_store.py`).

### SQLite events helpers
`src/openfactory/adapters/sqlite_events.py`. The SQL and row helpers for the `events` table, shared by `sqlite_store` and `sqlite_recorder` so that no SQL for the table is written twice. It has no port and no `TYPE_CHECKING` conformance assertion (ADR-010). None of its functions commits; the caller owns the transaction.
- `create_events_table(conn)`: creates the `events` table with the spec's DDL if it is missing.
- `insert_event(conn, event) -> bool`: `INSERT ... ON CONFLICT(event_id) DO NOTHING`; returns whether a row was written.
- `stored_event(conn, event) -> StoredEvent`: reads the stored row for the event's `event_id` and raises `EventConflictError` if its content, compared as canonical JSON of the envelope, differs from the event's.
- `select_events(conn, *, stream=None, after_seq=0) -> list[StoredEvent]`: stored events with a `seq` above `after_seq`, optionally of one stream, in ascending `seq`.

### SQLite recorder
`src/openfactory/adapters/sqlite_recorder.py`. Implements `EventRecorder` over SQLite (ADR-010). It imports nothing from `openfactory.app`.
- `SqliteEventRecorder(path)`: opens its own connection, sets WAL mode and `PRAGMA busy_timeout = 5000`, then, in one transaction, creates what is missing (the `events` table, the projections, and `projection_state` with its single row `id = 1`, `last_seq = 0`) and catches up.
- Catch-up: every stored event with `seq > last_seq` is applied in `seq` order and `last_seq` is set. It runs only when the recorder opens. A stored payload its model rejects raises `pydantic.ValidationError` whose title is `stored event seq N (<model>)`; a stored event the projector cannot write raises `sqlite3.IntegrityError` whose message starts the same way (no M1 event reaches this case since spec v1.9: a duplicated requirement or ADR id is skipped by the projector, not an error). In both cases the transaction is rolled back, nothing is applied, and the connection is closed.
- `record(event)`: inserts the event, and if it is new applies it with `SqliteProjector` and sets `last_seq` to its `seq`, all in one transaction. Any error rolls the transaction back, so a rejected payload leaves no stored event. A repeated `event_id` applies nothing.
- `rebuild()`: not on the port. In one transaction it reads every stored event, calls `SqliteProjector.rebuild` and sets `last_seq` to the highest `seq` (0 for an empty log); a failure rolls everything back. `projection_state` is updated in place, never dropped.
- `close()` releases the connection.
- Every transaction starts with `BEGIN IMMEDIATE`. `projection_state` is bookkeeping, not a projection; the recorder is its only writer.

### Spec version reference
`src/openfactory/domain/spec_versions.py`. Pure Pydantic v2 model, no I/O. It imports nothing from `adapters`, `app` or `ports`.
- `SpecVersionRef`: `id` (`SpecVersionId`) and `hash` (`ContentHash`), both from `payloads.py`. The model is frozen and rejects unknown fields.

### SpecVersions port
`src/openfactory/ports/spec_versions.py`. The read-only interface to the `spec_versions`, `requirements` and `adrs` projections (ADR-001, ADR-012). It imports from `openfactory.domain` only.
- `SpecVersions` (Protocol): four methods. `latest_approved() -> SpecVersionRef | None` and `current_draft() -> SpecVersionRef | None` return `None` when there is no such version. `next_id() -> str` returns the highest number in any row's id plus one, written with at least two digits (`sv_01` when there is no row), also while a draft exists. `spec_set(version_id: str) -> SpecSet | None` returns the stored spec set of a draft or an approved version, or `None` when the version has no row; a version imported with an empty spec set gives an empty `SpecSet`.

### SQLite spec versions
`src/openfactory/adapters/sqlite_spec_versions.py`. Implements `SpecVersions` over SQLite (ADR-001, ADR-010). It imports nothing from `openfactory.app`.
- `SqliteSpecVersions(path)`: opens its own connection and sets `PRAGMA busy_timeout = 5000`. It runs only `SELECT` on `spec_versions`, `requirements` and `adrs`, creates no table and writes nothing; a database without the `spec_versions` table raises `sqlite3.OperationalError`, which is not handled.
- Every call runs its query again and nothing is cached, so it sees what a recorder on another connection has committed. "Latest approved" is the approved row with the highest id number; ids are compared as integers with `CAST(substr(id, 4) AS INTEGER)`.
- `spec_set(version_id)` reads `components` from the `spec_versions` row (no row gives `None`) and the `requirements` and `adrs` rows of the version with `ORDER BY id`, decodes the JSON columns and validates the result with `SpecSet.model_validate`. The inner lists (`components`, `constrained_by`, `acceptance_criteria`) keep the order the stored arrays hold; item hashes are not returned. For a version imported with a duplicated id the projector kept the first item, so the set is smaller than the payload's.
- `close()` releases the connection.

### Runs port
`src/openfactory/ports/runs.py`. The read-only interface to the `agent_runs` projection (ADR-012). It imports nothing from `adapters` or `app`.
- `Runs` (Protocol): two methods. `next_id() -> str` returns the highest run number in any `agent_runs` row, finished or not, plus one, written as `run_NNNN` with at least four digits (`run_0001` when there is no row). `unfinished_run(task_id: str) -> str | None` returns the id of the task's run whose `exit` is null, or `None`; if there are several, the one with the highest run number. A planner run (null `task_id`) is never returned.

### SQLite runs
`src/openfactory/adapters/sqlite_runs.py`. Implements `Runs` over SQLite (ADR-012, ADR-010). It imports nothing from `openfactory.app`.
- `SqliteRuns(path)`: opens its own connection and sets `PRAGMA busy_timeout = 5000`. It runs only `SELECT` on `agent_runs`, creates no table and writes nothing; a database without the table raises `sqlite3.OperationalError`, which is not handled.
- `next_id` runs one query, `SELECT MAX(CAST(substr(id, 5) AS INTEGER)) FROM agent_runs`, on every call and caches nothing, so it sees what a recorder on another connection has committed.
- `unfinished_run` runs one `SELECT` over `agent_runs` where `task_id = ?` and `exit IS NULL`, highest run number first (`CAST(substr(id, 5) AS INTEGER) DESC`), `LIMIT 1`.
- `close()` releases the connection. The module ends with the `TYPE_CHECKING` assertion against `Runs`.

### Plan and task references
`src/openfactory/domain/plans.py`. Pure Pydantic v2 models, no I/O. It imports from `openfactory.domain` only.
- `PlanRef`: `id` (`PlanId`) and `spec_version` (`SpecVersionId`). It has no `status`; the method that returns it fixes the status. Frozen, rejects unknown fields.
- `CommitRef`: the `sha` (`CommitSha`) and `task_id` (`TaskId`) of one `commits` row; it has no `run_id` or `branch`. Frozen, rejects unknown fields.
- `GateResultRef`: the `gate` (`GateName`) and `passed` (`bool`) of one `gate_results` row; it has no `run_id` or `output_path`. Frozen, rejects unknown fields.
- `Task`: one row of the `tasks` projection with its dependencies: `id` (`TaskId`), `plan_id` (`PlanId`), `state` (`TaskState`), `attempt` (`int`), `contract` (`TaskContract`) and `depends_on` (`list[TaskId]`, read from `task_deps`) and `cost_usd` (`float`, default `0`, the `tasks.cost_usd` column: the sum of the task's runs' costs, nulls as 0). The objective is `contract.objective`. Frozen, rejects unknown fields.

### Plans port
`src/openfactory/ports/plans.py`. The read-only interface to the `plans`, `tasks`, `task_deps`, `commits`, `agent_runs` and `gate_results` projections (ADR-012). It imports from `openfactory.domain` only.
- `Plans` (Protocol): seven methods. `current_draft() -> PlanRef | None` and `approved() -> PlanRef | None` return `None` when there is no such plan; if several rows share the status, the one with the highest id number is returned. `next_id() -> str` returns the highest number in any `plans` row, superseded plans included, plus one, written as `plan_NN` with at least two digits (`plan_01` when there is no row). `tasks(plan_id: str) -> list[Task]` returns the plan's tasks in ascending id, each with its `depends_on`; it returns `[]` for a superseded plan and for a plan id with no row. `live_tasks_referencing(requirement_id: str) -> list[str]` returns, in ascending order, the ids of the tasks whose contract lists the requirement and whose state is neither `abandoned` nor `invalidated`. `latest_commit(plan_id: str) -> CommitRef | None` returns the commit with the highest run number among the plan's tasks, or `None` when the plan has no commit or no row; it does not look at the plan's status. `last_gate_result(task_id: str) -> GateResultRef | None` returns, for the task's implementer run with the highest run number that has a gate result, the gate that comes last in the task's `contract.required_gates` with its `passed`; it returns `None` when the task has no such result or no `tasks` row.

### SQLite plans
`src/openfactory/adapters/sqlite_plans.py`. Implements `Plans` over SQLite (ADR-012, ADR-010). It imports nothing from `openfactory.app`.
- `SqlitePlans(path)`: opens its own connection and sets `PRAGMA busy_timeout = 5000`. It runs only `SELECT` on `plans`, `tasks`, `task_deps`, `commits`, `agent_runs` and `gate_results`, creates no table and writes nothing; a database without those tables raises `sqlite3.OperationalError`, which is not handled.
- Every call runs its queries again and nothing is cached, so it sees what a recorder on another connection has committed. Ids are compared as integers with `CAST(substr(id, 6) AS INTEGER)`; `next_id` takes the `MAX` of that and the two plan reads order by it.
- `tasks` reads the `tasks` rows of the plan with `ORDER BY id` and the `task_deps` rows of those tasks with `ORDER BY depends_on`, and decodes `contract` with `TaskContract.model_validate_json`. The state is returned as the projection holds it; `TRANSITIONS` is not enforced.
- `live_tasks_referencing` selects the tasks not in `abandoned` or `invalidated` with `ORDER BY id` and filters in Python on the decoded contract's `requirements`. It does not look at plan status: the tasks of a superseded draft are gone from `tasks`, and those of a draft plan count.
- `latest_commit` runs one `SELECT` over `commits` joined to `tasks` on the task id, for the tasks whose `plan_id` is the plan's, ordered by `CAST(substr(commits.run_id, 5) AS INTEGER) DESC` with `LIMIT 1`, so run ids are compared by number.
- `last_gate_result` first reads the task's `contract` from `tasks` (no row gives `None`), then runs one `SELECT` over `gate_results` joined to `agent_runs` on `agent_runs.id = gate_results.run_id`, for `role = 'implementer'` and the task, restricted to the run with the highest `CAST(substr(run_id, 5) AS INTEGER)` among the task's implementer runs that have a gate result. In Python it takes the row whose gate has the highest index in the decoded `required_gates`.
- `close()` releases the connection. The module ends with the `TYPE_CHECKING` assertion against `Plans`.

### Validate use case
`src/openfactory/app/validate.py`. Application-layer use case that loads and hashes the spec set, imports it if it changed and runs the rules. It imports only from `openfactory.domain`, `openfactory.ports` and `app/spec_loader.py`, nothing from `adapters`. It returns data and prints nothing.
- `validate(files: SpecFiles, versions: SpecVersions, plans: Plans, recorder: EventRecorder) -> ValidateResult`.
- `ValidateResult`: a frozen model with `outcome` (`unloadable`, `matches_approved` or `validated`), `spec_version` (`None` when unloadable), `violations`, `policy_problems`, `hash` and `validated_event_id` (the last two are set only when a `SpecValidated` was recorded).
- `unloadable`: `load_spec` returned `schema` violations. They are the result's `violations`; no version is read and no event is recorded.
- `matches_approved`: the files' `content_hash` equals the latest approved version's. No event is recorded, the rules are not run, `violations` is empty, and a draft is left as it is.
- `validated`: otherwise. The version id is the current draft's, or `next_id()` when there is no draft. Unless the hash equals the draft's, it records `SpecImported` with `spec` in canonical order, then runs `validate_spec` and records `SpecValidated` with the violations as `RecordedViolation` in the order returned and empty `warnings`. When there is a latest approved version, it reads that version's stored set with `versions.spec_set`, asks `plans.live_tasks_referencing` for each id from `deleted_requirements` and appends one `deleted-requirement` violation per non-empty answer after those of `validate_spec`, so they are recorded in `SpecValidated` too. `violations` holds the rule results.
- Both events are built through the payload models, on stream `spec:<version>` with actor `orchestrator`. `SpecImported` has no `causation_id`; `SpecValidated` carries the `SpecImported` event id when one was recorded in the same call.
- `load_policy` runs in every case; its violations are returned as `policy_problems` and never recorded.
- Events are recorded only through `EventRecorder.record`; the spec versions are read only through `SpecVersions`. If the recorder raises, the error propagates.

### Approve spec use case
`src/openfactory/app/approve_spec.py`. Application-layer use case that runs the validate use case and then records `SpecApproved` or reports why it did not. It imports only from `openfactory.domain`, `openfactory.ports` and `app/validate.py`, nothing from `adapters`. It returns data and prints nothing.
- `approve_spec(files: SpecFiles, versions: SpecVersions, plans: Plans, recorder: EventRecorder) -> ApproveResult`. It calls `validate` itself, passing `plans` through, and does not rely on an earlier run; a `deleted-requirement` violation refuses the approval like any other.
- `ApproveResult`: a frozen model with `outcome` (`ApproveOutcome`: `unloadable`, `nothing_to_approve`, `refused` or `approved`), `spec_version` (the version approved or refused, the latest approved id for `nothing_to_approve`, `None` when unloadable), `violations` and `policy_problems`. It carries no hash and no `SpecApproved` event id.
- `unloadable` and `nothing_to_approve` follow `validate`'s `unloadable` and `matches_approved`; nothing more is recorded. `refused`: `validate` found violations; `SpecApproved` is not recorded.
- `approved`: the files loaded, differ from the latest approved version and have no violations. It records `SpecApproved` through `SpecApprovedPayload` on stream `spec:<version>` with actor `human` and `causation_id` set to the `SpecValidated` event id.
- Policy problems are returned in every case and never block the approval. If the recorder raises, the error propagates.

### List events use case
`src/openfactory/app/list_events.py`. Application-layer use case that reads the event log. It imports only from `openfactory.domain` and `openfactory.ports`, nothing from `adapters`. It returns data and prints nothing.
- `list_events(store: EventStore, stream: str | None = None) -> list[StoredEvent]`: returns `store.read(stream)` unchanged, in ascending `seq`. It never calls `append`.

### CLI
`src/openfactory/cli.py`. The Typer app `app` and the composition root (ADR-011): the one module that may import adapters and use cases and wire them. It sits outside the four layers, and no module under `domain/`, `ports/`, `adapters/` or `app/` imports it. It implements no port. `[project.scripts]` points `openfactory` at `openfactory.cli:app`.
- `init <repo>`: exits 1 with `not a git repository: <repo>` on standard error when `<repo>` has no `.git` entry (a directory or a file); the check runs before anything is created. Otherwise it creates, if missing and in this order, `.openfactory/openfactory.db` (by opening and closing `SqliteEventRecorder`; when the file exists the recorder is not opened), `.openfactory/.gitignore` containing `*`, and `specs/policies.yaml` from the spec's code block, never overwriting a file. It prints `created <path>` or `exists <path>` per item, relative to `<repo>`, and records no events.
- `require_init() -> Path`: the check later commands call first. It returns `Path(".openfactory/openfactory.db")` when `./.openfactory/` is a directory, and otherwise writes "run `openfactory init` first" to standard error and raises `typer.Exit(1)`. It does not search parent directories and does not check that the database file exists. `validate`, `approve spec`, `plan`, `approve plan`, `run` and `events` call it first.
- `_open_adapters(database)`: a private context manager that opens `SqliteEventRecorder` first (only the recorder creates the tables, ADR-010), then `SqliteSpecVersions`, `SqlitePlans` and `SqliteRuns` on the same path, always all three, yields them as the frozen dataclass `_Adapters` (`recorder`, `versions`, `plans`, `runs`) and closes them in reverse order (an `ExitStack` with `closing`). `validate`, `approve spec`, `plan`, `approve plan` and `run` use it.
- `validate`: no arguments. Calls `require_init()`, opens the adapters with `_open_adapters`, builds `FilesystemSpecFiles(Path("specs"))`, calls the `validate` use case with `adapters.plans` and closes the adapters. It prints the lines from `_result_lines` on standard output and exits 1 when there is any violation or policy problem, otherwise 0.
- `approve spec`: a command in the `approve` group (`approve_app`, a Typer sub-app registered with `app.add_typer(approve_app, name="approve")`, with a callback so it stays a group; the group's help reads "Approve a spec version or a plan."). No arguments. Calls `require_init()`, opens the adapters with `_open_adapters`, builds `FilesystemSpecFiles(Path("specs"))`, calls the `approve_spec` use case with `adapters.plans` and closes the adapters. It prints the lines from `_result_lines` on standard output, with the status line `approved <spec version>` only for the `approved` outcome; for `nothing_to_approve` it writes `nothing to approve` to standard error. It exits 0 for `approved` and 1 for every other outcome.
- `plan`: no arguments. Calls `require_init()`, then `_prepare_and_create_plan(database)`, which opens the adapters with `_open_adapters` (they are closed before the result is printed; the warning and any log line are written while they are open), builds `FilesystemSpecFiles(Path("specs"))`, calls `prepare_plan`, writes `spec files differ from approved <spec version>` to standard error when `PlanInputs.spec_files_differ`, then calls `create_plan` with `GitCli(Path("."))` and `ClaudeCodeLLM()`. `_refusal_line` maps `PlanRefusal` to `no approved spec version`, `policy is invalid; run openfactory validate` and `<plan_id> is already approved; use replan`, written to standard error (exit 1). By outcome: `created` prints one `task_id  objective` line per task and `created <plan_id>` (exit 0); `rejected` prints `rejection_lines` of the second reply on standard output (exit 1); `git_failed` and `failed` write `git ls-files failed: <error>` and `planner call failed: <error>` to standard error (exit 1), where `_first_line` gives `<error>` as the first line of `PlannerResult.error`.
- `approve plan`: a command in the `approve` group, function `approve_plan_command`, registered with `@approve_app.command("plan")` (the name `plan` is taken by the top-level command). No arguments. Calls `require_init()`, opens the adapters with `_open_adapters`, calls `approve_plan(versions, plans, recorder)` and closes the adapters before printing. `approved` prints one `task_id  ready` line per id in `result.ready`, in the order the use case gives them, then `approved <plan_id>`, on standard output (exit 0); `no_draft` writes `no draft plan` and `stale_draft` writes `<plan_id> was made for <spec_version>; run openfactory plan` to standard error (exit 1).
- `_configure_logging()`: configures structlog with `add_log_level` and `JSONRenderer` and `PrintLoggerFactory(file=sys.stderr)`, so a log line is a JSON object with `event` and `level` and no timestamp. It is called from the Typer callback `main()`, so it applies to every command.
- `events`: option `--stream S` (a string, default none). Calls `require_init()`, opens `SqliteEventStore` on the returned path (not the recorder, so no catch-up runs and nothing is written; the store creates a missing database file and the `events` table), calls the `list_events` use case, closes the store and prints one line per event on standard output. It prints nothing and exits 0 for an empty log or a stream with no match.
- `_event_line(event) -> str`: one `StoredEvent` as a JSON object with the keys `seq`, `event_id`, `stream`, `type`, `payload`, `actor`, `causation_id` (`null` when absent) and `created_at`, dumped with `json.dumps` with sorted keys at every level, separators `,` and `:`, and `ensure_ascii=False`. `created_at` is `isoformat()` of the stored datetime (offset `+00:00`), the form the adapters write, not Pydantic's `Z` form.
- `_result_lines(violations, policy_problems, status) -> list[str]`: the violation lines sorted on `(rule, subject, message)`, the policy lines sorted the same way, the count line `N violations, M policy problems`, then the status line (`matches approved sv_NN` from `validate`, `approved sv_NN` from `approve spec`) when there is one (`validate` and `approve spec` call it). Each line joins its fields with two spaces; the field tuples are sorted before joining.

- `run [--task ID]`: option `--task` (a string, default none). Calls `require_init()`, opens the adapters with `_open_adapters` and calls `run_plan` with `task_id`, `GitCli(Path("."))`, `ProcessGates(Path("."))`, `GitWorktree(Path("."))`, `ClaudeCodeExecutor(Path("."))`, `ClaudeCodeLLM()`, `FilesystemRunFiles(Path("."))` and `adapters.runs`, `plans`, `versions`, `recorder`; the adapters are closed before anything is printed. All output is written after `run_plan` returns, in this order: each of `RunReport.warnings` to standard error; on a refusal, the line from `_run_refusal_line` to standard error and exit 1 (`no approved plan`, `repository has no commit`, `git failed: <detail>`, `<detail> not found`, `unknown task <detail>`, `<ID> is <detail>, not ready` with the `--task` value as `<ID>`); otherwise, for each `TaskRunResult` in order, `<task id>  <state value>` to standard output, then its `warning` to standard error. It exits 1 when any task taken did not pass, otherwise 0; with no task taken nothing goes to standard output. A long run therefore shows nothing until it ends.

### Task contract models
`src/openfactory/domain/contracts.py`. Pure Pydantic v2 models of a task and the rule that completes one, no I/O. It imports `openfactory.domain.policy` and nothing from `adapters`, `app` or `ports`.
- `PlannedTask`: what the planner emits. `task_id` (string matching `^[A-Z]+-\d{3}$`), `objective`, `requirements`, `acceptance_criteria` and `allowed_paths` (the last three non-empty lists), `components` (list, may be empty), `role` (`implementer` only), and `depends_on` and `forbidden_paths` (lists, default `[]`). It has no `required_gates` or `limits`, and a reply that contains either fails validation.
- `Limits`: `max_runtime_s`, `max_attempts` (integers) and `max_cost_usd` (float), all required and greater than zero.
- `TaskContract(PlannedTask)`: adds `required_gates` (list of `path_check`, `ruff`, `pytest`, `gitleaks`, `review`, in the order given) and `limits`, both required. This is what is stored and executed.
- All three are frozen and reject unknown fields. Entries in the path lists are plain strings; their glob syntax is not checked. The matcher for them is in `domain/path_patterns.py`.
- `REQUIRED_GATES`: tuple of the five gate names `path_check`, `ruff`, `pytest`, `gitleaks`, `review`, declared `Final`.
- `PlannerReply`: frozen, rejects unknown fields; one field, `tasks: list[PlannedTask]`. It is the model that validates the planner's structured result; the list has no minimum length.
- `complete_contract(planned: PlannedTask, policy: Policy) -> TaskContract`: copies the planned task's fields and sets `depends_on` to the planner's list without duplicates, each id at its first position; `forbidden_paths` to the baseline paths, then the policy's list, then the planner's, each string kept at its first position; `required_gates` to `list(REQUIRED_GATES)`; and `limits` from the policy's `max_runtime_s`, `max_attempts` and `max_cost_usd`. Neither input is changed.

### Task state machine
`src/openfactory/domain/states.py`. Pure data, no I/O, no import from `adapters`, `app` or `ports`.
- `TaskState`: `StrEnum` of the nine states `pending`, `ready`, `running`, `gating`, `passed`, `failed`, `escalated`, `abandoned`, `invalidated`, in the spec's order.
- `TRANSITIONS: dict[TaskState, frozenset[TaskState]]`: the allowed transitions, as in the spec's block; `abandoned` and `invalidated` have no targets. It is data only: no function checks a transition and nothing enforces it.

### Plan checks
`src/openfactory/domain/plan_checks.py`. Pure function that checks a planner's tasks against a spec set, no I/O. It imports nothing from `adapters`, `app` or `ports`, and no graph library.
- `PlanRule`: `StrEnum` of the nine rule names of the spec's table: `schema`, `duplicate-task-id`, `unknown-dependency`, `cycle`, `unknown-requirement`, `deprecated-requirement`, `unknown-criterion`, `undeclared-component`, `uncovered`. It is separate from `Rule`. `check_plan` never returns `schema`; that rule belongs to `parse_reply`.
- `ParsedReply`: frozen; `tasks: list[PlannedTask] | None` and `rejections: list[PlanRejection]`. The model does not enforce it, but `parse_reply` returns tasks or rejections, never both: on any rejection `tasks` is `None`, so there is nothing to pass to `check_plan`.
- `parse_reply(structured: object | None) -> ParsedReply`: `None` gives one `schema` rejection with subject `reply` and message `no structured result`. Otherwise it validates with `PlannerReply` and gives one `schema` rejection per Pydantic error, with message `<dotted field path>: <Pydantic msg>` and the subject the `task_id` of the task the error lies in when that value is a string, else `reply`. An empty `tasks` list is not rejected here.
- `PlanRejection`: frozen, rejects unknown fields; `rule` (a `PlanRule`), `subject` (the task id, or the requirement or criterion id for `uncovered`) and `message` (names the offending id).
- `check_plan(tasks: Sequence[PlannedTask], spec: SpecSet) -> list[PlanRejection]`: runs the eight content rules and returns every rejection in one run, one per subject and offending id. Order is the spec table's rule order, then the order of the reply (`uncovered` in spec-set order); no test fixes it, and sorting for output is left to the callers.
- `cycle`: a task is reported when it can reach itself through `depends_on`; a walk in plain Python that does not follow a dependency outside the plan. A task that depends on itself is a `cycle`, not an `unknown-dependency`.
- `uncovered`: each requirement that is not deprecated, and each of its criteria, that no task lists.
- `rejection_lines(rejections: Sequence[PlanRejection]) -> list[str]`: one `rule  subject  message` line per rejection (two spaces between the fields), sorted by rule name, then subject, then message, as strings; the input is not changed. It is the form `plan` prints and `AgentRunFinished.error` stores, and the lines the retry prompt holds.

### Review verdict
`src/openfactory/domain/review.py`. Pure, no I/O; it imports `pydantic`, the standard library and `openfactory.domain.plan_checks` only. `run_task` calls `parse_review_reply` and `review_file_text`.
- `ReviewVerdict`: frozen, rejects unknown fields; `verdict` (`"approve"` or `"reject"`) and `comments` (`str`), both required; the spec's class block.
- `ParsedReview`: frozen; `verdict: ReviewVerdict | None` and `rejections: list[PlanRejection]`.
- `parse_review_reply(structured: object | None) -> ParsedReview`: as `parse_reply`: `None` gives one `schema` rejection with subject `reply` and message `no structured result`; otherwise one `schema` rejection per Pydantic error, message `<field path>: <Pydantic msg>` (only the message without a path). `rejection_lines` of `plan_checks.py` prints them.
- `review_file_text(verdict, error) -> str`: `verdict: <word>` then the comments, or with no verdict the `error`, ending in a line break (added when missing).

### Path patterns and the path check
`src/openfactory/domain/path_patterns.py`. Pure functions, no I/O. It imports `openfactory.domain.contracts` and the standard library only; no `fnmatch`, no `glob`, no new dependency (ADR-014).
- `matches(pattern, path) -> bool`: one pattern against one path relative to the repo root, with `/` separators, case-sensitively. A pattern that ends with `/` gets `**` added; a pattern with no `/` gets `**/` in front (so it matches a file of that name in any directory); then pattern and path are split on `/` and matched segment by segment. `**` as a whole segment matches zero or more segments. Within a segment `*` matches zero or more characters and `?` one character, neither crossing `/`; every other character, `!` and `[` included, matches itself only. The whole path must match.
- `matches_any(patterns, path) -> bool`: true when any pattern matches.
- `violating_paths(changed_paths, contract) -> list[str]`: the paths that match a `forbidden_paths` pattern or match no `allowed_paths` pattern, in the order of `changed_paths` (a repeated path is returned twice); `[]` for an empty list. A path that matches both lists is a violation. Neither argument is changed.

### Tag rule
`src/openfactory/domain/tag_rule.py`. Pure functions, no I/O. It imports `openfactory.domain.contracts`, `openfactory.domain.gates` and the standard library only.
- `uncovered_requirements(marker_lines, changed_paths, contract) -> list[str]`: the ids in `contract.requirements` for which no `MarkerLine` has the id in its `req` and a `file` equal, as a string, to one of `changed_paths`. The result is in contract order, each id once at its first position; no argument is changed. With no marker lines every requirement is uncovered.
- `tag_rule_lines(uncovered) -> list[str]`: one `no tagged test in a changed file: <id>` line per id, in the order given, with no line break; `[]` for an empty list. `run_task` adds the lines to the gate's text.

### Planner prompt
`src/openfactory/app/planner_prompt.py`. Pure functions, no I/O; it imports from `domain` only.
- `build_planner_prompt(spec, policy, tracked_files, rejections=()) -> str`: plain text in fixed order, so equal arguments give equal text. Sections: instructions (the reply form, and what the plan checks enforce: known ids, declared components, full coverage, no cycles, no `required_gates` or `limits`; that every task adds tests under `tests/` with a `req` marker for each of its requirements, so its `allowed_paths` covers them; and a "Path patterns:" block that copies the opening sentence and the six bullets of the spec's "Path patterns" word for word), components, requirements that are not deprecated (id, title, statement, priority, components, `constrained_by` ids, criteria with their text), the bodies of the ADRs those requirements are constrained by (each in an `<adr id="...">` delimiter), forbidden paths (the baseline, then the policy's), the gate names (`REQUIRED_GATES`) and the tracked file names, one per line, in the order given. An empty part (a requirement's `constrained_by`, or the components, ADRs or tracked files) is written as `(none)`.
- Left out: a deprecated requirement whole (id, statement, criteria), an ADR named only by a deprecated requirement or by none, and all file contents.
- Retry form: with `rejections` the prompt is the same text with a last section holding `rejection_lines(rejections)`. It does not hold the rejected reply. One function builds both, so the retry prompt cannot drift from the first.
- `context_hash(prompt) -> str`: SHA-256 of the prompt encoded as UTF-8, 64 lowercase hex characters; the `context_hash` of `AgentRunStarted`.

### Context pack
`src/openfactory/app/context_pack.py`. A pure function, no I/O; it imports from `domain` only (`ContextPack`, `TaskContract`, `SpecSet`, `Requirement`, `matches_any`).
- `build_context_pack(contract, spec, tracked_files) -> ContextPack`: plain text in fixed order, so equal arguments give equal text. Sections: instructions (every new test under `tests/` with a `req` marker, no `git commit`, nothing left outside `allowed_paths` including `__pycache__/`, and the opening sentence and six bullets of the spec's "Path patterns" word for word, as this module's own text), "## Task contract" (`contract.model_dump_json(indent=2)`), "## Requirements" (the requirements the contract names, in the stored set's order, each with id, title, statement, `constrained_by` and only the criteria the contract names), "## ADRs" (the bodies of the ADRs those requirements are constrained by, in stored order, each in an `<adr id="...">` delimiter) and "## Tracked files that match allowed_paths" (the names for which `matches_any(contract.allowed_paths, name)` holds, in the order given, one per line). An empty part is written as `(none)`.
- The spec items come from the `spec` argument only (the stored set of the plan's spec version), by filtering. The pack holds no file contents.
- The module does not import `context_hash`; the caller takes the hash with `context_hash` of `app/planner_prompt.py`, which is unchanged.

### Review prompt
`src/openfactory/app/review_prompt.py`. A pure function, no I/O; it imports from `domain` only. `run_task` calls it, once per reviewer run.
- `build_review_prompt(contract, diff, rejections=()) -> str`: fixed reviewer instructions, `## Task contract` (`model_dump_json(indent=2)`) and `## Staged diff` (the diff text unchanged). Equal arguments give equal text.
- Retry form: with `rejections` the same text gets a last section of `rejection_lines(rejections)`; the rejected reply is not in it.
- The module does not import `context_hash`; the caller takes the hash with `context_hash` of `app/planner_prompt.py`.

### Commit message
`src/openfactory/domain/commit_message.py`. A pure function, no I/O; it imports from `domain` only (`TaskContract`). It is in `domain` and not `app` because the spec fixes the form of the message ("Traceability" › "Commit trailers"), as with `rejection_lines`.
- `build_commit_message(contract, summary, run_id, spec_version) -> str`: paragraphs separated by one empty line, in this order: the subject `<task id>: <objective>` cut to 72 characters, the summary with its leading and trailing whitespace removed (no paragraph when nothing is left), and the trailers `Task`, `Requirements`, `Acceptance-Criteria`, `Agent-Run`, `Spec-Version` as the last paragraph. The id lists are joined with `, ` in contract order. The message ends with one `\n`. Equal arguments give equal text.
- An objective with a line break is used as written; the cut is not adjusted.

### LLM reply
`src/openfactory/domain/llm.py`. Pure Pydantic model, no I/O, no import from `ports`, `adapters` or `app`.
- `LLMReply`: frozen, rejects unknown fields. `structured: object | None` is the runtime's structured result, not validated (the caller validates it with its own model; `None` when the runtime gave none). `model`, `tokens_in`, `tokens_out` and `cost_usd` are `None` when the runtime reported none. `tokens_in` is every input token: uncached, written to the cache and read from it. `duration_s` is a float.

### LLMProvider port
`src/openfactory/ports/llm_provider.py`. The interface for one planner or classifier call.
- `LLMProvider` (Protocol): one method, `complete(prompt: str, schema: dict[str, object]) -> LLMReply`. `schema` is the JSON Schema of the structured result. A reply with no structured result, or one the caller's model would reject, is returned, not raised. Nothing is retried.
- `LLMError(Exception)`: keyword-only `duration_s: float` and `timeout: bool`; its text is `str(error)`. It sits beside the Protocol, as `EventConflictError` does.

### Claude Code LLM adapter
`src/openfactory/adapters/claude_code_llm.py`. `ClaudeCodeLLM(executable="claude", timeout_s=300)` implements `LLMProvider` (ADR-005); it ends with the `TYPE_CHECKING` assertion.
- One process per call: `claude -p --output-format json --json-schema <schema as JSON> --tools ""`, no `--model`. The prompt goes on standard input as UTF-8. The process runs in a new empty temporary directory, so no `CLAUDE.md`, settings or hooks of a repo are loaded.
- Its environment is every variable except `ANTHROPIC_API_KEY`, built from the names so the value is never read; one structlog warning (`anthropic_api_key_removed`) is logged when the name was present. structlog is configured by `cli.py` (`_configure_logging`, called from the Typer callback), not here.
- Envelope fields read, pinned by `tests/fixtures/claude_envelope.json` (captured from Claude Code 2.1.287, ADR-005 names 2.1.286): `structured_output`; the keys of `modelUsage` with each one's `outputTokens` (the model is the single key, or the one with the most output tokens, the first on a tie, `None` when absent, `null` or empty); `usage.input_tokens`, `usage.cache_creation_input_tokens` and `usage.cache_read_input_tokens` (those present summed into `tokens_in`, `None` when none is); `usage.output_tokens`; `total_cost_usd`; `duration_ms` (divided by 1000; the measured duration when absent). Absent metric fields give `None`; an absent or `null` `structured_output` gives `structured` `None`. `is_error` and `subtype` are not read.
- `LLMError` with `timeout` true: the limit passed (`timed out after 300 s`). With `timeout` false: a non-zero exit (standard error stripped, or `claude exited with status N` when empty); a `claude` that cannot be started (`claude could not be started: <OS error>`); standard output that is not a JSON object the private envelope model accepts (`claude output is not a JSON envelope`). `duration_s` is the measured time.
- Tests use a stand-in executable written under `tmp_path`; none starts `claude`.

### GitProvider port
`src/openfactory/ports/git_provider.py`. The interface to git for the plan and run use cases. It imports nothing from `adapters` or `app`.
- `GitProvider` (Protocol): six methods (ADR-012, ADR-014, ADR-015). `tracked_files(worktree: Path | None = None) -> list[str]` returns the tracked files as plain strings, relative to the repo or worktree with `/` as the separator, in git's order. `head_commit(worktree: Path | None = None) -> str | None` returns the sha of the commit `HEAD` points at, as git prints it, or `None` when `HEAD` points at no commit. `stage_changes(worktree: Path, base: str) -> list[str]` stages every change in the worktree, then returns the paths that differ from the commit `base`, in git's order. For the two optional paths, `None` is the repo the provider was made for. `reset_soft(worktree: Path, base: str) -> None` moves the branch checked out in the worktree to `base` and keeps the changes staged. `commit(worktree: Path, message: str) -> str` commits what is staged in the worktree with `message` and returns the new commit's sha. Both paths are required: neither operation is made on the checkout. `staged_diff(worktree: Path, base: str) -> str` returns the text of `git diff --cached <base>` in the worktree; the path is required, and a failed command raises `GitError`.
- `GitError(Exception)`: no extra fields; its text is `str(error)`. It sits beside the Protocol, as `LLMError` does.

### Git CLI adapter
`src/openfactory/adapters/git_cli.py`. `GitCli(repo: Path, executable: str = "git")` implements `GitProvider`; it ends with the `TYPE_CHECKING` assertion.
- A private `_run(worktree, *args, errors="strict")` starts one `git` process with no time limit, decoding output as UTF-8 with the given `errors`; its working directory (`cwd=`) is `repo` when `worktree` is `None`, otherwise `repo / worktree` (an absolute path is used as it is, a relative one is taken against the repo). `_checked(done)` returns standard output or raises `GitError`; the module function `_names` splits output on NUL and drops empty elements, so names are returned as git stores them, unquoted.
- `tracked_files` runs `git ls-files -z`. A file added and not committed is listed; an untracked or ignored file is not. With a worktree it lists that worktree's index, not the checkout's.
- `head_commit` runs `git rev-parse --verify --quiet HEAD` and returns standard output stripped. It returns `None` only when the exit status is exactly 1 and standard error is empty; every other non-zero exit raises `GitError` (checked against git 2.54.0: no commit gives 1 with empty output, a directory that is not a repository gives 128 with a `fatal:` line).
- `stage_changes` starts two processes: `git add -A`, then `git diff --cached --name-only -z --no-renames <base>`, output split on NUL. It stops after a failed `add`; the diff is not started.
- `reset_soft` runs `git reset --soft <base>`, one process. `commit` starts two processes: `git commit --no-verify -m <message>` (the message one argument), then `git rev-parse --verify HEAD` for the sha, standard output stripped; it stops after a failed commit and the second is not started. No `--cleanup`, identity, signing or `--allow-empty` option is passed, so git's default clean-up (`whitespace` on git 2.54.0) and the repo's configuration apply. A commit with nothing staged fails: git writes its text to standard output, so the `GitError` text is `git exited with status 1`.
- `staged_diff` runs exactly `git diff --cached <base>` in `repo / worktree`, one process, no added flag, so the repo's and the user's git configuration apply. It passes `errors="replace"` (the diff holds file contents that need not be UTF-8) and returns standard output unchanged, not stripped. The other methods stay strict.
- `GitError` texts: for a non-zero exit, standard error stripped, or `git exited with status N` when that is empty; for an `OSError` on start, `git could not be started: <OS error text>`.
- Tests run the real `git` on a repository under `tmp_path` (`tests/integration/test_git_cli.py`: `git init`, `git add`, no commit; `tests/integration/test_git_cli_m3.py`: commits and a linked worktree made with `git worktree add`; `tests/integration/test_git_cli_commit.py`: the soft reset and the commit, with failing `pre-commit` and `commit-msg` hooks; `tests/integration/test_git_cli_staged_diff.py`: the staged diff, on a linked worktree and with a stand-in) with `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` removed from the environment, and a stand-in executable for the command line and the failure cases. The test suite requires `git` on the machine.

### WorkspaceManager port
`src/openfactory/ports/workspace_manager.py`. The interface to a task's worktree and branch for the M3 run use case. It imports nothing from `adapters` or `app`; `GitError` comes from `ports/git_provider.py`.
- `WorkspaceManager` (Protocol): three methods (ADR-014). `create(task_id: str, base: str) -> Path` creates the worktree `.openfactory/worktrees/<task id>` on the new branch `openfactory/<task id>` at the commit `base` and returns the worktree's path relative to the repo; it does not remove anything first. `remove(task_id: str) -> None` removes the task's worktree and branch, each only if it exists. `remove_worktree(task_id: str) -> None` removes the worktree if it exists; the branch stays.
- A failed git command raises `GitError`. The returned path is relative; an adapter resolves it against its own repo, never the use case. `create` does not return the branch name.

### Git worktree adapter
`src/openfactory/adapters/git_worktree.py`. `GitWorktree(repo: Path, executable: str = "git")` implements `WorkspaceManager`; it ends with the `TYPE_CHECKING` assertion.
- A private `_run(*args)` starts one `git` process in `repo` (`cwd=`) with no time limit; `_checked(done)` returns standard output or raises `GitError`. They are the adapter's own, with the `GitError` texts of `GitCli` (standard error stripped, or `git exited with status N`; `git could not be started: <OS error text>`); `git_cli.py` is not changed.
- `create` runs `git worktree add .openfactory/worktrees/<id> -b openfactory/<id> <base>`, one process. git creates the missing `.openfactory/worktrees/` directory (confirmed on git 2.54.0).
- `remove_worktree` runs `git worktree remove --force .openfactory/worktrees/<id>` only when that directory exists; `--force` removes a worktree with changed and untracked files. `remove` does that, then runs `git branch -D openfactory/<id>` only when `git rev-parse --verify --quiet refs/heads/openfactory/<id>` exits 0; any non-zero status counts as no branch. No `git worktree prune`.
- The caller's environment is passed to `git` as `GitCli` does (decision of 2026-10-13).
- Tests (`tests/integration/test_git_worktree.py`) run the real `git` on a repository under `tmp_path` with `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` removed, and a stand-in executable for the command line and the failure cases; `tests/unit/test_workspace_manager_port.py` checks the port's shape.

### RunFiles port
`src/openfactory/ports/run_files.py`. The interface to the files of a run for the M3 run use case, so that `app` writes no file (ADR-006, ADR-014). It imports nothing from `adapters` or `app`.
- `RunFiles` (Protocol): two methods (ADR-015). `write(run_id: str, name: str, text: str) -> Path` writes `text` to the file `name` of the run and returns the file's path relative to the repo, `.openfactory/runs/<run id>/<name>`. The returned path does not depend on the process's working directory; the use case stores its POSIX form in `output_path`. `read(path: Path) -> str` returns the text of the run file at `path`, relative to the repo as `write` returned it.
- No method gives or creates the run's directory without writing a file; who creates it for `transcript.json` is open (audit F-5, "Later" in `docs/progress.md`).

### Filesystem run files
`src/openfactory/adapters/filesystem_run_files.py`. `FilesystemRunFiles(repo: Path)` implements `RunFiles`; it ends with the `TYPE_CHECKING` assertion.
- `write` creates `repo/.openfactory/runs/<run id>/` when it is missing (parents included) and writes `text.encode("utf-8")` with `write_bytes`, so the bytes are the text as given and a file of the same name is replaced. Other files in the directory are left as they are.
- It returns `Path(".openfactory/runs") / run_id / name`, resolved against its own `repo`, never the working directory.
- `read` reads `repo / path` as bytes and decodes strict UTF-8, so the text comes back exactly as written (non-ASCII, `\r\n`, no final line break). The path is resolved against `repo`, never the working directory; a missing file raises the uncaught `OSError`.
- `run_id`, `name` and `path` are not checked and an `OSError` is not caught.
- Tests: `tests/unit/test_run_files_port.py` checks the port's shape; `tests/integration/test_filesystem_run_files.py` runs on a directory under `tmp_path`.

### Agent run result

- `ContextPack = str`: one prompt text.
- `RunResult`: frozen, rejects unknown fields, eight required fields in the spec's order: `exit` (`RunExit` from `domain/payloads.py`: `ok`, `error`, `timeout`), `model`, `tokens_in`, `tokens_out`, `cost_usd` (each `None` when the runtime reported none), `duration_s` (float), `error` (`None` when `exit` is `ok`) and `summary` (the agent's final message). Its fields without `summary` are the fields of `AgentRunFinishedPayload` without `run_id`.

### AgentExecutor port
`src/openfactory/ports/agent_executor.py`. The interface to one agent run for the M3 run use case (ADR-005, ADR-014). It imports only from `openfactory.domain`.

### Claude Code executor adapter
`src/openfactory/adapters/claude_code_executor.py`. `ClaudeCodeExecutor(repo: Path, executable: str = "claude")` implements `AgentExecutor` (ADR-005, ADR-014); it ends with the `TYPE_CHECKING` assertion. No time-limit parameter: the limit is the contract's.
- One process per `run`: `claude -p --output-format json --tools "Read,Glob,Grep,Edit,Write,Bash" --allowedTools "Read,Glob,Grep,Edit,Write,Bash"` (each list one comma-joined argument), no `--model`, no `--json-schema`, no permission-bypass flag. The context pack goes on standard input as UTF-8. `timeout` is `contract.limits.max_runtime_s`. Tools and flags were confirmed on `claude --help` and by one real run of Claude Code 2.1.287 (fixture below). `--tools` speaks of the built-in set; MCP tools and user-level or target-repo Claude Code configuration may stay present (not checked).
- Paths: the working directory is `repo / workdir` and the envelope is written under `repo / output_dir`; a relative path is taken against the adapter's repo, an absolute one is used as it is, whatever the process's working directory.
- Environment: every variable except `ANTHROPIC_API_KEY`, built from the names so the value is never read; one structlog warning (`anthropic_api_key_removed`) when the name was present.
- `transcript.json`: standard output is captured as bytes and written with `write_bytes` to `repo / output_dir / transcript.json` (directory created, parents included) before it is parsed, so after a process that ran to its end the file holds the bytes as `claude` printed them; after a timeout or a `claude` that cannot be started it is written empty (decision of 2026-10-14). The file exists after every `run`.
- Envelope fields read, pinned by `tests/fixtures/claude_agent_envelope.json` (Claude Code 2.1.287): `result` (required string, the `summary`); the keys of `modelUsage` with each one's `outputTokens` (the model with the most, the first on a tie); `usage.input_tokens`, `usage.cache_creation_input_tokens` and `usage.cache_read_input_tokens` (summed into `tokens_in`); `usage.output_tokens`; `total_cost_usd`; `duration_ms` (divided by 1000; the measured duration when absent). The result has `exit` `ok` and `error` `None`. `is_error` and `subtype` are read for a failed process (below).
- A failed process is returned, never raised (`done.check_returncode()` is gone); `summary` is `""` and `duration_s` the measured duration. `subprocess.TimeoutExpired` gives `exit` `timeout` and `error` `timed out after <max_runtime_s> s`; an `OSError` from starting the process gives `exit` `error` and `claude could not be started: <OS error>`. In both the transcript is empty and the four nullable metrics are `None`.
- After a process that ran to its end the checks run in this order: (1) error envelope (`is_error` is `True`, or `subtype` a string other than `success`): `error` is the envelope's `result` when a non-empty string, else `claude reported an error: <subtype>`, else `claude reported an error`; (2) non-zero exit: standard error decoded as UTF-8 with replacement and stripped, else `claude exited with status N`; (3) the envelope does not validate (`result` is a required string) or the output is not JSON: `claude output is not a JSON envelope`; (4) success as above. All give `exit` `error`.
- Models: `_Metrics` (`usage`, `modelUsage`, `total_cost_usd`) is the base of `_Envelope` (adds required `result` and `duration_ms`) and of the all-optional `_Reported` (adds `is_error`, `subtype`, `result`, each of any type). For a failed process whose standard output is a JSON object that `_Reported` accepts, `model`, `tokens_in`, `tokens_out` and `cost_usd` are read from it; they are `None` when the output is not a JSON object or its metric fields do not validate. One private helper `_result` builds every `RunResult`; `_write_transcript` creates the directory and writes the file.
- The adapter has its own envelope models and helpers; `claude_code_llm.py` is not changed. No real error envelope has been observed: the `is_error` and `subtype` rule is tested on the fixture edited by hand. Nothing calls the adapter yet.
- Tests (`tests/integration/test_claude_code_executor.py` and `tests/integration/test_claude_code_executor_failures.py`) use a stand-in executable written under `tmp_path`; none starts `claude`.

### process_gates adapter
`src/openfactory/adapters/process_gates.py`. `ProcessGates(repo: Path)` implements `GateRunner` (ADR-015, ADR-016, ADR-017); it takes no executable parameters, and ends with the `TYPE_CHECKING` assertion against the port. It imports from `openfactory` only `domain` and `ports`.
- `missing_tool()`: the first of `uv` and `gitleaks` for which `shutil.which` finds nothing on `PATH`, else `None`.
- `run("ruff", worktree, timeout_s)`: `uv run ruff check`, then `uv run ruff format --check`; both always run, each in `repo / worktree` with its own `timeout_s` limit. `passed` is true when both exit 0; `finding` is false.
- `run("gitleaks", worktree, timeout_s)`: `gitleaks git --pre-commit --staged --redact --no-banner --exit-code 3 .` from `PATH` in `repo / worktree`. Exit 0 passes; exit 3 is a finding (`passed` false, `finding` true); any other exit, a timeout or a command that cannot start fails the gate with `finding` false.
- `marker_lines` is `[]` for both gates. A failure is returned, never raised.
- Text, per command: a `$ <shlex.join(cmd)>` line, then standard output, then standard error (UTF-8, `errors="replace"`), each non-empty part ending in `\n`. A timeout gives `timed out after <timeout_s> s` and a command that cannot start gives `<executable> could not be started: <OS error>`, in place of the output, with no partial output (decisions.md, 2026-10-16).
- `run("pytest", worktree, timeout_s)`: two commands in `repo / worktree`, `uv run pytest --collect-only -q -p openfactory_req tests/` then `uv run pytest -p openfactory_req tests/`; both always run, each with its own `timeout_s` limit. `passed` is true when both exit 0; `finding` is false. `PYTHONPATH` is the `pytest_plugin/` directory, then the caller's `PYTHONPATH` when set and not empty, for both. For the first command only, `OPENFACTORY_REQ_OUT` names a file made with `tempfile.mkstemp()` and deleted in a `finally`; its lines become `marker_lines`, read whatever the command's outcome (a missing or empty file gives `[]`). A line `MarkerLine` rejects gives `passed` false, `marker_lines` `[]` and a last text line `invalid marker line: <the line>`; nothing is raised (decisions.md, 2026-10-19).
- The caller's environment is passed to `uv` and `gitleaks`, and to `uv` for `pytest` with the two variables above added.
- Tests: `tests/integration/test_process_gates.py` on stand-in `uv` and `gitleaks` scripts first on `PATH`; `tests/integration/test_process_gates_gitleaks.py` on the real `gitleaks` and `git`, skipped where `gitleaks` is not on `PATH`; `tests/integration/test_process_gates_pytest.py` (16) for the `pytest` gate.

### Plan use case: the planner call
`src/openfactory/app/plan.py`. Depends on `domain` and `ports` and on `app/planner_prompt.py`; it imports nothing from `adapters` or `cli.py`, and prints nothing.
- `run_planner(spec_version, spec, policy, tracked_files, *, llm, runs, plans, recorder) -> PlannerResult` makes at most two attempts. Each attempt is a run: `Runs.next_id` (read after the earlier run started), `AgentRunStarted` (stream `run:<id>`, role `planner`, `context_hash` of the prompt), `LLMProvider.complete(prompt, PlannerReply.model_json_schema())`, `parse_reply`, `check_plan` when tasks loaded, then `AgentRunFinished`. The finish is recorded after the checks: a rejected reply has `exit: ok` and `error` set to its `rejection_lines` joined by newlines; an accepted one has `error: null`.
- Retry: a rejected reply (a `schema` rejection, a missing structured result, or a failed check) is retried once, with `build_planner_prompt(..., rejections=<the first reply's>)`, as a second pair of run events. The retry is inside `run_planner`; a helper shared with the classifier waits for M6.
- Failed process: an `LLMError` ends the attempt with `AgentRunFinished` (`exit` `timeout` or `error`, `error` the `str(error)` unchanged, `duration_s` from the error, model, tokens and cost null). It is not retried, and it ends the function whether it came first or second.
- Accepted reply: `Plans.next_id` is read, `complete_contract` runs per task, the contracts are sorted by `task_id`, and `PlanCreated` is recorded on stream `plan:<id>` with `policy_hash(policy)` and the `run_id` of the accepted run. Every event has actor `orchestrator`, and its `causation_id` is the `event_id` of the event recorded just before it (the first has none).
- `PlannerResult`: frozen, rejects unknown fields; `outcome` (`PlannerOutcome`: `created`, `rejected`, `failed`, and `git_failed`, which only `create_plan` returns), `plan_id`, `tasks` (the stored contracts), `rejections` (the second reply's, for `rejected`) and `error` (the whole text, for `failed` and `git_failed`). A private `_Attempt` model and `_attempt` function carry one run. `create_plan` can also return `git_failed` (next section).
- Tests (`tests/unit/test_plan_use_case.py`) use in-memory fakes for the recorder, `Runs`, `Plans` and the LLM.

### Run use case: one task
`src/openfactory/app/run.py`. Depends on `domain`, `ports`, `app/context_pack.py` and `app/planner_prompt.py` (`context_hash`); it imports nothing from `adapters` or `cli.py`, does no I/O of its own and prints nothing. `run_plan` (below) calls it; the `run` command in `cli.py` is its only caller outside tests.
- `run_task(task, plan, spec, *, causation_id=None, git, gates, workspace, executor, llm, run_files, runs, plans, recorder) -> TaskRunResult` runs the per-task sequence on one `ready` task. `plan` is the `PlanRef`, `spec` the stored `SpecSet` of the plan's spec version, `causation_id` the event recorded just before for this task in the same command, or `None`.
- Sequence: record `ready` to `running`; `<base>` is `Plans.latest_commit(plan.id).sha`, else `GitProvider.head_commit()`; `WorkspaceManager.remove`, then `create(task.id, base)`; `build_context_pack` over `GitProvider.tracked_files(worktree)`; `Runs.next_id`, `AgentRunStarted` (with `context_hash` of the pack), `AgentRunFinished` (the `RunResult` without `summary`) around `AgentExecutor.run(contract, pack, worktree, Path(".openfactory/runs") / run_id)`. An `exit` other than `ok` goes `running` to `failed` with reason `run error` or `run timeout`.
- For `ok`: `running` to `gating`, then `GitProvider.stage_changes(worktree, base)`. No changed path gives `failed` with reason `no changes` and no `GateEvaluated`. Otherwise `violating_paths` and one `GateEvaluated` (`path_check`). A violation writes `path_check.txt` through `RunFiles` (the paths in the order `violating_paths` returns them, each followed by `\n`), then `gating` to `failed` with reason `path_check` and `failed` to `escalated` with reason `path violation`. A pass then runs `ruff`, `pytest` and `gitleaks` in that order through `GateRunner.run(gate, worktree, contract.limits.max_runtime_s)`, always all three, whatever fails earlier. For each, the text is written to `<gate>.txt` through `RunFiles` (on a pass and a failure) and a `GateEvaluated` is recorded with `output_path` the path `write` returned. For `pytest`, `uncovered_requirements(marker_lines, changed paths, contract)` is applied: when it is not empty the gate fails, also if `pytest tests/` passed, and `tag_rule_lines` are appended to the text (a `\n` first when the text is non-empty and lacks one, then each line followed by `\n`). When `gitleaks` gave `finding`, `gating` goes to `failed` and `failed` to `escalated`, both with reason `secret found`, whatever else failed. Otherwise a failed gate gives `gating` to `failed` with reason the first failed gate in `required_gates` order. When none of the three failed, the `review` gate runs: `GitProvider.staged_diff(worktree, base)` (a `GitError` gives `failed` with reason `git: <first line>`, with no reviewer event and no `review` `GateEvaluated`), then one reviewer run through `_review_attempt` (`Runs.next_id`, `AgentRunStarted` with role `reviewer` and the `context_hash` of `build_review_prompt(contract, diff)`, `LLMProvider.complete(prompt, ReviewVerdict.model_json_schema())`, `parse_review_reply`, `AgentRunFinished`). An `LLMError` gives `exit` `timeout` or `error`, null metrics and `error` `str(error)`; a reply gives `exit` `ok`, the reply's metrics and `error` the sorted rejection lines joined by newlines, or null. A rejected reply is retried once with `build_review_prompt(contract, diff, rejections=...)`; a failed process is not. The diff goes into the prompt unchanged. `review.txt` is written under the implementer's run id with `review_file_text(verdict, error)`, `error` being the last reviewer run's, and a `GateEvaluated` (`review`, the implementer's `run_id`, `passed` true only for `approve`) follows. Anything but `approve` gives `gating` to `failed` with reason `review`, with nothing committed. Every reviewer event goes through `_Chain`. When `approve`, `run_task` calls `GitProvider.commit` with `build_commit_message`, records `CommitRecorded` (branch `openfactory/<task id>`, built here; `files` sorted), moves to `passed` and calls `WorkspaceManager.remove_worktree`.
- Cost limit: right after each `AgentRunFinished` (the implementer's, and each reviewer run's), before the implementer's `exit` is looked at and before a reviewer reply is used, `_over_cost_limit` re-reads `Plans.tasks(plan.id)` and compares the task's `cost_usd` with `contract.limits.max_cost_usd`. When it is greater (equal does not count), `run_task` records `failed` then `escalated` through `_Chain`, both with reason `cost limit`, and returns `escalated`: no further gate, no `review` `GateEvaluated`, no commit, and the reason replaces `run error` or `run timeout`.
- Every event has actor `orchestrator` and points at the one recorded before it, run events included (`causation_id`). The two run events are on stream `run:<run id>`, the rest on `task:<task id>`.
- `_Chain` (private) records each event and checks every `TaskStateChanged` against `TRANSITIONS` from the task's current state before recording; a transition not allowed raises `ValueError` (`<task id>: no transition from <from> to <to>`) and records nothing. The payload is built from a dict with the key `from`.
- `TaskRunResult`: frozen, rejects unknown fields; `task_id`, `state` (`passed`, `failed` or `escalated`) and `last_event_id` (for a pass, the `gating` to `passed` event) and `warning` (`str | None`, default `None`).
- Git failures: a `GitError` from the `<base>` read, `remove`, `create` or `tracked_files` (before `AgentRunStarted`), or from the tip read, `reset_soft`, `stage_changes` or `commit` (while `gating`), moves the task to `failed` with reason `git: <first line of the error>`. Nothing more is called; the worktree and branch are left for the next attempt's `remove`. Before `AgentRunStarted` no run event is recorded and the executor is not called. The `<base>` read comes after `ready` to `running`, so it falls under this rule.
- Soft reset: after an `ok` exit, once `running` to `gating` is recorded and before `stage_changes`, `head_commit(worktree)` is read; when it is not `<base>`, `GitProvider.reset_soft(worktree, base)` undoes the agent's commits and keeps the changes. There is no reset after an `error` or `timeout` exit.
- Warning: a `GitError` from `remove_worktree` after a pass records nothing and leaves the state `passed`; `TaskRunResult.warning` is then `worktree of <task id> not removed: <first line>`, else `None`. The use case does not print it; the `run` command writes it to standard error after the task's line.
- Tests (`tests/unit/test_run_task.py`) use in-memory fakes of the eight ports.

### Run use case: the Restart repair
Also in `app/run.py`. `repair_plan(plan, *, workspace, runs, plans, recorder) -> RepairResult` repairs the approved plan from the projections ("Restart"). It reads `plans.tasks(plan.id)` and `plans.latest_commit(plan.id)` once. `run_plan` calls it once per `run`.
- Step 1, ascending task id: a `gating` task that is the `latest_commit` task (single chain: only one `run` works at a time, so an interrupted gating task's commit is the newest) moves to `passed`, then `WorkspaceManager.remove_worktree`. A `GitError` there records nothing and adds `worktree of <task id> not removed: <first line>` to the warnings.
- Step 2, ascending task id: every other `running` or `gating` task. If `Runs.unfinished_run` gives a run id, `AgentRunFinished` is recorded on `run:<run id>` (`exit` `error`, `error` `interrupted`, `duration_s` 0, other nullable fields null), then the task moves to `failed` with reason `interrupted`.
- Step 3: `_promotable(tasks)` gives the `pending` tasks with no dependencies or all dependencies `passed` (a task step 1 passed counts), ascending id; each moves to `ready`. `run_plan` reuses it for promotion after a pass.
- Every event has actor `orchestrator` and a null `causation_id`; each transition goes through `_Chain.move`, checked against `TRANSITIONS`.
- `RepairResult`: frozen, rejects unknown fields; `warnings` (in order) and `last_event_ids` (task id to its last repair event id, so the loop can point a promoted task's first `ready` to `running` at it).
- Tests (`tests/unit/test_repair_plan.py`) use in-memory fakes of `Plans`, `Runs`, `WorkspaceManager` and `EventRecorder`.

### Run use case: the loop
Also in `app/run.py`. `run_plan(*, task_id=None, git, gates, workspace, executor, llm, run_files, runs, plans, versions, recorder) -> RunReport` is the whole of "`run`" as data; it prints nothing; the `run` command in `cli.py` wires it.
- Refusals, in this order, before any event and with no `WorkspaceManager` call: `Plans.approved()` is `None` gives `no_approved_plan` (no git call); `head_commit()` raising `GitError` gives `git_failed` with `detail` the first line; `head_commit()` `None` gives `no_commit`, checked even when the plan already has a commit; `GateRunner.missing_tool()` returning a name gives `tool_not_found` with `detail` that name (SC-115). `run_plan` itself calls only `missing_tool()` and passes `gates` and `llm` to `run_task`.
- Then `repair_plan`, and the stored spec set of `plan.spec_version` read once with `SpecVersions.spec_set` (not the latest approved version); `run_plan` asserts it is not `None`.
- Loop with no `task_id`: re-read `Plans.tasks(plan.id)`, take the `ready` task with the lowest id (as a string) and call `run_task`, repeat until none is `ready`. A task that does not pass does not stop the loop.
- Promotion: after a pass, each id `_promotable` gives, in ascending order, moves `pending` to `ready` through `_Chain.move` with `causation_id` the passing task's `last_event_id`. The promoted tasks are taken in the same call.
- Causation map: starts as `RepairResult.last_event_ids`; each promotion adds its event id. `run_task` gets `causation_id` from it for the task, else `None`.
- `task_id` given: after the repair, an id not in the plan gives `unknown_task` (`detail` the id); a task not `ready` gives `not_ready` (`detail` its state). Both keep the repair's events and return its warnings. Otherwise that task runs once and the promotion is recorded, but the promoted tasks are not taken.
- `RunRefusal` (`StrEnum`: `no_approved_plan`, `no_commit`, `git_failed`, `tool_not_found`, `unknown_task`, `not_ready`) and `RunReport` (frozen, `extra="forbid"`; `refusal`, `detail`, `warnings` the repair's, `tasks` the `TaskRunResult`s in the order taken). `cli.py` builds the refusal lines.
- Tests (`tests/unit/test_run_plan.py`, 20) use in-memory fakes of the eight ports; the fake `Plans` reflects the `TaskStateChanged` events the fake recorder stored.

## Data flow
<!-- updated when a milestone changes it -->
Events are stored in the SQLite `events` table, which assigns `seq`. There are two write paths, `EventRecorder.record` and `EventStore.append`; use cases are meant to use only the first (ADR-001). Stored events are read back in `seq` order by `EventStore.read`, whose callers are the `list_events` use case behind the `events` command and, in later tasks, replay. Specs are validated by the `validate_spec` function, which returns every violation found.

Use cases build the payload of a spec event through the models in `payloads.py`. The validate use case (`app/validate.py`) does so for `SpecImported` and `SpecValidated`, converting each `SpecViolation` to a `RecordedViolation`. The approve-spec use case (`app/approve_spec.py`) builds `SpecApproved` through `SpecApprovedPayload`.

`SqliteProjector` validates each stored payload against `PAYLOAD_MODELS` and writes the `spec_versions`, `requirements`, `adrs`, `plans`, `tasks`, `task_deps`, `agent_runs`, `gate_results` and `commits` projections, one event at a time or by a rebuild from the event log. Its only caller is `SqliteEventRecorder`, which appends an event, applies it and sets `projection_state.last_seq` in one transaction, applies unapplied events when it opens a database, and rebuilds the projections in one transaction. The validate use case calls the recorder through the `EventRecorder` port; the approve-spec use case records `SpecApproved` the same way. The `validate` command wires `SqliteEventRecorder` to the validate use case, and the `approve spec` command wires it to the approve-spec use case. Use cases must write through the recorder only; an event appended through `EventStore.append` while a recorder is open is not applied by that recorder (ADR-010).

Spec file text reaches the application layer through the `SpecFiles` port, not by reading the filesystem directly; `FilesystemSpecFiles` is the adapter. `load_spec` parses the YAML and ADR front matter from that text and returns either a `SpecSet` or the `schema` violations. It does not run `validate_spec`; the validate use case runs the content rules only when the load produced a spec set. `validate` calls `load_spec`. `load_policy` reads `policies.yaml` the same way and returns either a `Policy` or the `schema` violations; it is separate from `load_spec`, and the policy is not part of the spec set or its hash. `validate` calls `load_policy` in every case and returns its violations as policy problems.

Use cases read the spec version projections only through the `SpecVersions` port, to compare hashes and choose the spec version id; `SqliteSpecVersions` is the adapter and reads `spec_versions`, `requirements` and `adrs` on its own connection. The validate use case calls the port and `Plans`, and the approve-spec use case reaches it through `validate`. The CLI (`cli.py`) has `init`, which uses `SqliteEventRecorder` to create the database, and `validate`, which wires the recorder, `SqliteSpecVersions`, `SqlitePlans` and `FilesystemSpecFiles` to the validate use case, and `approve spec`, which wires the same four to the approve-spec use case; `_open_adapters` now opens the recorder and the three read adapters for `validate`, `approve spec`, `plan` and `approve plan`, and `approve plan` wires them to the approve-plan use case. `events` wires `SqliteEventStore` to the `list_events` use case and renders each stored event with `_event_line`; it reads the log only. `run` wires `GitCli`, `GitWorktree`, `ClaudeCodeExecutor`, `ClaudeCodeLLM` and `FilesystemRunFiles` (each but `ClaudeCodeLLM` on `Path(".")`) and the recorder, `SqlitePlans`, `SqliteSpecVersions` and `SqliteRuns` to `run_plan`, then prints the report after the call returns.

`SpecVersions.spec_set` and `Runs.next_id` exist, with `SqliteSpecVersions` and `SqliteRuns` behind them, for the plan use case; `run_planner` calls `Runs.next_id`, and `prepare_plan` calls `spec_set`. The five `Plans` reads (`current_draft`, `approved`, `next_id`, `tasks`, `live_tasks_referencing`) exist the same way, with `SqlitePlans` behind them, for the plan, approve-plan and `deleted-requirement` code; `run_planner` calls `next_id`, `prepare_plan` calls `approved`, `approve_plan` calls `current_draft` and `tasks`, and `validate` calls `live_tasks_referencing` for each deleted requirement.

The task contract models and the task state machine are used by the M2 payload models (`TaskContract` inside `PlanCreatedPayload`, `TaskState` in `TaskStateChangedPayload`); `run_planner` builds `PlanCreated`, and `approve_plan` builds `TaskStateChanged` (the `approve plan` command calls it). `complete_contract` and `policy_hash` are called by `run_planner`, which builds `PlanCreated` with complete contracts and the policy's hash. `check_plan` is run by `run_planner` on a reply that passed the reply model, and the reply is rejected when it returns any rejection. `parse_reply` is the step before it: it turns the planner's structured result into validated tasks or `schema` rejections.

`Plans.latest_commit` and `Runs.unfinished_run` (with `CommitRef`) exist, with `SqlitePlans` and `SqliteRuns` behind them, for the M3 run use case, which finds `<base>` and repairs an interrupted task from them; `run_task` calls `latest_commit` for `<base>`; `repair_plan` calls `latest_commit` and `unfinished_run`. `run_task` also calls `Runs.next_id`, for the implementer and each reviewer run.

`Plans.last_gate_result` (with `GateResultRef`) exists, with `SqlitePlans` behind it, for the M4 `status` command; nothing calls it yet.

`matches`, `matches_any` and `violating_paths` (`domain/path_patterns.py`) exist for the M3 run use case and the context pack; `build_context_pack` calls `matches_any`, its first caller; `run_task` calls `violating_paths`; no use case calls `matches` yet.

`build_context_pack` (`app/context_pack.py`) exists for the M3 run use case, which will pass it the contract, the plan's stored spec set and `GitProvider.tracked_files(worktree)` and hash the text with `context_hash`; `run_task` calls it, and the `run` command runs it through `run_plan`.

`build_commit_message` (`domain/commit_message.py`) exists for the M3 run use case, which will pass it the contract, the implementer run's summary and id and the plan's spec version, and give the text to `GitProvider.commit`; `run_task` calls it, and the `run` command runs it through `run_plan`.

`LLMProvider` and `ClaudeCodeLLM` exist for the plan use case; `run_planner` and `run_task` (the reviewer) call the port, and the `plan` and `run` commands wire the adapter.

`GitProvider` and `GitCli` exist for the plan use case; `create_plan` calls `GitProvider.tracked_files` to get the files for the planner prompt, and the `plan` command wires them. `head_commit`, `tracked_files` with a worktree and `stage_changes` exist for the M3 run use case (choose `<base>`, refuse a repo with no commit, build the context pack, run the path check); `reset_soft` and `commit` exist for the same use case, to discard the agent's commits and make the orchestrator's; `run_task` calls `head_commit`, `tracked_files`, `reset_soft`, `stage_changes` and `commit`. `staged_diff` exists for the M4 review gate; `run_task` calls it once, after the three gates pass.

`WorkspaceManager` and `GitWorktree` exist for the M3 run use case, which creates a task's worktree and branch before the agent runs and removes them after a pass and in the repair; `run_task` calls `remove`, `create` and `remove_worktree`, `repair_plan` calls `remove_worktree`, and the `run` command wires them.

`RunFiles` and `FilesystemRunFiles` exist for the M3 run use case, which writes the output file of a gate through the port; `run_task` calls `write` for a failed path check, and the `run` command wires them. `read` exists for the M4 failure report; nothing calls it yet.

`AgentExecutor` and `RunResult` exist for the M3 run use case, which runs the agent in a task's worktree through the port; `ClaudeCodeExecutor` is the adapter and returns a failed process as a result (error or timeout) as well as a success; `run_task` calls the port, and the `run` command wires the adapter.

`GateRunner`, `GateOutput`, `MarkerLine` and `ProcessGate` exist for the M4 run use case, which runs `ruff`, `pytest` and `gitleaks` through the port (`run_task`); `run_plan` already reads `missing_tool()` for its `<tool> not found` refusal. `ProcessGates` is the adapter for the three gates; for `pytest` it loads the `openfactory_req` plugin, which writes each collected test's file and `req` ids for `marker_lines`. `missing_tool()` is called by `run_plan`; `run` by `run_task` for the three gates; `review` is an `LLMProvider` call, not a `GateRunner` one.

`run_task` calls `uncovered_requirements` and `tag_rule_lines` (`domain/tag_rule.py`) with the `pytest` gate's `marker_lines`, the path check's changed paths and the contract.

`build_planner_prompt`, `context_hash` and `rejection_lines` are called by `run_planner`, which builds the prompt from the approved spec set, the policy and the tracked files, hashes it into `AgentRunStarted`, and builds the retry prompt from a rejected reply's rejections.

`run_planner` (`app/plan.py`) calls `Runs.next_id`, `Plans.next_id`, `LLMProvider.complete`, `parse_reply`, `check_plan`, `complete_contract`, `policy_hash`, `build_planner_prompt`, `context_hash` and `rejection_lines`, and records through `EventRecorder`. The `plan` command reaches it through `create_plan`.

`prepare_plan` (`app/plan.py`) calls `SpecVersions.latest_approved`, `Plans.approved`, `load_policy`, `load_spec`, `content_hash` and `SpecVersions.spec_set`. `create_plan` calls `GitProvider.tracked_files` and `run_planner`. The `plan` command calls `prepare_plan` and then `create_plan`, and wires `SqliteEventRecorder`, `SqliteSpecVersions`, `SqlitePlans`, `SqliteRuns`, `FilesystemSpecFiles`, `GitCli` and `ClaudeCodeLLM`.
